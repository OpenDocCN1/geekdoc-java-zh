Introduction to Apache Kafka

Apache Kafka provides publish-subscribe system. The producers publish data and the subscriber consumes the data. The data streams are processed quickly and efficiently within seconds. It is capable of processing real-time data. The data and information being streamed are also stored in a fault-tolerant manner. The messages sent to the Kafka are stored in multiple brokers to ensure fault-tolerance. Apache Kafka is written using Scala and Java. It is an open-source platform; therefore, it can be used without having to pay a fee for license.

The user can indicate the time duration for which the data has to be stored and the amount of data that needs to be stored. After the indicated time duration, the data will be purged. The Kafka messages are stored with a time stamp within partitions:

Figure 1.1: High-level Overview of Kafka

The figure 1.1 shows the high-level overview of message flow in Kafka. There are n producers producing messages and there are m consumers consuming the messages. The messages produced by producers are identified by a name called topic and a consumer may consume from multiple topics. The relay of these messages from the producer to the consumer and its management is performed by the zookeeper.

Kafka versus traditional message queues

The following are some of the differences between the traditional message queue and Kafka:

  • In traditional message queues, the messages are removed from the queue once they are read. However, in Kafka, the messages persist even after it is read. This time duration for which the message would persist can be configured.
  • Since the Kafka messages persists in the storage after being read, these messages can also be tracked, read again and reprocessed if required. This functionality is not possible with a traditional message queue.
  • In Kafka, the messages published by the producers are posted to a topic and the subscriber subscribes to the topic and reads the message. Therefore, there isn't a queue, which is used in the traditional message queues.
  • The topics in Kafka contain multiple partitions; therefore, this allows parallel processing and high throughput. These concepts will be detailed in the following chapters. The traditional message queues do not provide the same.
  • Kafka replicates the messages in different brokers and multiple servers; therefore, the availability of the data is high and it has a good way to recover failed data. The traditional messaging does not always provide message replication.
  • Load balancing is provided within the architecture of Kafka, whereas it has to be externally configured for the other message queues.

Therefore, from the preceding comparisons, we can understand that there are many benefits in using Kafka over the traditional queues. Due to these factors, it is been widely used in various applications.

Kafka architecture: producer, consumer, and broker

The figure 1.2 shows the architecture of Kafka. The Kafka architecture consists of the Kafka Cluster. The cluster contains multiple nodes. Brokers run with the cluster. Multiple brokers together constitute a Kafka cluster.

On a very high level, as shown in the following figure, the producers send messages to the cluster and the consumers consume these messages. The messages are also interchangeably known as records.

The Zookeeper is a used to manage the services of a Kafka cluster. It takes care of identifying the statuses of the brokers, which are present within the cluster. It notifies the nodes whenever a new broker has been added or if a broker is not active anymore. Any change is communicated to all the nodes through the Zookeeper.

Figure 1.2: Architecture of Kafka

The Zookeeper maintains the quota of the data for the producers and the consumers. The Zookeeper tracks the replicas for the topics, if a node fails, then the Zookeeper uses the other replica node. Thus, it contains information about which nodes store the different topics.

For the consumers, Zookeeper keeps track of the offset value, which is the value used by the consumer while reading from the partition.

Kafka architecture: topics and partitions

Each broker contains Kafka topics. Topics are the interface to which Kafka producers write. The consumer may subscribe to a topic and read from it. Many consumers may subscribe to a single topic. Similarly, a consumer may subscribe to multiple Topics.

Each Kafka topic is divided into multiple partitions. The content of the partition, that is, the record will be replicated in multiple nodes in the clusters. This creates high availability of the records as well as helps to recover the record in the event of failure or loss of record.

Each partition has an ordered sequence and is immutable. The data is stored in these partitions in the form of a log. This log is structured and ordered. The records that are present in the log contain sequence numbers, which are used as an offset by different consumers.

One of the partitions is appointed as the leader. Whenever a topic receives a message, the writing and reading of the record takes place via the leader. The leader replicates the content and updates the replicas whenever there is a change in the record. If the leader partition fails for some reason, the replica is assigned as the leader.

Figure 1.3: Topics and Partitions

Since many consumers read from a topic, each consumer tracks the reading process using an offset value. In the following example, in figure 1.4, consumer 1's offset is 3 and consumer 2's offset is 6:

Figure 1.4: Offset Operation

Therefore whenever the read operation takes place for consumer 1 the offset value 3 is used and the subsequent record 4 is read. Similarly when the consumer 2 reads from the partition the offset value 6 is referred and the next records, that is, 7 are read.

Core API of Kafka

Kafka has the following core API to support its key functions. As shown in the following figure 1.5, The Kafka Cluster uses these APIs to communicate with its producers and consumers:

Figure 1.5: Kafka APIs

  • Producer API: This API is used to publish records to a topic.
  • Consumer API: Using the consumer API, consumers can subscribe to multiple topics and they process the records written to these topics.
  • Streams API: This API reads streams of records from the input stream and sends to the output stream.
  • Connector API: This API is used to connect to data systems such as relational database to the Kafka topics. Once the API is defined, the change in the tables will be posted to the topics.
  • AdminClient API: This API is used to support the management of the broker and topics.

Therefore, the preceding APIs are the core to Kafka messaging, and in the later chapters, we will see how they are used for messaging.

Advantages of using Kafka

The following are some of the advantages of using Kafka streaming framework:

  • Highly scalable: Kafka can be used with large volumes of data. It scales very easily to process the records because of its architecture.
  • Fault tolerant: Since the records in Kafka is replicated in different nodes and servers, it can tolerate failures
  • Less downtime: The downtime of retrieving data from Kafka is very less. records can be read very fast
  • Reliability: Due to its distributed storage nature with the partition architecture, fault tolerant feature, it is known to be highly reliable
  • High throughput: The performance of Kafka is extremely good. Even with large quantities of data it achieves high throughput.

The aforementioned advantages of Kafka are leveraged by many applications that make use of it. Some of the application will be discussed in the next section.

Applications using Kafka

Some of the applications of Kafka are as follows:

  • Twitter: The tweets in Twitter used Kafka. Tweets are sent and received using it. The infrastructure used is Storm-Kafka.
  • LinkedIn: The activities in the LinkedIn platform use Kafka.
  • Netflix: Provides on-demand internet streaming of media content; it uses Kafka for event processing.

Generally, Kafka is used in the following scenarios:

  • Website tracking: Tracking of the pages, views or searches, which the user performs on a website can be stored in Kafka. Each activity can be published to a topic.
  • Log aggregation: Logs being written by various applications can be stored in Kafka to be processed and the information extracted from it can be given to the different subscribers.
  • Stream processing: Kafka has high-durability capability; hence, it is preferred over the other streaming applications.
  • Messaging: Since it is publish-subscribe system, it can replace the traditional message queues. Its throughput and fault tolerant nature makes it a more suitable choice.

These applications are the most widely used use cases of the Kafka Messaging architecture. Knowing the above applications will be helpful to understand how to make use Kafka for our own applications and use cases.

Components in messaging

There are several components in the Kafka messaging system. These include Kafka brokers and partitions. They form the core of the messaging architecture. In the following section, we will learn the functioning of these components and their importance toward the messaging system.

Kafka brokers and Kafka partitions

The following figure shows some of the important components of Kafka messaging. There are several brokers in the architecture. Each broker has multiple partitions (for example, P1, P2, etc.). When the producer generates messages for a particular topic, the content is stored in these partitions. Within a broker, there will be a leader partition and the other partitions store the messages belonging to the topic. When a leader fails, another partition takes over as a leader.

The producers will always write to a leader partition. The leader then decides where the data is to be stored and replicated. The data can be stored in a partition within the same broker or different broker. The leader decides the location of the replicas and therefore performs a kind of load balancing of the messages received from producers:

Figure 3.1: Brokers and partitions

As shown in the preceding figure, the brokers work collectively to receive the messages sent to a topic by the producers. The leader partition plays an important role in routing these messages to all the other partitions.

Kafka failover

The leader or the replica partition can fail. The following are the possibilities of failure:

  • Only the leader fails: In this scenario, the Kafka controller will choose another leader from the pool of partitions. There will be a downtime in processing the messages received after the failure as the LeaderNotAvailable exception will be thrown. But once the leader is chosen, the messages will continue to be processed again. There will not be a loss in data.
  • One replica fails: In this scenario, the replica will stop storing the messages and will be out of sync with the leader and its other replicas. Although once the replica partition is fixed and is active, the replica will be synced with the other replicas and the leader. When the replica is down, the consumers will fetch the latest data from the other replicas.
  • More than one replica fails: In this scenario, the replicas that have failed will discontinue to receive any data from the producer. The leader still contains a copy of the data, and therefore, the consumer can fetch from the leader. Once all the replicas are active again, they will be synced with all the data that was lost.
  • All replica fails (along with leader): When all the replicas, including the leader fail, the leader could be fixed and made active to restart its messaging receiving process. The leader will contain all the data it received until it went down. After becoming active, it will continue to receive latest messages. Another alternative is to elect another leader from another broker, but the messages received by the old leader will be lost. The new leader will start receiving the new data.

The preceding scenarios are the common failovers that can occur in the Kafka messaging system.

Kafka consumer

Kafka consumer is the client that reads records from the Kafka cluster. The consumer reads from topics using offset values. A consumer can subscribe to multiple topics. As set of consumers reading from similar topics are grouped together, these are called consumer groups.

Consumer groups

A topic in Kafka is written to multiple logs called partitions. The producers write to these logs at the end of each partition, while the consumer can consume from these logs at their own speed. The messages are read in a sequential manner from these partitions.

The reason behind distributing the read from different partition is to scale consumption of the data by the consumers. In the figure 5.1, Topic A is stored in three partitions. The topic has two consumers, Consumer 1 and Consumer 2. They constitute a consumer group. Each partition is assigned to a consumer for reading.

Each consumer in a consumer group will get an exclusive fair share of partitions. Within a consumer group, there will not be more than one consumer reading from a partition. Each group gets to read a partition via one of its consumers. This is the manner in which load balancing is performing for the consumer groups.

If the number of partitions is less than the number of consumer groups, then some of the consumer groups will remain idle and will be used during a failover. If there are more partitions than the consumer groups, few consumer groups may read from more than one partition.

Group coordination protocol

When a consumer group is created, the consumers within the groups needs to be managed. The group coordination protocol is used to manage the consumers. Each group has a designated broker, which is assigned as a group coordinator. This coordinator is responsible for managing the state of the group. The responsibilities of the coordinator are as follows:

  • Assigning log partitions to consumers for reading
  • If a new consumer is added then allocation of a partition to it.
  • When an existing consumer leaves, managing the state of the group.
  • If a topic changes, assigning the partitions accordingly.

When the read operation occurs, it is sequential within a partition. After reading few records the consumer may commit the already read records.

The figure 5.2 shows a typical partition log with positions. In the figure 5.2 the Last Committed Offset is the location until which the records read has been committed by the consumer. The consumer then continues to read up to position 4, which is its current reading point.

At this stage, failure happens and the consumer is replaced by a new consumer, the new consumer needs to read from offset 2, which is the previously saved record. The in-between read of records at positions 2 and 4 will need to be read again.

The records are also copied to other partitions as part of the replication process for high availability of the data. Therefore, the position of the records that are already saved to other log partitions is the high watermark point. The consumers can read until this point safely, beyond which if the consumer reads, there is a possibility that if the records are lost, then there is no replica of it elsewhere:

Therefore, using this protocol, the consumers are able to coordinate and access the data with high availability.

Core components of Storm

The following are the components of Storm cluster:

  • Nodes: A storm cluster contains two types of nodes, master node and worker nodes.
  • Nimbus: The Nimbus node is the master in a Storm cluster. The nimbus daemon's primary responsibility is to manage, coordinate, and monitor topologies running on a cluster, including topology deployment, task assignment, and task reassignment in the event of a failure. Nimbus is stateless and stores all of its data in Zookeeper.
  • Supervisor: This is the daemon run by the worker nodes. This performs that task assigned to it by the master node. A supervisor can have more than one worker nodes. The supervisor allocates the tasks to the worker nodes and can have as many resources it needs to successfully complete the tasks. It is responsible for creating, starting, and stopping worker processes to execute the tasks assigned to that node. Like Nimbus, a supervisor daemon is also fail-fast and stores all of its state in Zookeeper so that it can be restarted without any state loss.
  • Stream: The stream of data flowing into the topology from the data source contains tuples. Tuple is the component of the storm cluster. This tuple contains a list of data elements sent by the data source into the spout. They are the main data structures in Storm. They are named lists of varied values such as integers, bytes, floots, and byte arrays.
  • Spouts: The input stream from the data source is sent to the Spout. It reads the data continuously and creates tuples before sending it to a bolt. It can read from a Kafka message queue or database or a file systems, for example.
  • Bolts: Bolts are at the heart of all the logic processing in Storm; the data from the spout is sent to the bolt for processing. These bolts can perform computations on the data. The bolt can send the data to another bolt for further processing or store the output in the database.
  • Task: A task means processing the data in some form in the storm cluster. It can be a spout or a bolt. Even though the number of components and their tasks remain the same in a topology, the executors of these tasks can be changed. The executors may increase or decrease depending upon the input load given to the bolt to process. By default, Storm will run one task in one thread.
  • Topologies: A storm topology contains the components of storm, which are the spout and bolts. It is a network formed by several spouts and bolts. Every component will process the data and send its output to the connect components; therefore, it is an interconnected network of spouts and bolts organized to meet a goal.
  • Zookeeper: The storm cluster states are maintained by the Zookeeper. The daemons are stateless in storm. When there is a failure in the master or slave nodes, they will be restarted.

Introduction to Apache Spark

Apache Spark is open source software. It processes data in real time. It performs computation in a distributed manner, and therefore is scalable and fault tolerant. Spark contains many features for distributed computation. It can be used with programming languages such as Scala, Python, R, Java, and SQL. It provides machine learning libraries for implementations of ML pipelines.

The architecture of spark is master and slave architecture consisting of the master daemon and the worker daemon. In the following sections, we will learn the core concepts and the architecture of Spark.

Comparison of Spark and Hadoop

Apache Spark performs hundred times faster computations in memory. Hadoop performs computations, but it is much slower using the map/reduce framework. Spark contains all the management components within the same cluster. Hadoop contains various components to be managed different to execute its pipeline.

Spark can process real-time computations, whereas Hadoop can process data in batches only. Spark purpose is to improve the capabilities of the Hadoop stack. Therefore, its enhanced processing power capabilities integrate well with the Hadoop ecosystem.

Comparison of Spark and Storm

Apache Spark and Storm are similar in their applications and they differ in certain key aspects. Apache Spark is processes data in batches whereas Storm processes data in micro-batch processing manner. Spark has a latency of seconds and Storm has latency of milliseconds. Spark has lesser language support such as Java and Scala, whereas Storm has multiple language support such as Java, Clojure, and Scala.

Storm can process streams of data through spouts and Spark can process data in HDFS, HBase, Cassandra, Hive, and any Hadoop InputFormat. Storm uses Tuple and partitions, whereas Spark can process data in HDFS, HBase, Cassandra, Hive, and any Hadoop InputFormat.

Comparison of Spark and Kafka

Apache Spark has real time and batch processing, whereas Kafka has only real-time processing. Spark is supported by many easy-to-learn documentation and Kafka is very easy to configure. The recovery mechanism in Spark uses Cache and RDD. Kafka's recovery mechanism uses a replication approach.

Using Spark, we can perform ETL operations as we can persist the data in the form of objects. Kafka only supports real-time processing so that it can be used as message broker and it can retain the messages for a short period of time only. Spark's processing speed is much higher. Kafka also processes the data fast, but Spark's processing is 100 times faster than Hadoop.

  • Spark streaming: Spark streaming makes it easy to build scalable fault-tolerant streaming applications. The Spark streaming supports both batch and real-time streaming. Spark architecture

Apache Spark has a well-defined architecture. It is layered in nature and the components are loosely coupled. It also consists of various libraries to support its features. Apache Spark's architecture contains two main components. They are:

  • Resilient Distributed Dataset (RDD): The definition of RDD is R-Resilient, D-Distributed, and D-Datasets. It contains data that can be split into partitions. This data can be stored within the memory of the worker nodes, which are present in the Spark cluster.

    The two types of RDD's supported by Spark are:

    • Datasets from Hadoop that are in the form of files stored on HDFS
    • Existing data from Scala Collections that are parallelized

    RDDs are immutable. This is the fundamental element that is operated on multiple systems to enable parallel processing. The logical portion of the data in the RDD are distributed to other nodes for execution.

  • Directed Acyclic Graph (DAG): DAG are supported by spark. It supports stage-oriented scheduling. The traditional Map Reduce contains the Map and the Reduce stage, whereas the Spark can contain many stages that are defined through a DAG.

    It performs a sequence of transformation, each node is an RDD partition and the transformation is executed in the edge. The edge transformation transforms the data from one state to another. Since it is acyclic, the transformed data state has to proceed to the next partition as defined by the DAG nodes.

The following figure shows the architecture and the workflow of Spark applications:

Figure 9.2: Spark architecture

Apache Spark is a master-slave architecture. The two daemons are the master daemon and the worker daemon. This is managed by a cluster manager. The cluster manager starts the executors and the drivers of the cluster.

A Spark cluster many have a master node and multiple worker nodes. The Spark driver shown in the figure 9.2, is the entry point to the cluster; it contains the main() function. The Spark Context is created here. The SparkContext consists of all the functionalities that the cluster needs. The driver has scheduling components such as DAG scheduler, backend scheduler, task scheduler, and block manager. They will be used to convert the code written by the users into jobs that are executed on the cluster.

The Driver program and the context will be overseeing the tasks running on the cluster along with the Cluster manager, which performs resource allocation to the jobs. A job can be further split into multiple sub-tasks, which are assigned to different worker nodes.

The worker node executes its tasks and returns the result to the SparkContext. The data in the RDD can be saved in the cache of each worker node. The executors in each worker node is responsible of executing the job and providing its results to SparkContext. The executors are started when the application is initiated and it continues to run in the background as long as the application is active.

Kafka and Spark integration

Apache Kafka can be integrated with Spark streaming where the Spark streaming receives the data from Kafka. There are two approaches in which the integration can be performed:

  • Receiver-based approach
  • Direct approach

As shown in the following diagram, the Kafka Stream can send the data to the Spark streaming component. The Spark engine can perform any computation that is needed on the data. The processed data will be stored in the database:

Figure 11.1: Kafka and Spark integration

There is also a structured streaming integration with Kafka, where the data is read from Kafka streams and processed by Spark Engine and written back to Kafka as shown in the following diagram:

Figure 11.2: Structured Streaming Kafka and Spark integration

Kafka provides libraries and API to support the integration of the Spark engine with its input and output stream.

Approaches for integration

In this section, we will understand the two approaches, that is, the receiver-based approach and Direct approach;

  • Receiver-based approach: This is the initial approach where the receivers are used and implemented using Kafka API. The data is passed to the Spark Engine and the spark streaming processes the data. Data loss can happen on the receivers' side; we can avoid that by enabling Write ahead logs in Spark Streaming, which stores all the data received in HDFS. During a failure, the data from HDFS is used for recovery.
  • Direct approach: This is the new approach where we do not use receivers. The Spark Engine periodically queries Kafka for the data using the offsets for the topic. This approach provides simplified parallelism; multiple input Kafka Streams are not required as each Kafka partition will have a corresponding Spark RDD and the data is read in parallel. The previous approach required data to be stored in twice for providing reliability. Here, saving twice is not required as it can be read from Kafka partition in case of failure. The retention policy for Kafka can be set accordingly.
