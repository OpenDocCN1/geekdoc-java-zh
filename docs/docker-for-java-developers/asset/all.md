Docker for Java Developers

# Introduction

## 1\. Introduction

If you have not heard about [Docker](https://www.docker.com/), then you have probably spent the last few years on some other planet of the Solar system. [Docker](https://www.docker.com/) stormed into our industry and in no time dramatically changed many well-established software development and operational practices and patterns. These days pretty much every organization is using [Docker](https://www.docker.com/) (or equivalent of it), the brave ones even in production, and its adoption is growing at fantastic pace.

In this tutorial we are going to talk about how [Docker](https://www.docker.com/) can help us, [Java](https://www.java.com/en/) developers, in accomplishing our day to day tasks. The tutorial consists of several parts where we going to touch upon different aspects of [Docker](https://www.docker.com/) and its applicability to [Java](https://www.java.com/en/) applications development.

We will start off by learning the basics:

*   Why we should invest our time in learning [Docker](https://www.docker.com/)
*   Get to know [Docker](https://www.docker.com/) command line tooling
*   Using REST façade to talk to [Docker](https://www.docker.com/)

Then we will move on to the topics related specifically to [Docker](https://www.docker.com/) in context of [Java](https://www.java.com/en/) applications right after:

*   Building
*   Developing
*   Testing
*   Deploying
*   Continuous Integration / Delivery

The material we will be going through assumes that you have some basic familiarity with [Docker](https://www.docker.com/) and have at least version **17.06.1-ce** already [installed](https://docs.docker.com/engine/installation/) on the machine (it does not really matter if you are on Linux, Windows or Mac per se).

## 2\. Linux Containers: The Big Bang

The story, which made [Docker](https://www.docker.com/) and friends possible, begins back in 2006, when a couple of awesome engineers at [Google](https://en.wikipedia.org/wiki/Google) started the work on the feature under the name “process containers”.  It was later rebranded to “control groups” (or [cgroups](https://en.wikipedia.org/wiki/Cgroups) as we know them today) and was merged into the Linux kernel starting from version **2.6.24**, released in January 2008.

Essentially, [cgroups](https://en.wikipedia.org/wiki/Cgroups) is a [Linux kernel](https://en.wikipedia.org/wiki/Linux_kernel) feature that limits, accounts for, prioritizes and isolates the [resource usage](https://en.wikipedia.org/wiki/Resource_%28computer_science%29) (CPU, memory, disk I/O, network, etc.) of [processes](https://en.wikipedia.org/wiki/Process_%28computing%29). Most importantly, to support all that the [Linux kernel](https://en.wikipedia.org/wiki/Linux_kernel) does not need to start any [virtual machines](https://en.wikipedia.org/wiki/Virtual_machine) or [hypervisors](https://en.wikipedia.org/wiki/Hypervisor). Along with [namespaces](https://en.wikipedia.org/wiki/Linux_namespaces), another very powerful feature of the [Linux kernel](https://en.wikipedia.org/wiki/Linux_kernel), [cgroups](https://en.wikipedia.org/wiki/Cgroups) serve as a fundamental building block for [containers](https://en.wikipedia.org/wiki/Operating-system-level_virtualization): operating system-level virtualization.

Container-based virtualization is exceptionally lightweight (comparing to traditional [virtual machines](https://en.wikipedia.org/wiki/Virtual_machine)), imposes little to no overhead, share the same operating system kernel and do not require special hardware support to perform efficiently. To say it in other words, containers become a new model to wrap the applications so they could be run in isolation on a shared operating system. Although not without the limitations, going with containers becomes a mainstream in the virtualization space nowadays.

To be fair, not all Linux/Unix distributions use the same mechanisms for operating system-level virtualization. To mention a couple of examples, [FreeBSD](https://www.freebsd.org/) has [jails](https://en.wikipedia.org/wiki/FreeBSD_jail) for such purposes while [Solaris](https://en.wikipedia.org/wiki/Solaris_(operating_system)) has the concept of [zones](https://en.wikipedia.org/wiki/Solaris_Containers).

So, how to get started with containers? Well, you may have heard abbreviations like [LXC](https://linuxcontainers.org/lxc/introduction/) or [LXD](https://linuxcontainers.org/lxd/introduction/) which are essentially the entry points for containers management on most of the Linux/Unix distributions. The thing is, those are somewhat low-level and not easy to start with. But luckily we have [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) and [rkt](https://coreos.com/rkt), the application-centric container management engines, which right from the inception became the de facto choices for the application developers across the globe.

## 3\. Docker: Containers for Masses

So what is [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) essentially? It started off as a powerful and easy to use container engine but these days it would be fair to call it a full-fledged container management platform. It is written in [Go](https://golang.org/) and takes advantage of the Linux kernel features (mostly [namespaces](https://en.wikipedia.org/wiki/Linux_namespaces) and [cgroups](https://en.wikipedia.org/wiki/Cgroups)) to do the job. The community edition is downloadable free of charge whereas the enterprise edition is also available through subscription offerings. To settle the stage, along this tutorial we are going to use the features of the community edition only.

### 3.1\. Architecture

From the architectural perspective, [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) consists of three main parts. In the heart of [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) sits the daemon process, [dockerd](https://docs.docker.com/engine/reference/commandline/dockerd/). In turn, [dockerd](https://docs.docker.com/engine/reference/commandline/dockerd/) relies on another daemon, [containerd](https://containerd.io/), as the abstraction layer to interface with the Linux kernel [namespaces](https://en.wikipedia.org/wiki/Linux_namespaces) and [cgroups](https://en.wikipedia.org/wiki/Cgroups). The last piece of the puzzle is a set of command line tools (like for example [docker](https://docs.docker.com/engine/reference/commandline/docker/) and [docker-compose](https://docs.docker.com/compose/reference/overview/)), known as Docker CLI, which are able to talk to [dockerd](https://docs.docker.com/engine/reference/commandline/dockerd/) daemon though the [Docker Engine API](https://docs.docker.com/engine/api/) it exposes.

Each of the [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) components mentioned above deserves own tutorial, so many interesting features and capabilities they provide, though our focus would be primarily centered on [Docker Engine API](https://docs.docker.com/engine/api/) and the Docker CLI family ([docker](https://docs.docker.com/engine/reference/commandline/docker/) and [docker-compose](https://docs.docker.com/compose/reference/overview/)).

One of the strongest arguments in favor of choosing [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) is that it runs natively on the majority of the Linux distributions but it does not stop there. [macOS](https://www.docker.com/docker-mac) and [Windows](https://www.docker.com/docker-windows) operating systems are also supported pretty well, with a [few caveats](https://docs.docker.com/toolbox/overview/) to be aware of.

In order to understand how [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) works, we have to unveil a bit its internal model. At any time, if you feel like there are not enough details uncovered about the subject, please do not hesitate to consult the [official documentation](https://docs.docker.com/).

### 3.2\. Images

In [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29), everything you do is managing the specific objects. Images and containers are arguably the most important ones however there are others like volumes, networks and plugins, to name a few. All of them we are going to see in action in different sections of the tutorial, starting with images and containers right away.

Image could be treated as a set of instructions on how to create the container. In [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29), one image could be inherited (or based on) from another image, adding additional instructions on top of base ones. Each image consists of multiple layers, which are effectively immutable. Under the hood these layers are backed by dedicated file systems (by default [UnionFS](https://en.wikipedia.org/wiki/UnionFS), but others could be plugged in as well), making them very lightweight and fast.

So … how could you create such images for your own needs? It is actually pretty simple, to build your own image in [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) you create a [Dockerfile](https://docs.docker.com/engine/reference/builder/) which is just a text document that defines the set of steps (or instructions) required to assemble the image (and run it later). Along the way you may decide to [create  completely customized images](https://docs.docker.com/engine/userguide/eng-image/baseimages/) yourself or, in most cases, reference the images created by others, which are published in a [registry](#Introduction.xhtml__Registries). To give you a sneak peek on how the [Dockerfile](https://docs.docker.com/engine/reference/builder/)s may look like, here is a quick example:

| `1` | `FROM alpine:3.6` |

| `2` | `CMD [``"uname"``,` `"-a"``]` |

Each instruction in a [Dockerfile](https://docs.docker.com/engine/reference/builder/) creates a new layer so at the end each image has a list of immutable layers, stacked on top of each other, that represent the filesystem differences.

In the upcoming sections we will be writing quite a lot of different [Dockerfile](https://docs.docker.com/engine/reference/builder/)s, closely following the [best practices and recommendations](https://docs.docker.com/engine/userguide/eng-image/dockerfile_best-practices/).

### 3.3\. Containers

When you have your images ready, it is time to bring them to live. Here is where the containers appear on the stage: they are runnable instances of the images. You can run as many of them as your want, assuming the target host (where [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) is installed) has enough resources. All of that is feasible because the containers are well isolated from each other, at least by default (however you have quite a lot of options to control that).

When [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) creates an instance of the **container,** it also **adds a new writable layer** on top of the underlying stack of image layers, often called the **container layer**. All the changes which are made to the running container (such as creating, deleting or modifying files for example) are written to this thin layer.

It is important to think about containers as ephemeral: when a container is terminated (stopped and removed), any changes to its state disappear (unless they are stored in persistent storage).

As of now, [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) internally uses its own image format and heavily relies on [libcontainer](https://github.com/opencontainers/runc/tree/master/libcontainer) and [runc](https://github.com/opencontainers/runc) for spawning and running the containers.

### 3.4\. Registries

The purpose of the registries in [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) architecture is to store images so they could be shared and used as the base ones. [Docker Hub](https://hub.docker.com/) and [Docker Cloud](https://cloud.docker.com/) are the well-known public registries that anyone can use. To keep things simple, [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) is configured to look for images on [Docker Hub](https://hub.docker.com/) by default.

You may also consider the option to host your own private [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) registry (or registries). There are a lot of good reasons to do that, particularly in the world of enterprises. One of the most crucial ones is security as the public images do not undergo through comprehensive security audit and may have known [security vulnerabilities or exposures](http://dl.acm.org/citation.cfm?id=3029832). However, the things are getting better as more and more companies maintain so called [official repositories](https://docs.docker.com/docker-hub/official_repos/), which are curated and adhere to higher standards.

To make things even more intriguing, the new player has joined the game of registries recently. The flagship [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) product, [Docker Store](https://docs.docker.com/docker-store/), has been announced to become generally available.

### 3.5\. Image is the new RPM

With the [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) and other container engines becoming more and more popular and widespread, the way we used to package and distribute the application is also changing dramatically. Literally, the image becomes a “new RPM” in a sense that you could distribute it to any platform where the container engine of your choice is supported (more on that later) and just run it as a container. It is indeed easy, simple and powerful.

## 4\. Moby: The Future of Docker

[Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) has been seeing a lot of changes recently. Driven by initiatives to break [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) into modular components and consolidate all of its open source collaborations, the [Moby Project](https://mobyproject.org/) was born.

> *The Moby Project is a new open-source project to advance the software containerization movement and help the ecosystem take containers mainstream. It provides a library of components, a framework for assembling them into custom container-based systems and a place for all container enthusiasts to experiment and exchange ideas. –* [*https://blog.docker.com/2017/04/introducing-the-moby-project/*](https://blog.docker.com/2017/04/introducing-the-moby-project/)

As [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) continues to be split up into more components, the [Moby Project](https://mobyproject.org/) will become the home for those components as well, so let us keep an eye on it and look forward to exciting announcements.

## 5\. Towards Interoperability

With multiple application-centric container engines available at the moment, namely [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) and [rkt](https://coreos.com/rkt) (and very likely more to appear in the future), the obvious question to ask would be: how to pick one? And what happens if you would have to switch to another one along the way?

Indeed, at the moment if you select one container engine over the other, you would probably have to stick to it as the move to alternative may be proven difficult. But there is a hope, thanks to [Open Container Initiative](https://www.opencontainers.org/) (or just [OCI](https://www.opencontainers.org/)), that container engines interoperability would improve significantly, with enough players supporting the common specifications.

We have [mentioned earlier](#Introduction.xhtml__Containers) that at the moment [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) uses own image format. To our luck, the important milestone towards openness in this space has been achieved recently with the first release of [OCI Runtime and Image specifications](https://blog.docker.com/2017/07/oci-release-of-v1-0-runtime-and-image-format-specifications/).

## 6\. Docker and Java

There have been a lot of discussions lately regarding any legal consequences or licensing considerations while using [Java](https://www.java.com/en/) inside the containers. The official [Oracle](https://www.oracle.com/index.html) position on the matter is nicely summarized in the Q&A section:

> ***Are there any licensing considerations for Oracle Java SE that are unique to Docker?***
> 
> * No.  Docker is a containerization platform and there are no unique or special restrictions in the license for use or redistribution as compared to any operating system, virtualization or packaging format. The Oracle JDK is widely used and adopted in the Docker ecosystem. –* [*https://blogs.oracle.com/developers/official-docker-image-for-oracle-java-and-the-openjdk-roadmap-for-containers*](https://blogs.oracle.com/developers/official-docker-image-for-oracle-java-and-the-openjdk-roadmap-for-containers)

Although the answer is referring to [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) only, it is equally applicable to other container-based virtualization engines as well.

To prove the point, [Oracle](https://www.oracle.com/index.html) has published the official [Oracle Java 8 SE (Server JRE)](https://store.docker.com/images/oracle-serverjre-8) image into the [Docker Store](https://store.docker.com/), one of the places to find the trusted commercial and free software distributed as [Docker](https://en.wikipedia.org/wiki/Docker_%28software%29) Images.

In this introductory section of the tutorial we have looked a bit into evolution of virtualization mechanisms in the Linux/Unix operating systems. We have learned at the high level what are images, containers, their benefits comparing to traditional [virtual machines](https://en.wikipedia.org/wiki/Virtual_machine) and how we could get started using them.

# Docker over command line

## 1. Introduction

In this section of the tutorial we are going to master the Swiss army knife of [Docker](https://www.docker.com/), its command line tool of the same name [docker](https://docs.docker.com/engine/reference/commandline/cli/) and its best friend [docker-compose](https://docs.docker.com/compose/reference/overview/). To give these tools some credit, each of them supports myriads of different command line arguments and options so discussing all of them would make this section literally endless. Instead, we would be focusing on most useful classes of the commands, pointing to the relevant sections of the documentation in case you would like to learn more right away.

[Docker](https://www.docker.com/) evolves very fast and as such, [docker](https://docs.docker.com/engine/reference/commandline/cli/) and [docker-compose](https://docs.docker.com/compose/reference/overview/) are constantly changing as well, adding some new command line arguments while deprecating others. Breaking changes are not so rare but this is a reality [Docker](https://www.docker.com/) users are facing for quite a while now.

One of the largest changes which came into effect recently concerned exactly the command line tooling. In the past, the [docker](https://docs.docker.com/engine/reference/commandline/cli/) used to accept a single command as the first argument followed by list of options. However, the amount of different commands grew so large, that the tool became really confusing and cumbersome to use. It was decided to split the commands into classes (for example **image**, **container**, **network**, **volume**, **plugin**, **system**, …) so the every command will be preceded by its class (for example, **docker build** becomes **docker image build**). It was a really needed change and although the old-style usage of the commands is still supported, we would adhere to the recommended practices in the tutorial.

The section is structured in such a way so to familiarize you with the most useful commands while not really digging into the details and usage scenarios. The rationale behind is quite simple though, in the next sections of the tutorial we are going to battle-test most (if not all) of them while doing really practical things.

## 2\. Images

It looks logical to start from the bottom and get acquainted with [docker](https://docs.docker.com/engine/reference/commandline/cli/) by learning how to build images. In the first section of the tutorial we have briefly walked through the process but it is time to do it ourselves using [build](https://docs.docker.com/engine/reference/commandline/image_build/) command.

| `1` | `docker image build [OPTIONS] PATH &#124; URL &#124; -` |

As we remember, [docker](https://docs.docker.com/engine/reference/commandline/cli/) builds images from the [Dockerfile](https://docs.docker.com/engine/reference/builder/)s, executing each instruction in the order it is specified. The PATH or URL options are the hints where to look for the [Dockerfile](https://docs.docker.com/engine/reference/builder/).

Building small and efficient images, and doing so fast, is one of the key goals to aim for in order to be successful with [Docker](https://www.docker.com/). Image caching, labeling, tagging, reducing the final size of the image and many other topics are nicely summarized in the [best practices for writing Dockerfiles](https://docs.docker.com/engine/userguide/eng-image/dockerfile_best-practices/), it is highly recommended to go over this read.

You may rarely find the need to build your own base images so let us talk instead what would be our choices in order to pick the base image for Java applications.

As of now, objectively, the [Alpine Linux](https://alpinelinux.org/) is the de facto base Linux distribution for the containerized applications. If you happen to run your applications on [OpenJDK](https://en.wikipedia.org/wiki/OpenJDK), you are really lucky as the project’s [official DockerHub repository](https://hub.docker.com/_/openjdk/) provides plenty of the images based on [Alpine Linux](https://alpinelinux.org/). Quickly, here is a simplest [Dockerfile](https://docs.docker.com/engine/reference/builder/) example:

| `1` | `FROM openjdk:8u131-jdk-alpine` |

| `2` | `CMD [``"java"``,` `"-version"``]` |

Assuming your shell is pointing to the same folder where this [Dockerfile](https://docs.docker.com/engine/reference/builder/) resides, you can build (and also tag) the image with this command:

| `1` | `docker image build . --tag base:openjdk-131-jdk` |

In case you bet on [Oracle JVM](http://www.oracle.com/technetwork/java/javase/downloads/index.html) distributions, sadly the [Alpine Linux](https://alpinelinux.org/) is not officially supported yet (although you may see that some people are trying to marry those two together, please be aware that it kind of feasible but the JVM process in the container could crash any time). The options here are either to use [official Oracle Java 8 SE (Server JRE) image](https://store.docker.com/images/oracle-serverjre-8) or build your own based on [Ubuntu](https://hub.docker.com/_/ubuntu/) or [Debian](https://hub.docker.com/_/debian/) distributions.

In terms of which JVM version to build upon, please make sure to use at least **Java 8 update 131** or later, for the reasons we will discuss in details in the upcoming sections (but if you are curious, here is the [sneak peek behind the curtain](https://blogs.oracle.com/java-platform-group/java-se-support-for-docker-cpu-and-memory-limits)).

Along with [build](https://docs.docker.com/engine/reference/commandline/build/), there is a couple of very useful commands which are worth mentioning. The [ls](https://docs.docker.com/engine/reference/commandline/image_ls/) command shows all the images:

| `1` | `docker image` `ls` `[OPTIONS] [REPOSITORY[:TAG]]` |

The [history](https://docs.docker.com/engine/reference/commandline/image_history/) command shows the history of an image:

| `1` | `docker image` `history` `[OPTIONS] IMAGE` |

While the [rm](https://docs.docker.com/engine/reference/commandline/image_rm/) command removes one or more images:

| `1` | `docker image` `rm` `[OPTIONS] IMAGE [IMAGE...]` |

To interface with registries, there are [pull](https://docs.docker.com/engine/reference/commandline/image_pull/) and [push](https://docs.docker.com/engine/reference/commandline/image_push/) commands. The first one fetches the image from a registry while the latter uploads it to the registry.

| `1` | `docker image pull [OPTIONS] NAME[:TAG&#124;@DIGEST]` |

| `2` | `docker image push [OPTIONS] NAME[:TAG]` |

Lastly, the exceptionally useful [prune](https://docs.docker.com/engine/reference/commandline/image_prune/) command removes all unused images (which you have better to use with **-a** option all the time):

| `1` | `docker image prune [OPTIONS]` |

One of the tremendously useful features introduced by [Docker](https://www.docker.com/) in the recent release is the support of [multi-stage builds](https://docs.docker.com/engine/userguide/eng-image/multistage-build/) which allows to have multiple FROM statements in the [Dockerfile](https://docs.docker.com/engine/reference/builder/). We would just mention that here but it will come back to us in the upcoming sections of the tutorial.

## 3\. Containers

Container management constitutes a large portion of the [Docker](https://www.docker.com/) functionally and there are a lot of different commands to back it up. Let us start by dissecting super powerful [run](https://docs.docker.com/engine/reference/commandline/container_run/) command, which spawns a new container:

| `1` | `docker container run [OPTIONS] IMAGE [COMMAND] [ARG...]` |

To get a feeling of how easy it is, we could run the container using our [OpenJDK](https://en.wikipedia.org/wiki/OpenJDK)-based image which we have hand-built previously:

| `1` | `$ docker container run base:openjdk-131-jdk` |

| `2` |   |

| `3` | `openjdk version` `"1.8.0_131"` |

| `4` | `OpenJDK Runtime Environment (IcedTea 3.4.0) (Alpine 8.131.11-r2)` |

| `5` | `OpenJDK 64-Bit Server VM (build 25.131-b11, mixed mode)` |

Once you have the containers running, you could [attach](https://docs.docker.com/engine/reference/commandline/container_attach/) to them or use [start](https://docs.docker.com/engine/reference/commandline/container_start/) / [stop](https://docs.docker.com/engine/reference/commandline/container_stop/) / [restart](https://docs.docker.com/engine/reference/commandline/container_restart/) commands to manage their lifecycle.

| `1` | `docker container attach [OPTIONS] CONTAINER` |

| `2` | `docker container start [OPTIONS] CONTAINER [CONTAINER...]` |

| `3` | `docker container stop [OPTIONS] CONTAINER [CONTAINER...]` |

| `4` | `docker container restart [OPTIONS] CONTAINER [CONTAINER...]` |

Additionally, with [pause](https://docs.docker.com/engine/reference/commandline/container_pause/) / [unpause](https://docs.docker.com/engine/reference/commandline/container_unpause/) commands you have the control over the state of the processes within the containers.

| `1` | `docker container pause CONTAINER [CONTAINER...]` |

| `2` | `docker container unpause CONTAINER [CONTAINER...]` |

Probably, the [ls](https://docs.docker.com/engine/reference/commandline/container_ls/) command will be the most used one as it lists all running containers (and with **-a** option all containers, running and stopped):

| `1` | `docker container` `ls` `[OPTIONS]` |

Consequently, the [inspect](https://docs.docker.com/engine/reference/commandline/container_inspect/) command display detailed information about one or more containers:

| `1` | `docker container inspect [OPTIONS] CONTAINER [CONTAINER...]` |

The [stats](https://docs.docker.com/engine/reference/commandline/container_stats/) command is designated to expose runtime statistics about the container. The [top](https://docs.docker.com/engine/reference/commandline/container_top/) command shows running container processes while the [logs](https://docs.docker.com/engine/reference/commandline/container_logs/) command fetches the logs of the container.

| `1` | `docker container stats [OPTIONS] [CONTAINER...]` |

| `2` | `docker container` `top` `CONTAINER` |

| `3` | `docker container logs [OPTIONS] CONTAINER` |

Over its lifetime container could go through many modifications and diverge from its base image significantly. The [diff](https://docs.docker.com/engine/reference/commandline/container_diff/) command inspects all the changes to files or directories on a container’s filesystem and reports them.

| `1` | `docker container` `diff` `CONTAINER` |

In case you would need to capture these changes, there is a handy [commit](https://docs.docker.com/engine/reference/commandline/container_commit/) command which creates a new image from the container.

| `1` | `docker container commit [OPTIONS] CONTAINER [REPOSITORY[:TAG]]` |

Once container is not needed anymore, it could be terminated using [rm](https://docs.docker.com/engine/reference/commandline/container_rm/) command. Please be cautious as all the data stored inside the container will be gone (unless it is backed by [volumes](https://docs.docker.com/engine/admin/volumes/volumes/)).

| `1` | `docker container` `rm` `[OPTIONS] CONTAINER [CONTAINER...]` |

More extreme version of [rm](https://docs.docker.com/engine/reference/commandline/container_rm/) command, the [prune](https://docs.docker.com/engine/reference/commandline/container_prune/) command, mass-removes all stopped containers.

| `1` | `docker container prune [OPTIONS]` |

## 4\. Ports

Every container could expose ports to listen at runtime, either through image [Dockerfile](https://docs.docker.com/engine/reference/builder/) instructions or through the options of the [run](https://docs.docker.com/engine/reference/commandline/container_run/) command. The [port](https://docs.docker.com/engine/reference/commandline/container_port/) command lists all port mappings (or a specific mapping) for the container.

| `1` | `docker container port CONTAINER [PRIVATE_PORT[/PROTO]]` |

## 5\. Volumes

As we remember, containers are ephemeral and once the container is terminated, all the data it holds will be lost. It might not be a problem in many cases, but if you run the data store in a container for example, it is very likely you would prefer to keep your data.

To fill this gap [Docker](https://www.docker.com/) introduces [volumes](https://docs.docker.com/engine/admin/volumes/volumes/) as the preferred mechanism for persisting data used by containers and, obviously, [docker](https://docs.docker.com/engine/reference/commandline/cli/) has a dedicated class of commands for that ([create](https://docs.docker.com/engine/reference/commandline/volume_create/), [inspect](https://docs.docker.com/engine/reference/commandline/volume_inspect/), [ls](https://docs.docker.com/engine/reference/commandline/volume_ls/), [prune](https://docs.docker.com/engine/reference/commandline/volume_prune/) and [rm](https://docs.docker.com/engine/reference/commandline/volume_rm/)).

| `1` | `docker volume create [OPTIONS] [VOLUME]` |

| `2` | `docker volume inspect [OPTIONS] VOLUME [VOLUME...]` |

| `3` | `docker volume` `ls` `[OPTIONS]` |

| `4` | `docker volume prune [OPTIONS]` |

| `5` | `docker volume` `rm` `[OPTIONS] VOLUME [VOLUME...]` |

## 6\. Networks

[Docker](https://www.docker.com/) has pretty good [networking support](Docker%20container%20networking) for containers with a number of network drivers available out of the box. Surely, the standard set of [create](https://docs.docker.com/engine/reference/commandline/volume_create/), [inspect](https://docs.docker.com/engine/reference/commandline/volume_inspect/), [ls](https://docs.docker.com/engine/reference/commandline/volume_ls/), [prune](https://docs.docker.com/engine/reference/commandline/volume_prune/) and [rm](https://docs.docker.com/engine/reference/commandline/volume_rm/) commands is available to manage the networks.

| `1` | `docker network create [OPTIONS] NETWORK` |

| `2` | `docker network inspect [OPTIONS] NETWORK [NETWORK...]` |

| `3` | `docker network` `ls` `[OPTIONS]` |

| `4` | `docker network prune [OPTIONS]` |

| `5` | `docker network` `rm` `NETWORK [NETWORK...]` |

What distinguishes [Docker](https://www.docker.com/) networking is the fact the [dockerd](https://docs.docker.com/engine/reference/commandline/dockerd/) daemon contains an embedded DNS server which provides names resolution among containers connected to the same user-define network (so that the containers could be referenced by their names, not only IP addresses).

Any running container could be connected to the network or disconnected from the network using [connect](https://docs.docker.com/engine/reference/commandline/network_connect/) and [disconnect](https://docs.docker.com/engine/reference/commandline/network_disconnect/) commands respectively.

| `1` | `docker network connect [OPTIONS] NETWORK CONTAINER` |

| `2` | `docker network disconnect [OPTIONS] NETWORK CONTAINER` |

Aside from that, the container could be connected to a particular network by passing the options to the [run](https://docs.docker.com/engine/reference/commandline/container_run/) command. All unused networks could be removed by invoking the [prune](https://docs.docker.com/engine/reference/commandline/network_prune/) command.

| `1` | `docker network prune [OPTIONS]` |

## 7\. Linking

More often than not your application stack would be composed of many connected components rather than standalone ones (a typical example would be a Java server-side application which talks to [MySQL](https://hub.docker.com/_/mysql/) data store). Projecting that to the world of containers, you would need a group of containers which could somehow discover their upstream dependencies and communicate with each other. In [Docker](https://www.docker.com/) it used to be known as [linking](https://docs.docker.com/engine/userguide/networking/default_network/dockerlinks/) but nowadays it could be easily achieved using [user-defined networks](https://docs.docker.com/engine/userguide/networking/work-with-networks/#connect-containers) (which is also the recommended practice).

## 8\. Health Checks

Usually [Docker](https://www.docker.com/) daemon provisions the containers pretty fast however it does not mean that the applications packaged inside the containers are ready and fully functional. For many [Docker](https://www.docker.com/) users it used to be one of the most annoying issues to deal with, forcing the community to come up with many ad-hoc solutions to the problem.

But kudos to [Docker](https://www.docker.com/) team, we now have [health checks](https://docs.docker.com/engine/reference/builder/#healthcheck) (which could be specified in the [Dockerfile](https://docs.docker.com/engine/reference/builder/) or using the options of the [run](https://docs.docker.com/engine/reference/commandline/container_run/) command). It is an additional verification layer which instructs the [Docker](https://www.docker.com/) on how to test that the application inside the container is working. It resulted into adding a new **health status** property to complement the regular container status.

## 9\. Resource Limits

Interestingly, by default a container has no resource constraints and may consume all the resources of its host operating system. It could have been a show-stopper but fortunately [Docker](https://www.docker.com/) provides [a way to control](https://docs.docker.com/engine/admin/resource_constraints/) how much memory, CPU, or block I/O a particular container can use by passing a number of options to the [run](https://docs.docker.com/engine/reference/commandline/container_run/) command. Alternatively, for the running containers the [update](https://docs.docker.com/engine/reference/commandline/container_update/) command allows to adjust the container configuration (primary, resource limits) dynamically.

[view source](#DockerOverCommandLine.xhtml_viewSource "view source")[print](#DockerOverCommandLine.xhtml_printSource "print")[?](#DockerOverCommandLine.xhtml_about "?")

| `1` | `docker container update [OPTIONS] CONTAINER [CONTAINER...]` |

With respect to JVM running inside the container, the subject of the CPU and memory limits gets a bit trickier. As of **Java SE 8u131** (and surely in **JDK 9**) and later, the [JVM is Docker-aware](https://blogs.oracle.com/java-platform-group/java-se-support-for-docker-cpu-and-memory-limits) and with just a little bit of tuning is able to play nicely according to the rules.

## 10\. Clean up

As we have seen so far, there are a lot of abstractions you can manage with [Docker](https://www.docker.com/). However, with a time [Docker](https://www.docker.com/) generates a lot of garbage (like unused layers, images, containers, volumes, …), eating the precious disk space. It has been a known issue for years but since not long ago we have a dedicated [prune](https://docs.docker.com/engine/reference/commandline/system_prune/) command which cleans up all unused data:

| `1` | `docker system prune [OPTIONS]` |

Please note that by default the command will not clean up the volumes unless the **–volumes** option is specified.

## 11\. All-in-One: The Deployment Stack

As we have seen up to this point, you can accomplish any task using just [docker](https://docs.docker.com/engine/reference/commandline/cli/) command line tool. But managing lifecycle of multiple containers connected together will quickly become a burden and force you to think about automating the process, ether with bunch of shell scripts or alike.

The community has realized the problem early on and came up with a brilliant solution to that, known these days as [Docker Compose](https://docs.docker.com/compose/overview/). In a nutshell, [Docker Compose](https://docs.docker.com/compose/overview/) provides the declarative way for defining and then running multiple [Docker](https://www.docker.com/) containers, drastically simplifying the rather complex deployment of the containerized application stacks.

So how does it work? There are just a three simple steps involved, some of them we are already quite familiar with:

*   Prepare the images for your applications, usually by means of [Dockerfile](https://docs.docker.com/engine/reference/builder/)s
*   Use [docker-compose.yml](https://docs.docker.com/compose/compose-file/compose-file-v2/) specification to outline your stack in terms of containers
*   Use [docker-compose](https://docs.docker.com/compose/reference/overview/) command line tool to materialize the specification into a set of running (and usually connected) containers

Let us take a quick look on imaginable deployment stack which involves the JDK image we have created before, `base:openjdk-131-jdk`, and [MySQL](https://hub.docker.com/_/mysql/) database image `mysql:8.0.2`, all put into the [docker-compose.yml](https://docs.docker.com/compose/compose-file/compose-file-v2/) file.

| `01` | `version:` `'2.1'` |

| `02` |   |

| `03` | `services:` |

| `04` | `mysql:` |

| `05` | `image: mysql:8.0.2` |

| `06` | `environment:` |

| `07` | `- MYSQL_ROOT_PASSWORD=p$ssw0rd` |

| `08` | `- MYSQL_DATABASE=my_app_db` |

| `09` | `expose:` |

| `10` | `- 3306` |

| `11` | `networks:` |

| `12` | `- my-app-network` |

| `13` |   |

| `14` | `java-app:` |

| `15` | `image: base:openjdk-131-jdk` |

| `16` | `mem_limit: 256M` |

| `17` | `environment:` |

| `18` | `- DB=mysql:3306` |

| `19` | `ports:` |

| `20` | `- 8080` |

| `21` | `depends_on:` |

| `22` | `- mysql` |

| `23` | `networks:` |

| `24` | `- my-app-network` |

| `25` |   |

| `26` | `networks:` |

| `27` | `my-app-network:` |

| `28` | `driver: bridge` |

Pretty neat and straightforward, isn’t it? The versioning of the [docker-compose.yml](https://docs.docker.com/compose/compose-file/compose-file-v2/) specification formats needs a particular discussion. The latest and recommended specification format is `3.x`, but `2.x` which we have used in the example above [is also supported and evolves independently](https://docs.docker.com/compose/compose-file/compose-versioning/). Why is that?

The `3.x` is designed to be cross-compatible between [Docker Compose](https://docs.docker.com/compose/overview/) and [Docker Swarm](https://docs.docker.com/engine/swarm/swarm-tutorial/) (clustering solution we are going to touch upon briefly later on in the tutorial) but sadly, it also removes several very useful options (along with adding a few more). In general, we are going to stick to `3.x` whenever we can, falling back to `2.x` from time to time to showcase some really neat features.

## 12\. Conclusions

In this section we glanced over [Docker](https://www.docker.com/) awesome command line tooling, [docker](https://docs.docker.com/engine/reference/commandline/cli/) and [docker-compose](https://docs.docker.com/compose/reference/overview/), highlighting the most useful and important commands. We have not seen most of them in action yet but in the next sections of the tutorial each of them is going to find the time to appear on the stage.

# Docker over HTTP/REST

## 1\. Introduction

From the previous parts of the tutorial we already know that [Docker](https://www.docker.com/) not only has an awesome command line tooling, but exposes a feature-rich [Docker Engine API](https://docs.docker.com/engine/api/) as well. As of now, the officially supported clients are provided for Go and Python languages. Certainly, not very encouraging news for Java developer, but there is a light at the end of the tunnel.

Quite a long time ago [Spotify](https://spotify.github.io/) started its own journey to develop a Java client for the [Docker Engine API](https://docs.docker.com/engine/api/) (more widely known as [Spotify Docker Client](https://github.com/spotify/docker-client)). The project is being actively maintained ever since to follow all the recent developments in [Docker](https://www.docker.com/) / [Engine API](https://docs.docker.com/engine/api/) space and is the de-facto choice for JVM based applications nowadays. It does the job really well but has one caveat you should be aware of: because this is a community effort, not the official Java client from [Docker](https://www.docker.com/), it takes some time to catch up with all the changes introduced by frequent [Docker](https://www.docker.com/) releases.

In this section of the tutorial we will go over a few key [Docker Engine APIs](https://docs.docker.com/engine/api/) and demonstrate how those could be consumed from your Java applications using [Spotify Docker Client](https://github.com/spotify/docker-client).

## 2\. Versioning

Before getting started, we have to understand how [Docker Engine API](https://docs.docker.com/engine/api/) is [versioned](https://docs.docker.com/engine/api/v1.30/#section/Versioning) and how to match the [Docker](https://www.docker.com/) release and the version of the API it supports. The [version](https://docs.docker.com/engine/reference/commandline/version/) command of the [docker](https://docs.docker.com/engine/reference/commandline/cli/) command line tool is what we need.

| `10` |   |

| `11` | `Server:` |

| `12` | `Version:      17.06.1-ce` |

| `13` | `API version:  1.30 (minimum version 1.12)` |

## 3\. Getting Started

To begin with, we would need to introduce the respective [Spotify Docker Client](https://github.com/spotify/docker-client) dependency to our projects. In case of [Apache Maven](https://maven.apache.org/), it is fairly easy:

| `1` | `<``dependency``>` |

| `2` | `<``groupId``>com.spotify</``groupId``>` |

| `3` | `<``artifactId``>docker-client</``artifactId``>` |

| `4` | `<``version``>8.9.1</``version``>` |

| `5` | `</``dependency``>` |

As everything else in [Docker](https://www.docker.com/)‘s ecosystem, the [Engine API](https://docs.docker.com/engine/api/) evolves pretty fast so it is highly recommended to rely on the most recent [Spotify Docker Client](https://github.com/spotify/docker-client) release. As of now, `8.9.1` is the latest one we could use.

Awesome, dependency is there, so we could go ahead and create an instance of `DockerClient` class. There are a couple of ways to do that and, essentially, it really depends on which operating system (or systems) you are using (either in development, continuous integration or production environments).

Probably, the quickest, safest and most portable approach would be to use `DefaultDockerClient.fromEnv`  method which will gather the required details from the environment variables and will work across a range of [Docker](https://www.docker.com/) installations, including older Mac and Windows systems were [Docker](https://www.docker.com/) is not natively supported (things like [Docker Toolbox](https://docs.docker.com/toolbox/toolbox_install_windows/) or [boot2docker](https://github.com/boot2docker/boot2docker)).

| `1` | `final` `DockerClient client = DefaultDockerClient` |

| `2` | `.fromEnv()` |

| `3` | `.build();` |

Here we just assume the default [Docker](https://www.docker.com/) configuration is in place but you have a total [control over customizing](https://github.com/spotify/docker-client/blob/master/docs/user_manual.md#creating-a-docker-client) it, including connection URIs, registry authentication, connection pooling, etc.  It is important to remember that when you are done with the instance of the client, please close it, for example:

| `1` | `client.close();` |

Great, we have our [Docker](https://www.docker.com/) client instance. It is a single entry point to call numerous [Docker Engine APIs](https://docs.docker.com/engine/api/), let us take a look what we could accomplish with it.

## 4\. Images

The first [Engine API](https://docs.docker.com/engine/api/) we are going to look at is [Images API](https://docs.docker.com/engine/api/v1.30/#tag/Image). The [Spotify Docker Client](https://github.com/spotify/docker-client) supports most of its features through a family of methods. To illustrate that, let us borrow the [Dockerfile](https://docs.docker.com/engine/reference/builder/) from the previous section of the tutorial and store its content in the `src/main/resources` folder, inside the file with name `Dockerfile`:

| `1` | `FROM openjdk:8u131-jdk-alpine` |

| `2` | `CMD [``"java"``,` `"-version"``]` |

And now, let us build the image from it using [Spotify Docker Client](https://github.com/spotify/docker-client):

| `1` | `final` `URL dockerfile = getClass().getResource(``"/"``);` |

| `2` |   |

| `3` | `final` `String imageId = client.build(Paths.get(dockerfile.toURI()),` |

| `4` | `BuildParam.name(``"base:openjdk-131-jdk"``));` |

Easy, but how could we check if the image is there? Our old buddy [docker](https://docs.docker.com/engine/reference/commandline/cli/) command line tool comes into mind first, but why not to use [Spotify Docker Client](https://github.com/spotify/docker-client) for that?

| `1` | `final` `ImageInfo imageInfo = client.inspectImage(imageId);` |

Nice, what about fetching all available images?

| `1` | `final` `List allImages = client.listImages();` |

What if we need to add additional tags to the image?

| `1` | `client.tag(imageId,` `"openjdk"``);` |

It is also possible to get image history, for example:

| `1` | `final` `List history = client.history(imageId);` |

In case we do not need this image anymore, it could be easily removed:

| `1` | `final` `List removedImages = client.removeImage(imageId,` `true``,` `false``);` |

We can also search images in the [Docker Hub](https://hub.docker.com/) registry. For example, let us look up for all available JDK images:

| `1` | `final` `List jdkImages = client.searchImages(``"jdk"``);` |

To interface with registries, there are pull and push methods. The first one fetches the image from a registry while the latter uploads it to a registry.

| `1` | `client.pull(``"base:openjdk-131-jdk"``);` |

| `2` | `client.push(``"base:openjdk-131-jdk"``);` |

In order to get more details related to images manipulation, please check out the [the official Spotify Docker Client documentation](https://github.com/spotify/docker-client/blob/master/docs/user_manual.md#images).

## 5\. Containers

## 6\. Ports

## 11\. Conclusions

Fairly speaking, [Docker Engine API](https://docs.docker.com/engine/api/) is just a set of [REST(ful) services](https://en.wikipedia.org/wiki/Representational_state_transfer), very rich ones though. For sure, anyone could access them from any Java application just by using generic HTTP client. So what the deal?

Personally, I would emphasize the explicit contracts, maintainability and type-safety. Instead of dealing with URIs, query or path parameters, raw [JSON](http://www.json.org/) for request and response payloads, you have a stable Java-based API, with strict set of capabilities and expectations.

As we are going to see later on, [Spotify Docker Client](https://github.com/spotify/docker-client) serves as a solid foundation for automation and advanced testing techniques, particularly in context of Java development. Thank you, [Spotify](https://spotify.github.io/), for giving back to the community!

In order to package a typical [Spring Boot](https://projects.spring.io/spring-boot/) application as a [Docker](https://www.docker.com/) image using [Gradle](https://gradle.org/) we just need to include two additional plugins in `build.gradle` file:

## 4\. Gradle on Docker

It turns out that building [Docker](https://www.docker.com/) images with [Gradle](https://gradle.org/) is not painful at all. But still, the prerequisite to have [Gradle](https://gradle.org/) installed on the target system, along with JDK/JRE, requires some preliminary work to be done. It may not be an issue let say for development, as it is very likely you would have all of that (and many more) installed anyway.

In the case of cloud deployments or CI/CD pipelines, this could be an issue though, incurring additional costs in terms of work or/and maintenance. Could we somehow find a way to get rid of such overhead and rely on [Docker](https://www.docker.com/) entirely? Yes, in fact we can, by adopting [multi-stage builds](https://docs.docker.com/engine/userguide/eng-image/multistage-build/), one of the recent additions to the [Docker](https://www.docker.com/) feature set.

If you are wondering how it may help us, here is the idea. Essentially, we are going to follow the regular procedure to build the image from the [Dockerfile](https://docs.docker.com/engine/reference/builder/). But the [Dockerfile](https://docs.docker.com/engine/reference/builder/) would actually contain two image definitions. The first one (based on the one of the [official Gradle images](https://hub.docker.com/_/gradle/)) instructs the [Docker](https://www.docker.com/) to run the [Gradle](https://gradle.org/) build of our [Spring Boot](https://projects.spring.io/spring-boot/) application. The second one would pick the binaries produced by the first image and create the final [Docker](https://www.docker.com/)  image with our [Spring Boot](https://projects.spring.io/spring-boot/) application sealed inside (much like we have done before).

It might be better to see it once than trying to explain it. The `Dockerfile.build` file below illustrates this idea in action, using [multi-stage build](https://docs.docker.com/engine/userguide/eng-image/multistage-build/) instructions.

| `01` | `FROM gradle:4.3.0-jdk8-alpine` |

| `02` |   |

| `03` | `ADD src src` |

| `04` | `ADD build.gradle .` |

| `05` | `ADD gradle.properties .` |

| `06` |   |

| `07` | `RUN gradle build` |

| `08` |   |

| `09` | `FROM openjdk:8-jdk-alpine` |

| `10` | `ARG BUILD_VERSION` |

| `11` |   |

| `12` | `ENV DB_HOST localhost` |

| `13` | `ENV DB_PORT 3306` |

| `14` |   |

| `15` | `COPY --from=0 /home/gradle/build/libs/spring-boot-webapp-${BUILD_VERSION}.jar spring-boot-webapp.jar` |

| `16` |   |

| `17` | `EXPOSE 19900` |

| `18` |   |

| `19` | `ENTRYPOINT` `exec` `java $JAVA_OPTS -Ddb.host=$DB_HOST -Ddb.port=$DB_PORT -jar /spring-boot-webapp.jar` |

The first part of the [Dockerfile](https://docs.docker.com/engine/reference/builder/) definition describes the image based on  `gradle:4.3.0-jdk8-alpine`. Because our project is quite small, we just copy all the sources inside the image and run `gradle build` command (this command will be executed by [Docker](https://www.docker.com/) while the image is being built). The result of the build would be the [uber-jar](https://stackoverflow.com/questions/11947037/what-is-an-uber-jar) which we feed into another image definition, this time based on `openjdk:8-jdk-alpine`. This would constitute our final image, which we could produce using [docker](https://docs.docker.com/engine/reference/commandline/cli/) command line tool.

| `1` | `docker image build \` |

| `2` | `--build-arg BUILD_VERSION=0.0.1-SNAPSHOT \` |

| `3` | `-f Dockerfile.build \` |

| `4` | `-t jcg/spring-boot-webapp:latest \` |

| `5` | `-t jcg/spring-boot-webapp:0.0.1-SNAPSHOT .` |

Upon command competition, we should see our newly baked image in the list of the available [Docker](https://www.docker.com/) images.

| `1` | `$ docker image` `ls` |

| `2` | `REPOSITORY               TAG            IMAGE ID       CREATED           SIZE` |

| `3` | `jcg/spring-boot-webapp   0.0.1-SNAPSHOT  02abf724da64  10 seconds ago    133MB` |

| `4` | `jcg/spring-boot-webapp   latest          02abf724da64  10 seconds ago    133MB` |

| `5` | `...` |

There is lot of potential behind [multi-stage builds](https://docs.docker.com/engine/userguide/eng-image/multistage-build/), but even for such a simple application as ours they have proven to be worth the attention.

| `09` |   |

| `10` | `exec` `"$@"` |

### 5.2\. cAdvisor

Often while we are developing our applications there is a need to get more insights regarding what is going on with our containers, either we are talking about CPU, memory or network utilization. Luckily, there are quite a few options here and one of the very useful tools we are going to talk about is [cAdvisor](https://github.com/google/cadvisor) (or in full version, container advisor) which analyzes the resource usage and performance characteristics of running containers.

> “[*cAdvisor*](https://github.com/google/cadvisor) *provides container users an understanding of the resource usage and performance characteristics of their running containers. It is a running daemon that collects, aggregates, processes, and exports information about running containers. Specifically, for each container it keeps resource isolation parameters, historical resource usage, histograms of complete historical resource usage and network statistics. This data is exported by container and machine-wide.*” – [https://github.com/google/cadvisor](https://github.com/google/cadvisor)

Interestingly, [cAdvisor](https://github.com/google/cadvisor) goes beyond just [Docker](https://www.docker.com/) and should support just about any other container type out of the box. ## 6\. Docker Engine Metrics

[Docker](https://www.docker.com/) engine exposes a lot of interesting metrics in the format which is fully compatible with [Prometheus](https://prometheus.io/), tremendously popular open-source monitoring and alerting solution. Although this feature became generally available quite a while ago, not many people know about it and as such, not many make use of it.

This feature is still considered experimental so it is not available by default and needs a bit of configuration tweaking. The [official documentation](https://docs.docker.com/engine/admin/prometheus/) thoroughly describes all the necessary steps to be done with respect to the operating system you are running [Docker](https://www.docker.com/) on. But essentially, the first step is to modify `daemon.json` and add the following properties there.

| `1` | `{` |

| `2` | `"metrics-addr"` `:` `"localhost:9323"``,` |

| `3` | `"experimental"` `:` `true` |

| `4` | `}` |

In order for this change to take effect, the [Docker](https://www.docker.com/) daemon should be restarted. Right after, the metrics should become available at the [http://localhost:9323/metrics](http://localhost:9323/metrics) endpoint. Next step is to prepare [Prometheus](https://prometheus.io/) configuration, `prometheus.yml`, in order to scrape the [Docker](https://www.docker.com/) engine metrics.

| `1` | `scrape_configs:` |

| `2` | `- job_name:` `'prometheus'` |

| `3` | `static_configs:` |

| `4` | `- targets: [``'localhost:9090'``]` |

| `5` | `- job_name:` `'docker'` |

| `6` | `static_configs:` |

| `7` | `- targets: [``'localhost:9323'``]` |

With this minimal configuration in hand we could start the [Prometheus](https://prometheus.io/) server (which has reached version `2.0` as of moment of this writing) as [Docker](https://www.docker.com/) container:

| `1` | `docker run -p 9090:9090 \` |

| `2` | `-``v` `prometheus.yml:/etc/prometheus/prometheus.yml \` |

| `3` | `prom/Prometheus` |

Once the container is started, the [Prometheus](https://prometheus.io/) web UI should be available at [http://localhost:9090](http://localhost:9090). Let us navigate to this URL and check that all targets we have configured are accessible.

[![Prometheus Targets](images/prometheus-jcg-1024x367.png)](http:../images/prometheus-jcg.png)

Prometheus Targets

Fairly speaking, the [Prometheus](https://prometheus.io/) web UI is quite capable to graph different metrics but [Grafana](https://grafana.com/), another open-source project, is the state of the art platform to query, visualize, alert on and understand the metrics.

| `1` | `docker run -d -p 3000:3000 \` |

| `2` | `-e` `"GF_SECURITY_ADMIN_PASSWORD=pa$$w0rd"` `\` |

# Test on Docker

## 1\. Introduction

If we think about the areas of software engineering where the impact of the [Docker](https://www.docker.com/) and container-based virtualization is most noticeable, testing and test automation is certainly one of those. As the software systems become more and more complex, so do the software stacks they are built upon, with many moving parts involved.

In this section of the tutorial we are going to learn a couple of the frameworks which enormously simplify the integration, component and end-to-end testing of JVM-based applications by leveraging [Docker](https://www.docker.com/) and the tooling around it.

## 2\. Before getting started

In the [second part of this tutorial](https://www.javacodegeeks.com/2017/09/docker-java-developers-docker-command-line.html) we have briefly mentioned that Java applications deployed as [Docker](https://www.docker.com/) containers should use at least `Java 8 update 131` or later but we have not had chance to elaborate on importance of this fact just yet.

To understand the issue, let us focus on how JVM deal with two most important resources for Java applications: memory (heap) and CPU. For the purpose of the illustration, we are going to have [Docker](https://www.docker.com/) installed on a dedicated virtual machine which has `2 CPU cores` and `4GB of memory` allocated. Keeping this configuration in mind, let us take a look on that from JVM perspective:

| `1` | `$ docker run --``rm` `openjdk:8-jdk-alpine java -XshowSettings:vm -XX:+UseParallelGC -XX:+PrintFlagsFinal –version` |

There are going to be a lot of information printed out in the console, but there most interesting pieces for us are `ParallelGCThreads` and `VM settings`.

| `01` | `...` |

| `02` | `uintx ParallelGCThreads = 2` |

| `03` | `...` |

| `04` |   |

| `05` | `VM settings:` |

| `06` | `Max. Heap Size (Estimated): 992.00M` |

| `07` | `Ergonomics Machine Class: server` |

| `08` | `Using VM: OpenJDK 64-Bit Server VM` |

| `09` |   |

| `10` | `openjdk version` `"1.8.0_131"` |

| `11` | `OpenJDK Runtime Environment (IcedTea 3.4.0) (Alpine 8.131.11-r2)` |

| `12` | `OpenJDK 64-Bit Server VM (build 25.131-b11, mixed mode)` |

On the machines with less than (or equal to) 8 cores, the `ParallelGCThreads` is [equal to number of cores](https://docs.oracle.com/javase/8/docs/technotes/guides/vm/gctuning/parallel.html), while the default maximum limit for heap is roughly [25% of available physical memory](https://docs.oracle.com/javase/8/docs/technotes/guides/vm/gc-ergonomics.html). Cool, the numbers which JVM reports make sense so far.

Let us push it a bit further and use [Docker](https://www.docker.com/) resource management capabilities to restrict container CPU and memory usage to `1 core` and `256Mb` respectively.

## 3\. Storing data in RAM

It is rarely the case that the application has no dependency on some kind of data store (sometimes even more than one). And, unsurprisingly, most of such stores persist the data on some kind of durable storage. This is great indeed, but quite often the presence of such data stores makes the testing a challenge, specifically when summoning the isolation of the test cases on the data level.

You may have already guessed, [Docker](https://www.docker.com/) could enormously reduce the efforts required to create reproducible test scenarios. But still, the data stores serve as the major contributor to overall test execution time.

As we are going to see in a moment, [Docker](https://www.docker.com/) has something in the sleeve to help us out: [tmpfs](https://docs.docker.com/engine/admin/volumes/tmpfs/). It effectively gives the container a way to manage the data without writing it anywhere permanently, keeping it in the host machine’s memory (or swap, if memory is running low).

There are multiple options available which allow to attach [tmpfs](https://docs.docker.com/engine/admin/volumes/tmpfs/)-backed volumes to your container, but the recommended one these days is to use `--mount` command line argument (or [tmpfs](https://docs.docker.com/compose/compose-file/#tmpfs) section of the specification in case of [docker-compose](https://docs.docker.com/compose/reference/overview/)).

| `1` | `docker run --``rm` `-d \` |

| `2` | `--name mysql \` |

| `3` | `--``mount` `type``=tmpfs,destination=/var/lib/mysql \` |

| `4` | `-e MYSQL_ROOT_PASSWORD=``'p$ssw0rd'` `\` |

| `5` | `-e MYSQL_DATABASE=my_app_db \` |

| `6` | `-e MYSQL_ROOT_HOST=% \` |

| `7` | `mysql:8.0.2` |

The speed gains for test executions could be tremendous, but you should not use this feature in production (and very likely, in any other environments), ever, because when the container stops, the [tmpfs](https://docs.docker.com/engine/admin/volumes/tmpfs/) mount disappears. Even if the container is committed, the [tmpfs](https://docs.docker.com/engine/admin/volumes/tmpfs/) mount is not saved.

## 4\. The Scenario

Armed with these tricks and tips, we could discuss the test scenario we are going to implement. Essentially, it would be great to run end-to-end test for one of the applications we have developed in the previous parts of the tutorial. The eventual goal of the test scenario would be to verify that [REST(ful) APIs](https://en.wikipedia.org/wiki/Representational_state_transfer) for tasks management is available and returning the expected results.

From the deployment stack perspective, it means we have to have the instance of [MySQL](https://www.mysql.com/) and the instance of the application (let us pick the [Spring Boot](https://projects.spring.io/spring-boot/) based one we have developed before but it does not really matter much). This application exposes the [REST(ful) APIs](https://en.wikipedia.org/wiki/Representational_state_transfer) and should be able to communicate with [MySQL](https://www.mysql.com/) instance. Surely, we would like those instances to live as [Docker](https://www.docker.com/) containers.

The test scenario is going to call the task managements [REST(ful) APIs](https://en.wikipedia.org/wiki/Representational_state_transfer) to get the list of all available tasks, using terrific [REST-assured](http://rest-assured.io/) framework for test scaffolding. Also, all our test scenarios are going to be based on [JUnit](http://junit.org/) framework.

## 7\. Overcast

# Deploy on Docker

## 1\. Introduction

Many companies have been using container-based virtualization to deploy applications (including JVM based ones) in production way before [Docker](https://www.docker.com/) appearance on the horizon. However, primarily because of [Docker](https://www.docker.com/), deployment practices using containers turned into the mainstream these days.

In this section of the tutorial we are going to glance over some of the most popular orchestration and cluster management engines (covering a couple of cloud offerings as well) which natively support deployment and lifecycle of the containerized applications.

The topics we are going to talk about are worth of several books (at least!) so the goal of this part would be to serve as an introduction. If you feel a particular interest in any of those, there is a tremendous amount of the resources available in the public access.

## 2\. Containers as Deployment Units

These days containers (in particular, [Docker](https://www.docker.com/) containers) became standardized units of software deployment. They are prepackaged with everything that the applications may need to run: code (or binary), runtime, system tools and libraries, you name it.

Managing and orchestrating the container-based deployments is quite a hot topic and, as we are going to see in a moment, every solution out there offers it right from the start.

## 3\. Orchestration using Kubernetes

In a rare case you haven’t heard about it yet, [Kubernetes](https://kubernetes.io/) is an open-source system for automating deployment, scaling, and management of containerized applications. This is one of the most exciting, innovative and actively evolving projects in the open-source community. Probably, if you or your company is looking for container orchestration solution, [Kubernetes](https://kubernetes.io/) is the de-facto choice nowadays.

There are a lot of things which [Kubernetes](https://kubernetes.io/) could do for you, but in this part of the tutorial we are going to see how easy it is to deploy our containerized [Spring Boot](https://projects.spring.io/spring-boot/) application stack, including [MySQL](https://dev.mysql.com/doc/connector-j/8.0/en/), using only minimal subset of the [Kubernetes](https://kubernetes.io/) features.

Setting up a full-fledged [Kubernetes](https://kubernetes.io/) cluster on the local machine might sound a bit impractical but luckily [Kubernetes](https://kubernetes.io/) could be deployed in development mode via [minikube](https://kubernetes.io/docs/getting-started-guides/minikube/#quickstart). This awesome tool spawns a single-node [Kubernetes](https://kubernetes.io/) cluster inside a virtual machine so you could develop on it day-to-day using your laptop or desktop for example.

With the assumption that you [installed minikube](https://kubernetes.io/docs/getting-started-guides/minikube/#installation) on the operating system of your choice, let us move on to the next step and deploy a couple of [Docker](https://www.docker.com/) containers on it.

## 4\. Orchestration using Apache Mesos

[Apache Mesos](http://mesos.apache.org/) is arguably the one of the oldest resource and cluster management frameworks in use. It effectively abstracts resources (CPU, memory, storage) away from physical or virtual hardware, allowing to build and operate fault-tolerant and elastic distributed systems. One of its strengths is exceptional level of extensibility and support of containerized application deployments, however it is also known to be quite complex and difficult to operate.

Architecturally, [Apache Mesos](http://mesos.apache.org/) consists of a `master` that manages `agents` (running on each cluster node), and `frameworks` (that run `tasks` on these agents). The master enables fine-grained sharing of resources (CPU, RAM, …) across frameworks by making them `resource offers`. Bounding ourselves to only the necessary components, let us take a look on how [Apache Mesos](http://mesos.apache.org/) cluster could be defined using [docker-compose](https://docs.docker.com/compose/compose-file/compose-file/) specification.

## 5\. Orchestration using Docker Swarm

It has been awhile since [Docker](https://www.docker.com/) has the cluster management and orchestration features embedded in the engine. This orchestration layer is used to be known as [Docker Swarm](https://github.com/docker/swarm) but later on evolved into, essentially, just a special mode ([swarm mode](https://docs.docker.com/engine/swarm/)) to run [Docker Engine](https://docs.docker.com/engine/) in.

If you are betting heavily on [Docker](https://www.docker.com/) and prefer not to look for anything else, running [Docker Engine](https://docs.docker.com/engine/) in a [swarm mode](https://docs.docker.com/engine/swarm/) could be a good option as an orchestrator. It is fairly easy to get started with as well.

[view source](#DeployOnDocker.xhtml_viewSource "view source")[print](#DeployOnDocker.xhtml_printSource "print")[?](#DeployOnDocker.xhtml_about "?")

| `1` | `$ docker swarm init` |

Conceptually, there are quite a few differences which swarm mode introduces, beyond just changes in the [Docker Engine](https://docs.docker.com/engine/) itself. First and foremost, you should start thinking in terms of services, not containers. The assumptions about running everything inside single [Docker](https://www.docker.com/) host won’t be accurate anymore as the swarm would very like consist of many [Docker](https://www.docker.com/) hosts distributed over the network.

When running [Docker Engine](https://docs.docker.com/engine/) in a [swarm mode](https://docs.docker.com/engine/swarm/), we can deploy a complete application (service) stack using already familiar [docker-compose](https://docs.docker.com/compose/compose-file/compose-file/) specification. There is only one constraint though, the [docker-compose](https://docs.docker.com/compose/compose-file/compose-file/) file format should be version `3 (or above)` to be compatible between [Docker Compose](https://docs.docker.com/compose/overview/) and [Docker Engine](https://docs.docker.com/engine/)’s [swarm mode](https://docs.docker.com/engine/swarm/).

To see the [swarm mode](https://docs.docker.com/engine/swarm/) in action, let us rework our [Spring Boot](https://projects.spring.io/spring-boot/) application stack a bit to comply with [docker-compose](https://docs.docker.com/compose/compose-file/compose-file/) file format version `3.3`.

## 6\. Containers in the Cloud

Every major player in the cloud space is rushing to the market their own managed offerings which intend to support the deployment and orchestration of the containers so you could just drop one and magic happens. Let us quickly glance through them.

### 6.1\. Amazon Elastic Container Service

[Amazon Elastic Container Service](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html) (or simply [Amazon ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html)) is a highly scalable, fast, container management service that makes it easy to run, stop, and manage [Docker](https://www.docker.com/) containers in the cluster. As you may expect, [Amazon ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html) integrates nicely with many other cloud offerings from [Amazon Web Services](https://aws.amazon.com/) portfolio, including:

*   AWS Identity and Access Management
*   Amazon EC2 Auto Scaling
*   Elastic Load Balancing
*   Amazon Elastic Container Registry
*   AWS CloudFormation

[Amazon ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html) is a regional service that simplifies running application containers in a highly available manner across multiple availability zones within a region.

### 6.2\. Google Kubernetes Engine

[Google Kubernetes Engine](https://cloud.google.com/kubernetes-engine/) (formerly known as Google Container Engine) is a managed environment for deploying containerized applications. It brings [Google](https://www.google.com)’s unique experience and latest innovations in developer productivity, resource efficiency, automated operations, and open source flexibility to accelerate the time to market.

Google has been running production workloads in containers for a very long time, and have incorporated the best of what they learnt into [Kubernetes](https://kubernetes.io), the industry-leading open source container orchestrator which powers [Kubernetes Engine](https://cloud.google.com/kubernetes-engine/). It offers (but is not limited to) the following distinguishing features:

*   Identity & Access Management
*   Hybrid Networking
*   Security and Compliance
*   Integrated Logging & Monitoring
*   Auto Scale
*   Auto Upgrade
*   Auto Repair
*   Resource Limits
*   Stateful Application Support
*   [Docker](https://www.docker.com/) Images Support
*   Fully Managed
*   OS Built for Containers
*   Private Container Registry
*   Fast Consistent Builds
*   Open Source Portability

### 6.3\. Azure Container Service

[Azure Container Service](https://azure.microsoft.com/en-ca/services/container-service/) (AKS) manages the hosted [Kubernetes](https://kubernetes.io) environment, making it quick and easy to deploy and manage containerized applications without container orchestration expertise. It also eliminates the burden of ongoing operations and maintenance by provisioning, upgrading, and scaling resources on demand, without the need to take the applications offline.

As a managed [Kubernetes](https://kubernetes.io) service, [Azure Container Service](https://azure.microsoft.com/en-ca/services/container-service/) provides:

*   Automated [Kubernetes](https://kubernetes.io) version upgrades and patching
*   Easy cluster scaling
*   Self-healing hosted control plane (masters)
*   Pay only for running agent pool nodes

## 1. Introduction

## 2\. Why Jenkins?

For many, the relationship with [Jenkins](https://jenkins.io/) falls into hate or love category. Leaving the history behind, the second generation of [Jenkins](https://jenkins.io/) platform, namely `2.x` release branch, hit the ecosystem like a tornado and literally became a game changer.

*   Built-in support for delivery pipelines (also known as “pipeline as a code”)

*   Very easy to install and configure
*   Exceptional extensibility and very rich plugins ecosystem

## 5\. Docker in Jenkins

As we mentioned already, [Jenkins](https://jenkins.io/) has an outstanding [Docker](https://www.docker.com/) support fulfilled by fair number of plugins with [Docker plugin](https://plugins.jenkins.io/docker-plugin) and [Docker Pipeline plugin](https://plugins.jenkins.io/docker-workflow) being the keys ones. What it means practically is that your pipeline (or other kind of job) may spin up containers to run the build (and any other tasks or stage) on them.

The best way to illustrate the difference is to modify our [Jenkinsfile](https://jenkins.io/doc/book/pipeline/jenkinsfile/) from the previous section to use [Docker](https://www.docker.com/) agent instead of predefined tooling.

This pipeline looks more compact. We get rid of quite a few definitions (and practically could get rid of some initialization scripts as well). When we commit this new [Jenkinsfile](https://jenkins.io/doc/book/pipeline/jenkinsfile/) to our existing repository (overriding the current one) we should observe a bit different set of stages but the build is still green.

![](images/build-docker-jcg.png)

Build stages with Docker

This is just one example of [Docker](https://www.docker.com/) integration with [Jenkins](https://jenkins.io/), there are tons of different ways you could leverage [Docker](https://www.docker.com/)  to push the limits of your continuous integration (and delivery) processes to perfection.

There is one more thing to mention here before we wrap up the discussion. Because we are running [Jenkins](https://jenkins.io/) in [Docker](https://www.docker.com/), and [Jenkins](https://jenkins.io/) itself executes job/stage steps in [Docker](https://www.docker.com/), such model of containers usage is known as `Docker-in-Docker` (or shortly `DinD`). There are quite a few things to be aware of when you are running `DinD` environments, brilliantly summarized by [Jérôme Petazzoni in the blog post](https://jpetazzo.github.io/2015/09/03/do-not-use-docker-in-docker-for-ci/). Please check it out if you are seriously considering this model.
