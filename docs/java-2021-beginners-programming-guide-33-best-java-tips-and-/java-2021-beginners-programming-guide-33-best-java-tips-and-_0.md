## 什么是 Java 语言？

Java 是一种高级、编译型、过程化的语言，通常用作 Java 虚拟机 (`JVM`) 的底层引擎，并作为 Java 标准库的基础。

Java 是几种可以编译为机器码并运行的编程语言之一，它可以运行在 IBM 主机、英特尔 x86 处理器以及许多其他架构上。

由于 Java 是一种脚本语言，它被认为是一门动态编程语言，这意味着很容易自动化执行包含许多步骤的任务，且很少或没有样板代码。

Java 运行在许多不同的平台上：它运行在 Unix、Linux 和 macOS 操作系统上；运行在 Microsoft Windows 上；它是 Android 的首选语言。你还可以在服务器、容器化环境以及嵌入式系统（如树莓派）上运行 Java。

Java 是一种以开发者为中心的编程语言，这意味着它是为那些希望为从命令行到网络浏览器的各种系统编写代码的程序员而设计的。它也是一种对扩展和自定义非常友好的语言。

传统上，Java 被认为是一门“服务端”语言，这意味着它非常适合编写服务器应用程序。但随着时间的推移，它创建桌面应用程序的潜力不断增长。这部分归功于其 Cordova 软件开发包，它允许 Java 代码作为移动应用程序的基础。

## 选择合适的编辑器

选择要使用的哪种 `IDE` 有一些原因。首先，最重要的是，你需要确保它是高效的。如果不选择正确的编辑器，你就无法构建出一个高效的工作环境。

选择一个良好的 `IDE` 的另一个原因是它的易学性。通过 Windows 版本的 Visual Studio，你将可以使用 Windows Visual Studio `IDE`，这意味着你可以与你开发团队的其他成员在相同的环境中学习它。这使得学习变得容易得多。

## Java 语言的优势是什么？

与其他编程语言相比，`Java` 语言具有许多优势，包括：

- **一致性**。每个 `Java` 程序都可以编译成相同的字节码。这允许人们以这种方式编写程序，使得每个运行的程序看起来都一样。虽然每个 `Java` 程序也可以被即时解释，但其性能更为局限。
- **硬件赋能**。由于 `Java` 虚拟机被编译为 `Java` 字节码，`JVM` 可以运行所有所有支持的处理器。
- **打包应用开发**。与其他编程语言不同，`Java` 程序的编写方式可以使整个程序被打包、放入磁盘并进行部署。这显著缩短了部署和生产所需的时间。
- **编译器即代码**。`Java` 程序被编译成机器码（通常是某种指令集架构的变体），然后由计算机执行。这避免了在运行时重写代码的需求。

在使用 `Java` 时，某些优势只有通过使用 `JVM` 才能实现。好消息是，通过 `JVM` 可以提高应用程序的性能。

## Java 语言的缺点是什么？

使用 `Java` 有许多缺点。一个缺点是许多开发者认为它是一门复杂的语言。另一个缺点是它比其他编程语言更消耗内存。

这意味着即使应用程序使用的内存较少，也可能会产生性能影响。更重要的是，如果应用程序加载时间过长或发生冻结，将影响用户体验。

一个不经常移动或变化的应用程序将获得更好的用户体验。使用 `Java` 的一个良好例子是 `Yahoo! Finance`。

如果你是一家企业或能够证明你是一家企业，你可以使用替代的编程语言，例如 `PHP`。

## J2EE 应用服务器设计是否存在设计缺陷？

**与其他应用服务器不兼容**：J2EE 应用服务器规范没有显式支持不同 J2EE 应用服务器之间的互操作性。

**对需求的更改**：需求的更改不是通过规范进行的，而且目前还不清楚更改将是什么。未来的规范版本可能需要此类更改。

## Java 语言规范 (JLS) 指定的版本是最终版本吗，还是会以某种方式进行修订？

Java 语言规范指定的版本是纯粹的规范，尚未指定任何最终版本。例如，在网上无法找到任何定义哪个版本的 Java 语言是最新版本的文章。如果 JLS 发生某种变化，可能会影响 Java 语言规范的最新版本。

## 我应该使用 J2EE 应用服务器规范来编写 J2EE 应用程序吗？

Java 语言规范并没有要求为 J2EE 应用程序使用应用服务器规范。可以存在不使用规范或与规范配合的 J2EE 实现，但它们的构建方式与当前最常见的实现不同。

## J2EE 客户端知道如何创建一个与服务器通信的程序？

它可以通过其定义的接口创建一个与服务器通信的程序。与服务器通信的程序可以使用服务器支持的任何类型，使用该类型的客户端可以将该程序视为服务器。它还可以使用该程序的任何行为，无论该行为是由程序本身提供的还是由其他客户端方法提供的。J2EE 客户端不需要创建自己的 J2EE 服务器；如果现有服务器支持客户端接口，它可以使用任何现有的服务器。

与应用服务器通信的程序使用 `Session` 协议来实现此。客户端定义了一个指向服务器的接口。然后，它可以使用接口中的任何方法或不同的类来与服务器通信。

客户端还需要一种从服务器接收消息的方法。消息类型使用客户端类的 `read` 方法创建。只要该类型与类兼容，它就可以从服务器接收任何类型的消息。特别是，它可以同时接收基于方法的消息和基于消息的消息。

客户端也可以向服务器发送消息，但它必须使用客户端类的 `write` 方法来写入消息，并且在发送自己的消息之前必须等待消息发送完毕。通过这种方式，客户端可以以类似于客户端程序与人类程序（如网络浏览器）通信的方式发送消息。

## J2EE 规范定义了哪些 J2EE 特性和标准 J2EE 服务器？

J2EE 定义了几种标准方法，每个方法都在各自的规范中描述。提供的 J2EE 特性列表说明了 J2EE 标准如何定义这些特性。

另一个 J2EE 特性是可以可以在定义定义实现的情况下调用方法并定义处理器。然后，为实现接口的客户端提供这些方法中每个方法的默认实现。

符合标准 J2EE 服务器的 Java 类在类定义中添加以下代码：

```java
public final class JavaServer implements Service {
    public void write(Session session, ReadableReusableData<String> data) {
        WriteableReusableData<String> data = data;
        return true;
    }
    public void read(Session session, String s) {
        String data = s;
        return true;
    }
}
```

## JavaServer 接口是如何工作的？

`JavaServer` 接口指定了服务器支持的方法。

`write` 方法由客户端调用，它为客户端向服务器发送数据提供了一种方法。如果服务器有响应，则返回 true，否则返回 false。`read` 方法在客户端向服务器发送数据时由服务器调用。它返回数据的实际值，无论数据是否正确。

`JavaServer` 实现是 `JavaServerBase` 类的子类。特别是，它添加了 `java.lang` 包中的方法以及服务器实现。该实现还为 `read` 方法定义了默认实现，以便没有实现接口的客户端仍然访问 `read` 方法的默认实现。

`JavaServer` 类还定义了几个工厂方法，允许客户端在没有实现接口时设置一个备备用的 `JavaServer` 实例。标准 J2EE 实现支持以下内容：

- `java.util.Scanner` 用于读取单条消息。

- `java.io.InputStreamReader` 用于读取消息数据。

- `java.io.OutputStreamWriter` 用于写入消息数据。

- `java.io.OutputStream` 用于写入二进制消息。

- J2EE 尚未集成到 Java EE 6。

### 是否可以在基于 J2EE 的配置中部署 Java EE 6 应用程序？

可以的。`JavaServer` 和 `JavaServerBase` 实现具有两个完全不同的定义。`JavaServer` 接口不会影响 `JavaServer` 实现的行为。然而，`JavaServer` 实现也能够运行和配置其他服务器实现。

这些其他服务器实现可以在 `java.net` 命名空间中找到。它们被包含在 `JavaServer` 实现命名空间中，是因为它们是用 Java 实现的。

此外，J2EE 的当前版本（`J2EE 1.5`）是 `JavaServer` 接口的一个独立实现。它与 Java EE 6 完全不冲突。从 J2EE 1.5 开始，`J2EE 1.5` 实现对 `JavaServer` 接口的定义不同。它定义了 `java.net.Server` 接口。定义此接口是为了允许 J2EE 实现独立开发，并允许不同的 `JavaServer` 接口实现部署在同一个环境中。

在 J2EE 1.5 中，按照 Java EE 5 定义的 `JavaServer` 实现对 Java EE 6 中定义的 `JavaServer` 实现没有任何影响。

在 J2EE 1.5 中，`JavaServer` 接口是一个 `JavaInterfaces` 接口。该接口在 Java EE 5 中并不存在。在 Java EE 6 中，该接口现在是一个 `JavaServer` 实现接口。因此，可以配置 `JavaServer` 实现以部署到 Java EE 6。

## 类型推断中的空 (Null in type inference)

类型推断对于任何类型系统都是至关重要的，因为它可以帮助避免许多常见的错误，例如空引用。例如，类型推断中的空错误简单取决于类型系统如何识别何时需要空值，何时不需要。

因此，Scala 团队做出了若干设计决策，以使类型推断尽可能准确。

此类类型永远不会生成空检查（这可以通过在编译任务中手动设置类型来尝试修复）。因此，对于此类类型，如果你不确定值是否为空，则必须传递一个参数，例如空值或数组中另一个元素的引用。

如果类型不支持可空值，那么即使你向返回值的方法提供字符串值，该值也将为空。

这意味着，不像 `JavaScript`、`C#` 和 `Java` 等语言需要明确表达“空”的含义，在 Scala 中，你必须以可空类型来思考。当某些这些类型用原始类型表示时，这是一个缺点，但优点是 Scala 的类型推断非常出色，以至于这类问题非常罕见。

旧类型系统的最后残留遗迹是：如果你对一个带有操作符实例的对象进行引用，并尝试将该对象实例的值设置为 `null`，编译器将抛出异常。如果你尝试传递一个类型系统认为未初始化的值（即其类型不包含构造方法的值），它也总是会抛出异常。但你无法定义一种产生异常的失败条件，而这种异常在 Scala 处理未初始化数组、`null` 等情况时本应是正常情况。

## 优先使用闭包而非具体类型 (Favor closed over types)

Scala 的最后一个一个可以从类型推断中获益的领域是极少使用的 Scala 类型之一：函数的第一个参数。这是一个类型为 `AssertionError` 类型。该类型本质上是一个布尔值，表示断言是否失败，通常用于记录函数的第一个参数等操作。方法的调用要么成功（如果成功，则该方法中的代码执行成功），要么失败（如果失败，则方法调用未成功）。

因此，如果你不确定是否需要担心让第一个参数变为可选，函数的第一个参数可以是类型为 `AssertionError` 的类型（即 `False` 或 `Some [Failure]`）。在这种情况下，你可以自由地声明参数类型为 `AssertionError`（如果参数是第一个参数则为 `true`，否则也为 `true`）或 `AssertionError`（如果参数是第一个参数则为 `false`，否则为 `false`），而无需担心将其设为包含第一个参数值的类型。这结合类型推断，这意味着函数的第一个参数是一个值为 `False` 或 `Some[Failure]` 的未初始化元组，因为类型推断可以轻松识别出函数期望第一个参数的什么值，而无需任何显式实例化。

如果你在好奇，编译器之所以在函数第一个参数未初始化时智能地不抛出 `AssertionError`，原因在于：你总是将函数的第一个参数放入一个列表中，因此它在实际上是一个未初始化的元组。由于在这种情况下你保证会把第一个参数放入列表，而且由于元组列表始终只有一个值，因此编译器不需要担心其他问题。只要你不是开始向一个期望未初始化元组的函数传递列表，就是安全的。

在许多其他情况下，函数第一个参数的类型并不重要。如果函数有几个参数，如果函数正在对大型集合进行某种转换，那么省略第一个参数可能是合理的。或者，如果第一个参数只是非常简单的东西，比如元组或返回元组的函数，它可能完全没有影响。

### 为什么第一个参数很重要 (Why the first argument matters)

但让第一个参数作为一个至少包含一个参数的函数是非常重要的。其一，你不能将一个期望未初始化元组的函数传递给一个期望布尔值的实际方法。另一方面，如果函数有一个接口类型参数，你可能希望为函数的第一个参数提供一个合理的默认值（或至少是一个合理的可能值）。这有助于保持一致性。

许多期望被另一个函数调用的函数，在第一个参数上需要一些额外的安全保障。例如，假设你有这样一个函数：

```scala
def greet(person: Person, greeting: String) = person.greeting
```

此函数期望被另一个函数调用，而该函数又期望被另一个期望字符串的函数调用。在这种情况下，如果第一个参数未初始化，则第一个参数没有合理的默认值，因此你可能需要在调用第一个函数之前增加一个额外步骤：


# 第 4 章 Java 和 Javascript 是一样的吗？

极有可能，它们会非常相似，因为如果说有什么的话，它们将是你最初接触互联网的好地方，比如回到世界的中心。但如果你发现一些非常明显的区别，也不要惊讶。

在非常基础的层，Javascript 和 Java 的区别在于，当 Javascript 在计算机上运行时，它会访问操作系统的一个称为“网络堆栈”（network stack）的独立并在并在上运行。Java 版本将在标准的操作系统（即操作系统）上运行。Javascript 运行时与运行在 Java 上运行时，你的计算机行为在语义上存在差异。

这些语言会非常相似，但在实际理解业务及其运行细节的语境下，这些语言在语义上会有不同。如果你在经营业务，你将执行更多高层次的任务，该语言的语法与你作为开发者世界中的爱好者使用该语言时会非常不同。

## 我应该先学什么？

在 Javascript 的情况下，你可能对它的编程感兴趣是因为 Google 处理其搜索的方式。Javascript 的基本函数与 Java 非常相似，你能够创建带有参数的函数、获取函数结果并返回函数，这些都是类 Java 的构造。

你还应该考虑 Javascript 还有另外两个 Java 没有的“技巧”，即闭包（closures）和匿名函数（anonymous functions）。闭包是一种定义块的方式，该块无法以任何方式访问，但你可以在另一个函数或栈上的另一个块中访问它；匿名函数是另一种形式，函数将返回一个值，但它不会以任何方式绑定到全局作用域，以便下一个函数可以调用该函数，依此类推，你可以非常自然地传递变量。这些都是 Javascript 的基本构建模块。

你还会看到越越小的表达式函数，这些在 Java 中被称为 lambdas，在 Javascript 语境下将是函数，它们允许你执行与 Java 方法非常不同的事情，在 Java 中，你无法像在 Javascript 中那样通过函数传递变量。

但很多时候，如果你对 Javascript 的唯一接触仅于 Google 搜索以及在 Stack Overflow 等地方阅读关于该语言的文章，你会看到很多小而常见的 JavaScript 模式，你会很快开始学习它们，随着你理解和熟悉程度的增加，真正的基础语法和语言特征将复杂得多，如果你不了解语言中更小、更简单的部分，将无法理解这些内容。



我的经验是，在某一点，无论你学习 `Javascript` 多久，无论你写多少代码，你都会遇到必须阅读别人代码的时刻，这可能需要你花费一段时间。但大多数情况下，如果你现在开始学习 `Javascript`，我建议你从学习一些 `Javascript` 中没有的编程语言开始，以帮助建立基础。

## 什么是 Java 框架？

如果你习惯于使用框架（从定义上来说，大多数 `Java` 开发者都是如此），请阅读这关于关于框架及其本质的文章。框架的设计是为了帮助你使用通用功能，这些功能可以包含在代码库中，也可以为了开发而提取出来。

你可能会认为，如果你的应用程序完全由框架组成（几乎类似于 `JavaScript` 中的库），你应该编写自己的代码，而完全不需要担心框架。如果你遵循微服务的指南，这就是正确的，因为这正是现代代码库应该有的样子。你编写代码，而框架只为你提供它的静态部分。

但如果你想，例如编写一个可以在浏览器中运行的嵌入式服务器，或者只是一个暴露静态路由供客户端加载/列出你的 `RESTful API` 的 `Web API`，那么完全没有理由将你的代码考虑为某些底层框架的实现。你可以直接用纯 `Java` 编写应用程序，框架会为你完成额外的工作。

正是这种灵活性让框架变得令人头疼。你可能认为框架为代码增加的工作是为你完成的。但事实是，大多数框架的设计方式要求你以一种特定的方式来思考你所编写的代码。框架改变了你思考应用程序构建的方式。你不希望破坏你的结构，因为那会导致混乱。

举个快速的例子：要在你的 `Java Web` 应用程序中使用 `JSF`，你必须使用注解来指定 `Java` 对象应该如何渲染。

你需要这个注解，并且应该始终使用它。它会隐藏你的代码，并让不熟悉 `JSF` 的开发者清楚地知道这个类应该命名为 `MyPresenter`，并且它的 `primary()` 方法应该被命名为 `schedule()`。

## 框架设计考虑

现在我们解决了语义问题，让我们来谈论使得在 `Java` 中编写框架可能的设计选择。我在这里列出了其中几个，然后我尝试帮助你理解框架中包含的内容。

## 美学与语法

框架之所以糟糕，是因为它们看起来很难看。它们看起来像是回到了一个一切使用 `XML` 文件存储数据的世界。当你编写一个作为服务运行的脚本时，这可能看起来并不糟糕，但当你开始编写像 `Spring MVC` 框架这样的东西时，你会开始讨厌它。你想要向你构建应用程序的平台靠拢，但由于你正在编写一个框架，你的 `MVC` 代码需要遵守该框架的所有语法规范，以便让它看起来美观。

我之前说过框架糟糕是因为它们看起来很难看，但糟糕的部分并不是它看起来丑，而是一切都必须看起来美观，这增加了项目的复杂性。当你开始向系统中添加更多依赖和类时，你如何保持系统的模块化？你被迫将越来越多的纯洁、模块化的部分混合在一起以组成一个整体，这种垂直分离程度非常令人恼。

当你尝试编写纯 `Java` 框架时，也会发生同样。你不仅需要将代码封装在 `Java` 和 `Scala` 的特殊混合中以表现得像真正的框架，你还需要提供必要的库让框架理解它。例如，`javax.faces` 应该是 `Spring MVC` 的核心库，但你不能将其作为项目的依赖提供。

它和 `XML` 配置文件有相同的原因：它看起来和行为上应该像是设计为代码库的一部分的。你不想把它隐藏在某人找不到的地方，即使这有助于你增加它的模块化。所以你最终创建了一个巨大的类，带有一组抽象的 `API`，只有具备框架工作知识的开发者才能使用。

相比之下，`Java` 没有这个问题。一个想要使用设计为项目一部分的纯 `Java` 库的程序员可以直接使用它，而无需担心框架。`Spring MVC` 是一个 `Java` 库，而不是框架。它是开始 `Web` 开发的好地方，因为它提供的所有抽象都是纯 `Java` 的，不需要担心注解以及何时使用它们。`Scala` 团队从中吸了教训，开发了 `Typesafe Scala`，它和 `javax.faces` 一样，是一个 `Java` 库。

## Scala 和 MVC

使用 `Scala` 的最大优势是它从底层开始为 `MVC` 提供了框架。它是一种纯函数式语言，提供了原语和过程化抽象，从底层为你提供框架，而不需要额外的依赖。你只需要专注于你的应用程序，并在本地 `IDE` 中进行所有重构。通过使用 `val` 等概念，有一些技巧可以让代码更具模块化。然而，纯 `Java` 的实现仍然提供了所有功能，而且毫无头疼。

至于 `MVC` 框架的其他部分，`Spring` 和 `MVC` 只是另一个 `Java` 库。它们有很多相似之处。`Spring MVC` 基于 `JPA` 框架，`JPA` 最近用 `Scala` 重写了，可以提供比 `Java` 更具声明性的 `API`。`JPA` 允许系统根据实体对象中声明的列来解析列和列集。

从 `Scala` 提供的函数式编程概念来看，它可以被视为 `Scala` 语言的泛化。语言本身没有根本变化，它提供了库来实现命令式概念，如 `setter`、谓词等。然而，堆栈中添加的每一层都会为代码增加抽象和功能性元素。因此，用功能概念扩展应用程序的主要方法是在现有的 `Java` 应用程序中使用 `Scala` 代码。

本质上，`MVC` 模式是 `Spring` 应用使用的一组方法，以便你可以启动应用程序并将你想要暴露的主要参数传递到 `MVC` 结构的组件中。`Spring` 汲取了你可以在 `JSF` 中找到的模板系统，以及一些扩展了系统默认行为的特定注解，并生成了一个设计接口，你可以使用任何你喜欢的约定来实现它。

例如，你可以将视图（`View`）定义为模板，将其作为参数传递给构造函数是完全有效的，或者使用一段特定的代码作为视图来定义视图并获取一个可以操作的视图实例。实体（`Entity`）可以是一个由你实现的类，也可以是一个 `Lambda` 表达式。

你必须记住的是，`MVC` 模式仍然是一种模式，但它是 `Java` 编程语言中最常用的模式之一。因此，每当你在代码中看到它时，它可能是一个框架的一部分，该框架被定义为开发 `MVC` 结构的一套规则。

值得注意的是，`Spring MVC` 并不并不我在文章开头提到的 `MVC` 概念，即将模型（`Model`）、视图（`View`）和控制器（`Controller`）分离。其核心思想仍然相同：视图只是创建一个视图的便捷 `API`，它实现了 `MVC` 结构中的组件；而控制器是继承自 `Spring MVC Controller` 类的类。模型是 `ViewModel` 接口的实现，控制器是 `Controller` 接口的实现。`Spring MVC` 的问题在于它的扩展性不是很好。它是一种“适用于小型项目”的模式。如果你正在处理一些非常小的东西，比如一个小网站之类的，它是一个极佳的选择；但如果你想将该 `Web` 应用部署到生产环境，那么你就需要考虑其他模式。

这就是为什么我在开头建议，如果你在开发一个大型 `Web` 应用，请使用诸如响应式编程等 `OOP` 模式。响应式编程是一种面向对象的范式，涉及建模响应式行为的元素（因此，它通常与响应式编程结合），并允许你对真实世界建模，即具有许多异步元素和大量数据流的实时系统。响应式编程是实时系统建模的一种很好的方法。

实时是一个抽象概念，但响应式编程确实帮助你能够在 `OOP` 环境内建模的抽象概念集中，具备处理响应元素的能力。实时性已经存在很长时间了，响应式编程可以用于任何 `OOP` 环境。其中一个例子是数据库，你可以实时读取数据并实时修改这些数据，同时保持状态尽可能静态。另一个例子是你可以使用 `REST` 以及更通泛的事件驱动编程。你可以将实时性建模为一种无状态函数式编程范式。多年来，我看到许多从数据库启动并使用各种响应式技术的项目。

大多数，响应式编程帮助你以声明式的方式应对实时系统和响应元素，这允许你以声明式的方式对事物建模，然后编写代码来处理这些响应元素并处理对时间敏感的元素。

如果你考虑当今正在开发的典型 `Web` 应用，这基本上就是你对响应式编程 `Web` 应用时所会做的事情。我将描述一个简单的响应式编程 `Web` 应用作为一个案例研究，你可以在下一节中进行学习。

## Web 应用中的响应式编程 - 真实案例

早些时候解释过，如果你有一个响应式的软件问题，你通常需要编写代码来处理响应元素，例如发起 `HTTP call`、从数据库读取数据、处理请求参数的请求、发起 `HTTP call` 等。响应式编程通常还涉及大量数据结构，包括结构性和动态。这整套数据结构（我们称之为响应式数据库或响应式缓存）帮助我们对系统的响应性建模。

我将使用 `Linux` 操作系统的例子来解释如何构建响应式数据库。对我来说，`Linux 内核`是 `Linux` 操作系统中最趣的单一组件。`Linux 内核`中的大部分系统只是我们在其他项目中构建的极其复杂系统的简单示例。这就是为什么内核是响应式系统的经典案例，特别是响应式系统的示例。

`Linux 内核`的核心完全在于数据流，特别是关于性能。让我简单地说明：如果我们有一组用户连接到我们的网络，我们需要以一种非常高效且响应迅速的方式处理用户连接的涌入，其中一种方法是使用微内核，让网络栈管理用户连接以及对如网络接口等硬件的访问。

我喜欢这种使用微内核让网络栈管理用户连接的想法，但我对内核最喜欢的部分是网络栈。每当我打开电脑时，我都会在硬件层连接到 `Linux 内核`，并连接到内核提供的所有服务。

对于用户会话，我以非常特定的方式连接到主内核线程（`CPU`），因为我还需要能够与其他用户共享我的设备并共享我的部分 `CPU`。`CPU` 的访问由硬件层的内核管理。例如，如果我有显卡驱动程序，我可以直接从 `CPU` 使用图形设备。如果没有使用显卡驱动程序，我也会通过 `IPC service` 连接到 `CPU`。

然而，为了让会话连接到网络栈并从网络读取数据，我必须连接到内核。这意味着我必须绑定特定的 `CPU`。这可以通过套接字编程或向内核注册的锁来实现。你可以看到内核是一个响应式系统，允许我直接从内核创建会话，并具有这种非常有趣的读取内核的能力。这就是为什么我倾向将网络栈作为响应式系统的核心。

在构造函数中，我们注册了 `Reactive` 类的初始状态以及所有我们可以与数据库交互的必要端点。`Reactive` 类还包含一个新的 `DefaultExecutionListener`，负责处理事务过程。

我们调用 `execute()` 方法来启动事务并处理结果。如果成功，则完成事务。如果失败，我们捕获异常并调用 `stop()` 方法，该方法会信号终止事务。

为了处理数据库连接详情，我们注册了一个新的默认执行监听器。当连接处于激活时，我们在 `onTransactionSuccess` 方法中调用它们来执行事务。如果失败，我们捕获异常并调用 `stop()` 方法，信号终止事务。

在处理完数据库连接详情后，我们拥有了数据库连接的引用。我们可以使用 `connect()` 方法将其注入到反应器中。

```scala
class DatabaseConnector extends Reactive.class {

  def connection: Connection = new DefaultConnection("testdb")

  def reactor: Reactive = new DefaultLoader

  reactor.register(

    new DefaultExecutionListener {

      override fun onTransactionSuccess(executor: ExecutionContext, result: ExecutionResult) {

        transaction.finishExecution(result)

      }

      override fun onTransactionFailure(executor: ExecutionContext, result: ExecutionResult) {

        transaction.failure(result)

      }

      override fun onStop() {

        dispatcher.stop()

      }

      override fun onStart() {

        reactor.start()

      }

      override fun onFinish() {

        reactor.stop()

      }

      def onSuccess(transaction: Transaction): ExecutionResult = transaction.transactionCompleted(result)

      def onSuccess(transaction: Transaction): ExecutionResult = transaction.transactionStarted(result)

    }

  )

  // 构造函数需要将连接添加到网络中，以便我们

  // 在之后注册其他的反应器

  def connectionConnector(db: DatabaseConnection) = DatabaseConnector(db)

}
```

我们定义了一个新的连接监听器来注册连接，该连接用于连接数据库并将其挂载到 `Reactive` 类。反应器类成为所有对数据库调用的接收者。

你只需要创建一个带有计时器的新 `JobBuilder`，该计时器在后台运行，并在计时器过期时杀死主线程。

```scala

val reactor = reactor()

reactor.run(job)

```

这样我们就消除了对外部线程的需求。所有的重型工作都在 `reactor` 类内部完成。

`Run` 是绑定到 `onStart()` 方法的 `ExecutionListener`。在我们的 `run` 方法中，我们调用 `Upgrade()` 方法替换现有的接收者。

在运行实际业务逻辑时，反应器简单地调用状态转换器 `onUpdate()`。我们在执行数据库事务时，对数据进行任何操作。

## 第 5 章：Java 语言工具是什么？

假设你有一些可用的语言结构和特性。其中某些（如内联或纯函数构造）将带来更好的性能，而某些功能提高了 Java 的安全性、可读性或开发生产力，但并非在所有情况下都有效。此外，某些用法使得任务变得困难。

这些问题导致许多开发者以不同的方式使用 Java。对于某些人来说，工具并不重要，但对另一些人来说非常重要。例如，有些人使用 `Eclipse`，另一些人使用 `IntelliJ`，问题在于 `Eclipse` 或 `IntelliJ` 在某些方面是否更好。JVM 本身也是如此。有些人以严格单线程的方式使用它，而其他人则倾向于使用 JVM 级别的优化或 JIT。就像许多事情一样，没有“最佳”方法，只有产生不同结果的方法谱。理解特定问题工具之间的差异，以及理解涉及的权衡，对于你的案例做出最佳决策至关重要。

我们接触过的多数开发者都属于“太简单”阵营，即少数几个工具可以“开箱即用”，无需任何配置（或者至少比所需的要少得多）。一些开发者属于“不简单”阵营，他们必须对功能进行配置才能使其变得有用（例如打印、查询以及许多其他操作）。还有一些人属于“没用”阵营，由于任务不适合任何现有的工具，这些工具完全没有被使用。

## 工具运行良好吗？

将使用以下问题陈述来评估工具的有效性：

“标准 `JVM` 的目的是允许我们以单线程、低延迟的方式运行 Java 代码。因此，在通常情况下，我们希望 `JVM` 以单线程、低延迟的方式运行。然而，我们的一些项目可能更适合多线程、高延迟操作，例如从网络下载图像的 Web 应用。这些项目将受益于线程的使用，而 `JVM` 可能会赋予我们以多线程、高延迟的方式运行这些项目的能力。”

当然，上述陈述包含许多子部分，每个部分都有不同层次的抽象。通常情况下，我倾向于从低级抽象开始，然后逐步向上，并在过程中考虑真实开发者的关注点。换句话说，这是对真实开发者想法的非常粗略的近似，而不是一套硬性需求。

## 工具提供了必要的配置吗？

要让一个工具有用，它必须提供足够的配置以供使用。这可能是最让大多数开发者感到困惑的地方，因为配置工具有许多方法。

一种方法是对开发者如何使用工具做出假设（例如，“所有开发者都是同的，所以让我们配置工具在所有开发者中都以相同的方式运行”）。也就是说，如果你的目标是为你的工具提供一张“配置映射”，那么你很可能会失败。

另一种方法是采用开发者使用工具的典型方式（例如用户层、通过命令行进行配置等），然后反向推，设计一种能够按照用户当前使用工具的方式运行的工具。也就是说，确保工具运行在 `JVM` 上，而不是运行在某些其他处理器上（Java Web Start 并非如此）。

这引出了另一个我称之为“模式匹配”的概念，因为它涉及到项目/应用程序与特定配置的匹配（可以是特定的 `JDK` 版本，甚至是特定的 `JVM` 配置）。这可以使用与项目或应用程序对应的代理配置文件来实现，通过解析这些文件来确定哪些配置文件是合适的。（这篇文章对模式匹配有很好的介绍。）

另一种方法是确保工具为每种支持的配置都包含一个配置文件。然而，这是一种繁琐的方法，对于许多只有单一配置的小型项目来说并不实际。此外，混合配置文件也存在一些顾虑：如果你需要在同一个 `JDK` 版本之间切换，但你有两个不同的配置，会发生什么？配置文件也是不同的，所以你无法在项目之间复用配置文件。

因此，问题是：如何为给定的配置提供正确格式的配置？

## 配置组织得当吗？

有时，你必须关注细节。你需要一个文件来存储配置，并且需要确保该文件包含正确的选项。同时，你希望配置是易读的。

## 配置是自定义的吗？

当然，如果配置不易修改，工具的用途就有限了。配置本身呢？你希望它是可编辑的吗？（Java Web Start 无法做到这一点。）

最后，Web Start 的配置略有不同。在抽象层次方面，有许多方法可以配置工具使其在 `JVM` 上运行。然而，Web Start 在如何创建该配置提供了一些灵活性：它支持一种原生配置解析器，并可以修改程序以运行在不同的 `JVM` 上（例如在 Oracle 支持的 `JVMs` 之间）。

因此，Web Start 为开发者在创建配置方面提供了更大的灵活性。

## 未来

有许多方法可以定义工具的配置模式（schema）。某些采用“配置映射”方法，而另一些则使用配置文件模式。但有一点是可以肯定的：任何提供在工具中创建配置能力的工具，都需要为特定配置提供正确的格式，而正确的格式随工具和配置而异。（我还没有研究如何为仅允许你创建单个配置的某个工具提供配置支持，但这绝对可能的。）

作为 PostgreSQL Console 持续开发的一部分，我们创建了一个原型解决方案，为 `PostgreSQL`、`JRockit` 和 `Percona XtraDB` 的配置文件提供支持。（我们将其命名为 Percona XtraDB Console。）

与其为 PostgreSQL Console 开发类似的解决方案，在我们的下一次大发布中，我们将专注于扩展用户编写的类型与现有提供程序配合使用的能力。

第一个建议是将类型参数添加到由配置创建的客户端的 `pathname` 属性中。该类型名称随后必须以架构文件的类型名称为缀，这样如果你想创建一个与类型中配置不同的新类型，你就需要指定包含该配置类型的文件。

然而，这将要求开发者对他们想要使用的类型更加明确：他们需要为配置类型指定一个值。

另一个选项是扩展 `System.IO.Configuration` 接口（它是为 .NET 4.6 设计的）。该接口提供了创建类型的方法，只要它们符合 `System.IO.Configuration.Types` 接口（由于 `System.IO.Configuration.Types` 不是 `System.IO` 类型，它需要内置）。因此，我们可以在 API 中提供一个接受 `TypeBuilder` 的模块，它提供了创建新类型的声明语言。类型构建器将返回一个 `TypeBuilderValue` 类型，它是访问其配置属性的简单封装器。

未来的目标是将配置类型添加到提供程序的命名空间中，使其成为工具内置的一部分。

另一种方法是为配置文件尝试类似的解决方案，允许开发者在工具的“config”目录中创建一个文件，并使用单行将其导入工具，而不是像现有配置那样需要多行。

因此，我们正在调查提供如下内容的可能性：

```scala
# 在文件 "settings" 中创建一个新类型 . {"ConfigFileType" . {"configFilePath" }

# 在工具提供程序 "TypeBuilder" 中定义的类型构建器中导入该类型 . new "ConfigFileType" . configFilePath {"configFileType" . {"configFilePath" }
```



但是，正如我在开头提到的，这引发了关于如何命名这些不同类型的顾虑。这种想法与为工具中提供的类型提供一组公共类是一致的，从而提供创建遵循相同 API 的不同类型的能力。例如，可以有一个符合`Base`类的类，一个符合`ConfigAttribute`类的类，一个符合`ConfigAttributeConstraint`类的类，等等。

当然，我们不能将此主意用于`System.IO.Type System`的`TypeBuilder`接口。因此，我们面临选择：要么扩展`System.IO.Type System`类（类似于从`Connection`变为`ConnectionBuilder`时的扩展方式）以支持更多类型，或者我们可以添加一种特定的设计，要求开发者显式指定他们正在使用的类型种类。

## 结构改进

讨论过程中出现的另一个大话题是对`TypeBuilder`接口进行结构性更改的能力。目前，这些更改仅支持`WFT`和`TypeProvider`接口，但我们希望将此支持扩展到许多其他类型，例如`WCF-type providers`。

现在，如果用户选择替换内置类型，他们被迫从`TypeBuilder`接口中删除它。要使用未在接口上定义的类型，他们需要提供额外的构造函数参数。

当你与`WCF`提供程序工作时，这是一个很好的功能，但当你有一个在工具中已经存在的类型时，情况就会变得复杂。例如，我们可能有一个名为`CustomType`的类型，它在`TypeBuilder`接口中实现，但该类型已经在`WCF`提供程序中定义。这可以被视为一个独立的“类型”并应该被这样对待。如果用户更改了`TypeBuilder`接口，他们需要修改正在使用的类型，因为他们的构造函数参数将变得不同。

那么，针对这个问题可能的解决方案有哪些？其中一个想法是更改`TypeBuilder`接口，不再为当前接口上不存在的类型提供构造函数，而是为涉及的类型提供一个构造函数，其方法签名允许不同的类型。

另一个想法是实现该类型的构造函数，使其为它可以被用的所有接口提供构造函数，然后用户就能执行正确的操作。

在学习`Java`编程时，你应该考虑以下几个问题：

## 什么是常量？

常量是一个整数或浮点值。它没有单一的可能值。如果你有一个浮点数，你应该预期它有一个单一的可能值。例如，在`Java`中，浮点数被表示为 32 位整数，而两个可能的值是`2.71828182845e-18`和`2.71828182845e-15`。整数被表示为 32 位浮点数，而两个可能的值是`0.5`和`1.0`。

当你开始学习`Java`编程时，记住这个硬的事实：数字永远是数字。

## 最大的质数是多少？

它是`253`。

换句话说，最大的质数是`253`。

你还应该知道，你可以使用带有许多不同非常量值的`Integer`字段。它们存在于每个类中，且不应该被使用。

你还应该知道设计对象有很多方法。如果你以后改变了主意，可以更改字段的默认值。例如，你可以将`Int`中字段的默认值从`0.5`改为`1`，或者将其更改为`2.71828182845e-15`。

## Java 中的常量(T) 是什么？

常量被作常量的变量，该变量与常量同名。

示例：

```java

    static Integer constant1 = T;

    static Integer constant2 = T;

    private int maxValue;

        } else if (value > maxValue) {

        } else if (value < minValue) {

            value = value.toString();

        } else {

    public static void setMaxValue(T value) {

        maxValue = value.toString();

    }

    public static void setMinValue(T value) {

        minValue = value.toString();

    }

    public static int getValue() {

        return value;

    }

    public static T getValues() {

        return values;

    }
```

# 参数化类

## 基础定义

```
public ConstInt value;
public Comparable<T> valueComparator;
public T getValue() { return value; }
public static T getValues() { return values; }
```

重要的是，当你在参数化类中创建参数声明时，你应该拥有不同版本的参数。

在第一个版本中，参数的类型应该是 `T`。

在第二个版本中，参数的类型应该是 `ConstInt`。

这里是一个示例：

```java
public class ExampleParameterizedInteger<T> {

    public static T getValues() { return values; }
}
```

## 参数化类包含哪些方法？

在参数化类中，你必须声明一个或多个方法。在这个类中，有两个方法声明：

```java
public void compare(T value, T comparator) { if (value == comparator) { return; } }
public void returnValue(T value) { return value; }
```

`compare()` 方法比较参数值与 `comparator` 中参数的值。

`returnValue()` 方法返回参数的值。你可以使用参数引用作为第一个参数调用 `returnValue()` 方法。

## 你是否必须创建一个类并使用参数化类的参数来实现方法？

不需要。有一个名为 `ParameterizedMethod` 的类，在其中有一个名为 `ParameterizedMethodBuilder` 的类，你可以用它来参数化你的方法定义。

## 如何向参数化类中添加 `ParameterizedMethodBuilder`？

`ParameterizedMethodBuilder` 类实现为 `ServiceProvider`，你可以将 `ParameterizedMethodBuilder` 注册到参数化类中。这里是一个示例：

```java
public class ExampleParameterizedMethodBuilder {
    public ParameterizedMethodBuilder(ServiceProviderParameterizedMethodBuilderBuilderProvider) {
        this.ParameterizedMethodBuilderProvider = ParameterizedMethodBuilderProvider.create();
    }
    public ParameterizedMethodBuilderBuilder create() {
        this.ParameterizedMethodBuilderProvider.register(new ParameterizedMethodBuilder(NewParameterizedParameterizerProvider.class));
        return this;
    }
}
```

`ParameterizedMethodBuilder` 是 `ServiceProvider` 的实例。在参数化类中，没有 `ServiceProvider` 的实例，因此 `ParameterizedMethodBuilder` 使用参数化类的服务提供者。

## 弱参数化类和强参数化类之间的区别是什么？

区别在于参数化类是“继承”自基参数化类，而不是“拥有权限”。如果你使用一个弱参数化类，该参数可以被其子类修改。

例如，在 `CustomType` 类中，你可以更改参数的值使其不起作用。如果该参数化类是 `WeakParameterizedType<T>`，它仍然会继承自基类，因此你仍然需要像下面的示例那样调用方法：

```java
public class CustomType<T> {
    public WeakParameterizedType<T> (T value) { this.value = value; }
    public WeakParameterizedType<T>(T value, string name) { this.value = name; }
    public WeakParameterizedType<T>(T value, int number) { this.value = number; }
    public WeakParameterizedType<T>(T value, bool equals) { this.noEqual = equals; }
    public WeakParameterizedType<T>(T value, int noNumber) { this.noNumber = noNumber; }
    public T getValue() { return value.getValue(); }
    public WeakParameterizedType<T>(T value, string name) { this.value = name; }
    public WeakParameterizedType<T>(T value, int noNumber) { this.noNumber = noNumber; }
    public void setValue(T value) { this.value = value; }
    public void setNoEqual(bool isEqual) { this.noEqual = isEqual; }
    public int getNoEqual() { return noEqual; }
    public int getNoEqual() { return noEqual; }
}
```

在开始之前，有一点很重要：Java 编程库（有时称为 Java 库）只是 Java 语言的一部分。我们应该理解它们以及它们如何帮助我们，但绝不应该将它们视为编写代码的替代方案。解决完这个问题后，以下是你在使用库和通过库编写 Java 程序时需要了解的最重要事项。

## 兼者的优势：用于 Java 编程的库

当你开发程序时，Java 库为你解决各种问题提供了一个极佳的选择。这太方便了！特别是当你需要反复解决许多相似的问题时，这真是一种解脱。它们简化了编写程序的工作。这一切都是因为它们替你处理了大部分细节：你只需要编写自己的程序，剩下的由它们来处理。

它们可以让你免于编写许多繁琐的任务，例如安全检查，或者需要进行繁琐类型检查才能正确运行的代码。

## Java 库的众多用途之一

然而，在开始使用 Java 库之前，请确保你已经熟悉它。Java 库有很多。有些（例如处理 SQL、XML 和 JSON 字符串的）针对特定编程语言非常特殊。另一些（例如由 Java 编译器本身提供的）通常带有大型代码库，并为普通 Java 程序员提供许多实用程序。

库的妙之处在于，它们允许你为项目编写所需的任何代码。你不需要像自己独立完成时那样担心管理和维护你的代码。你只需要几行代码就可以为库添加新功能。你最不想担心的就是发现你正在使用的某个函数是库中新增的，或者它最近是否更新过。库会替你处理这些问题！

此外，你可以轻松使用一个库，而无需从头开始编写任何内容。使用一个良好的库，你甚至不需要写一行代码就能让它运行。这也是一个非常实用的特性。

## 并不那么易用：库需要一些精力

库的另一个特点是它们并不容易获取。它们通常要求你创建一个并注册一个完整的项目才能使用。有时它们有不同的注册方案。但这样一来，你可能需要为你使用的每一个库编写不同的、自定义的代码。使用某些库（尤其是复杂库）所需的任务可能看起来令望而畏畏。

使用库的另一个困难方面是它们可能会有不同的接口。你必须研究它们如何工作、如何使用它们以及你可以用它们做什么，以便充分掌握它们提供的实用性以及你程序的最终实现。

最后，某些库包含了大量的代码。如果你使用它们，就必须花时间理解它们的所有部分以便使用。更糟糕的是，有时库与库之间存在不兼容性。这通常意味着你可以在不进行更改的情况下无法复用或集成库。这可能更加令人恼恼，因为你必须修复由此创建的程序。

## 使用库时你会面临哪些问题？

如果你创建一个对象数组，数组中的某个项可能与数组中已有的某个项具有相同的名称。如果你随后修改了原始项，你就必须更改数组中的引用。

这样做的问题在于，一旦你修改了其中一个项，整个数组都会发生变化。因此，基于对象的数据结构的可扩展性低于基于数组的数据结构。

此外，存储大型对象所需的空间大小通常是许多大型数据结构的限制因素。如果你想存储大量的大型对象，可以使用如图、哈希表或矩阵等大型数据结构。

### 基于数组的 (Array-based)

基于数组的对象在内存和磁盘空间方面可能非常大，并且存在很多效率性问题。解决这些问题的方法之一是使用缓存，缓存应该将所有数据都保留在内存中。你可以将缓存放在一个变量中，然后在需要数据时从缓存中分配一个对象。

### 基于结构体 (Struct-based)

基于结构体的数据结构允许你定义一个结构并将其某些成员变量设为私有。然后，每当你需要某个成员变量时，你通过其接口提供它，这样你只需要将其应用于数据结构，而不需要将其传递给所有成员。需要注意的是，这有时更适合该结构，但如果你想保持结构私有并允许每个成员独立于整个结构进行更新，则不应使用它。

换句话说，你可以拥有如下的`Struct`：

```
struct Patient { String name ; Integer age ; String address ; } ;
```




在这种情况下，你不需要担心成员会从一个类传递到另一个类，但它们仍然可以通过其接口可用。

基于结构体的结构的另一个优势是，它们允许你向数据结构添加一个可选成员，该对象通过其接口暴露该成员。因此，你可以拥有结构化数据结构的多个组件，这意味着它们可以比数组更小。

基于数组的数据结构提供了非常好的性能，特别是当你拥有不需要经常更新的大型对象时，例如大型数据库或映射（maps）。

Java 有一种非常有趣的数据结构叫做哈希表，它用于大规模面向对象的数据库。但在 Java 中，你需要将其实现为一种面向对象的数据结构，这意味着你需要确保数据结构的每个属性都与其他任何属性隔离开来。此外，如果属于该属性的值发生变化，你就无法对哈希表类进行任何更改，这使得开销非常大。

简而言之，每种数据结构都有优缺点，但我更喜欢数组而不是哈希表，而且数组速度更快。

## Java 9 传递数据类型

Java 9 引入了一个新类型，它与 `Date` 相关。它被称为 `Time`，是一种允许你创建和管理日期的传递数据类型：

```java
Time new = new java.util.Date(new java.util.Calendar().getTimesUnit()); Time setCurrentDate(Time new); Time yesterday = new java.util.Date(new java.util.Calendar().getTimesUnit()); time = new java.util.Date(new java.util.Calendar().getTimesUnit());
```

如果我们想在 `Time` 中存储内容，可以使用静态的 `getCurrentDate()` 方法将其格式设置为我们想要的任何格式：


### 什么是 JPA 3.0

JPA 3.0 的名称是"Entity Framework 1.0"，尽管这并不是一个为了将`Entity Framework 1.0`迁移到`JPA`而过度努力的任务。它可能是为了解决`Entity Framework`所名的问题而付出的最大长期努力，以及如何为使用`JPA`开发的实体与数据库后端之间建立最佳映射。

从上述描述中可以看出，将`Entity Framework`真正迁移到`JPA`存在许多困难。从我看来，`Entity Framework`是数据库集成可用最佳选项之一。因此，努力的方向并不是开发一个非常昂贵的`Entity Framework`到`JPA`的迁移。其目标是开发一个可以通过`JPA`扩展轻松实现和扩展、且门槛较低的库。

`Entity Framework`使用 HTTP 协议来暴露其功能。问题是`JPA`规范没有提供标准的方法让 HTTP 客户端与`JPA`接口。为`JPA`客户端提供 HTTP 客户端的标准方法是通过使用 Web 服务器。有几个非常流行的 Web 服务器，但它们各自也有缺点。

基于 JavaScript 的精简版`Hibernate`是`JPA`客户端 API 的标准实现。它为任何数据库提供客户端功能。`Hibernate`的原始版本基于更早的、过时的`Hibernate`版本的功能。其他主要的`JPA`实现是`JBoss EAP`和`Grails-JPA`。它们为每个数据库提供客户端功能。

已经有一些将 HTTP 客户端标准化到`JPA`的努力，但它们目前还不够广泛，不足以对`JPA`领域产生实质影响。可能还需要另一代`JPA`实现才能变得足够广泛，从而使“标准”客户端库广泛可用。

`JPA` 3.0 中的 API 变化是为了提高`Hibernate`与`JPA`客户端之间互操作性和可靠性的努力结果。

### 注意事项 #1

这一部分更多是一个警告，而不是真正的抱怨。我并不是声称`JPA`委员会的每位成员都是坏人，或者`JPA`委员会的每位成员都是邪恶。`JPA`社区的好人确实多于坏人。

一位`JPA`专家说`JPA`规范最大的缺陷是它“充满了复杂性”。我问他的“复杂”是什么意思。复杂性是来自涵盖每个实现细节中所有可能的变体，还是来自每个客户端代码中所有可能的变体？他说`JPA`太复杂了。然而，我不信在使用的`JPA`实现有很多（或至少几乎所有的实现）是这样复杂的。

### 注意事项 #2

对于“真实”数据库的定义存在一些分歧。有人说`Oracle`数据库是真实的数据库，而另人说`DB2`数据库是真实的数据库。这很遗憾，因为`DB2`和`Oracle`都支持`JPA`。有大量使用`JDBC`的`JPA`实现。问题是，它们通常不是作为独立或集成的支持提供的，通常只是被用来绕过 Java 社区缺乏良好支持的`JPA`实现。例如，一个`JPA`实现`JSR 341`提供了一个应用程序工具包，为每个注册的应用程序提供了一套执行`JPA`的机制。这种方法有两个问题：首先，它对大多数用户来说可能太复杂了；其次，即使用户找到了使用`JPA`工具的方法，要与支持非`JPA`接口的第三方工具协作可能需要大量工作。这并不没有支持非`JPA`接口的第三方工具，但它们非常少。

许多人声称`Oracle`只有在其他厂商支持时才会支持`JPA`。我认为这有点胡扯。我们需要的是使用标准`JDBC`接口的`JPA`实现，因为许多第三方工具支持`JDBC`接口。当然，某些因素使得这变得更加困难。`JPA`工具包为每个数据库实现了接口，而不只是`Oracle`或`DB2`。工具包本身是私有的，因此对于选择实现它的每个厂商都是私有的。最后，工具包通常包含大量功能，例如与大量对象通信的能力。协调这些各种需求通常非常困难。

随着许多人对`JPA API`以及其他问题的埋怨，我希望我们很快就能看到一个标准且支持良好的`JPA API`。然而，自`JSR 343`（又名`JPA 2.1`）提交以来已经过去了一多年，而我们仍然处于开发的初阶段。由于我所使用的多数工具都不提供`JPA support`，我怀疑在大多数开发环境中，`JPA`工具包是没有任何替代方案的。

# 第 15 章：什么是手机版 Java？

手机版 Java（Java for phones）是开源、免费的并由 Sun 公司开发。Sun 公司已明确表示，一家名为 Maturity in Telecommunications (`MT`）的独立公司将负责此项目。

对于 Java 社区而言，策略是在所有主要平台和功能尺寸上获得单一的运行时和应用平台。其目标是在所有不同形式的手持设备和网络笔记本/智能手机产品中创建统一的用户体验。

## 手机版 Java 将如何工作

根据官方文档，手机版 Java 基于 `Java EE 5`。因此，经典的 `J2EE` 应用服务器也受支持。不再支持其他传统的服务器开发库；任何平台的内存消耗和复杂性将显著降低。

手机版 Java 用 `Java` 编写，这意味着代码将可以到任何 `Java 1.5` 语言变体，包括 `Java 6`。

分布式应用程序使用通用的 Java 框架编写。这意味着可以使用现有的 Java 应用服务器。预计应用程序将在单线程中运行，并使用单独的线程进行高性能处理。

## 灵活的领域对象

基于 Java 开发移动应用程序有多种面向对象的方法，但基本前提是构建单个原生的或分布式的应用程序，这些程序应使用相同类型的系统，可以访问底层结构，并根据需要利用语言/库 API。

不假设存在通用的语言/API。因此，使用了针对不同类型警报的意图（intents）和事件方法。手机版 Java 尚未支持此类功能。

## 手机版 Java 支持的平台

手机版 Java 针对三种不同的设备形态：智能手机、网络笔记本和智能卡。经过一些调整，它也能够运行在其他形态上，如个人数字助理（`PDA`）和手持游戏机。

### 手机目标

对于原生用户界面，该系统围绕 Java 构建，而来自手机制造商的原生接口是原生布局和设计的起点。这意味着只要编写代码时尊重了预期的目标设备，任何预先存在的 Java API 都应该能够正常工作。

Java 开发者需要为手机版 Java 开发原生代码，以访问手机功能。

“由于渲染原生应用 UI 以及读取/写入/编辑用户数据的功能无法从运行时的其他部分抽象出来，因此 `JDK` 本身的构建方式需要让 Android 团队无需为访问这些功能而添加任何特殊功能或更改，”Oracle 的 Elliot Schulman 说。

对于使用原生操作系统 API 的应用程序，使用了标准的 Android API。这意味着 Java 前端将能够利用原生栈提供平台集成以及用户界面代码本身。

### 手机 API 目标

手机版 Java 围绕统一 API 构建。由于该平台专注于支持原生代码，传统的 Java 语言将无法提供 API。

“现有的 Java API 在手机版 Java 框架中得到了支持，并达到了完整范围。因此，可以使用该 API 并利用现有库来提供丰富的应用程序功能，”手机版 FAQ 表示。

## 测试手机版 Java 平台

集成测试是测试手机版 Java 平台的方法。Oracle 的 Schulman 指出，构建使用手机版 Java API 的应用程序相对容易，并且测试应用程序将如何运行、API 接口如何以及手机版 Java 测试框架支持什么。

由于测试框架需要能够在 `JSR` 中自动注册，因此新的测试框架应该考虑到手机版 Java 进行编写。

网络集成测试也将非常重要。

“当应用程序提供给所有终端用户时，也将获得发现问题和对 API 提供反馈的机会，”Schulman 说，“因此在开发的每个阶段都应该对 API 功能进行测试。”

这意味着与原生代码集成也是重要的。“自然的选择是使用与手机版 Java 框架相同的 Java 库。”

再次，有机会编写新的测试框架来利用手机版 Java 框架。

“由于 `JSR` 针对的是终端用户而非开发团队，预计所有的 `APIs` 都不会被实现，”Schulman 说，“因此，在进行测试时，需要更多地关注使用框架来检测性能问题和逻辑漏洞。”

## 手机版 Java - 对 Java 意味着什么

根据 Schulman 的说法，`API` 有可能移植到其他平台。这为编写目标移动设备的应用程序提供了一个绝佳的机会，而无需迁移 `JVM`。

他还注意到，通过实现额外的封装器，可以相对容易地使用手机版 Java 进行测试。然而，他不认为这会形成一个巨大的用户群体。“目前，`Android` 社区有很多人正致力于将 `Java` 引入其他设备，尤其是手机手机。”

## 那么 Java 开发者会对手机版 Java 感兴趣吗？

Schulman 认为，开发者使用的语言特性越多越好。手机版 Java 的主要目标是让跨平台的应用程序创建变得简单。他还指出，由于 `Java` 对正则表达式有强力支持，`JSR` 提供了一个编写无需编码程序的机会。

“`Java` 是一种涵盖大量领域的大型语言，而其中一个覆盖得不是很好的领域就是手机版 `Java`。最后，Schulman 指出 `JSR 310` 正在积极开发中。开发者可以期待添加到手机版 Java 中的语言特性很快可用。规范正在重写，某些提议的功能可能不会删除。”

## 什么是 Java 开发？

`Java` 是一种已经存在多年的软件语言。它用 `Java` 编写并由 Sun Microsystems, Ltd. 开发。由于它是设计为 PC、`Mac` 以及最近的 `Android` 和 `iOS` 操作系统开发应用程序，因此非常灵活。

## 它的优势是什么？

`Java` 是一种多功能语言，可以用于构建各种应用程序，包括 Web 应用、桌面应用、服务器应用等。由于其广泛的使用，它已被一些公司和企业组织采用。

开发者喜爱 `Java` 是因为它是一种强大的语言。由于它是基于 `Java` 的语言，开发者可以使用 `C`、`C++`、`C#`、`Clojure`、`ClojureScript`、`Kotlin`、`Go`、`Groovy`、`JRuby`、`Python`、`Ruby` 和 `Scala`。它还具有兼容性，因此使用标准语法将代码移植到另一种语言非常容易。`Java` 也非常安全，并提供易于集成的 Java 环境 (`JRE`)。

## 它的劣势是什么？

多年来，开发者在使用 `Java` 时遇到过一些问题。`Java` 对非 Java 应用也有影响，最近的 `Java 8` 也没有什么帮助。由于此，Java 开发者正在寻找其他日益受欢迎的替代方案。

此外，于 4 月发布的 `Java 9` 还没有准备就绪。Java 开发者已经等待了这个版本的发布多年，而在 `Java` 变得完全可用并适用于所有支持的版本之前，还有很漫长的等待。

## 我可以用 Java 使用什么？

许多语言可以用于开发 `Java` 应用程序。有些是原生语言，另一些是解释型。对于服务器、后端应用程序以及桌面应用也有不同的选择。

要开始，你可以从 Java 虚拟机 (`JVM`) 开始，它在 `Windows`、`Mac` 或 `Linux` 上运行 `Java` 的虚拟副本。从那里，你可以在虚拟机上运行 `C` 或 `C++` 运行时（例如 `Java 7`、`Java 8` 或 `Java 9`），以开发桌面应用。

对于服务器应用，你可以使用 `Apache Maven`，这是一个开源的 `Java` 应用程序框架，用于构建、管理和打包 `Java` 应用程序。它包含了开发 `Java` 应用程序的各种工具，如构建工具、依赖管理等。

对于 `iOS` 和 `Android` 开发，可以使用苹果的 `Swift` 或 Google 的 `Go`，它们都是用于开发服务器和桌面应用的解释型语言。

如果你需要构建 Web 端，可以使用 `Node.js`，它是一个开源的服务端 JavaScript 平台。

目前，`Java` 持续主导服务器和桌面开发市场。然而，关注目前流行的替代语言和框架是重要的。下面我们将查看一些最流行的替代方案。

其中一种语言就是 `Swift`。这种语言由苹果开发，包含了一些有趣的特性，如可选类型、包含 `check` 和 `assert` 等函数的标准库、一等函数语法等。它非常受欢迎，下载量超过 9 亿次，并且在服务器、桌面和移动开发领域变得非常流行。

## 函数式编程简介

在这节课程中，我将展示一下 `Erlang` 编程语言。然后我会展示 `BufHandle` 和几个函数，接着我会展示几个函数式风格的函数。

但这还不够，所以让我们从函数式编程的介绍开始。我将介绍以下术语，并会尝试解释清楚我们为什么要使用这些术语。

首先，我会说我们使用“函数式编程”一词是指“一元操作（Unary Operations）”。一元操作是在单个输入上进行调用并返回单个结果的函数。你把它说成一个词，然后解释它。你也可以把“函数式编程”作为泛指编程的术语。

有些人说：“我想用函数式编程来编程。”你可以使用某些纯函数式语言在 `Erlang` 中编程，或者你也可以在 `Erlang` 中编程，使用 `Haskell`、`Scala` 或任何你想要的语言。

但我想如果你想这样做，用纯函数式语言编程会更有效率。但如果你不想这样做，尽管可以使用命令式语言。我想用函数式语言编程会更有成效。

另一个要说的术语是“一元运算符（unary operators）”。我们通常把一个表达式看作 `AND` 或 `OR`。你可以把 `AND` 放在右边，或者把 `OR` 放在左边，它们都在右边。

但这些是不正确的；你必须不是 `OR`，而是 `AND`。所以你有一个表达式，然后有两个边。一边是 `AND`，另一边是 `OR`。

所以当你把 `AND` 放在右边，把 `OR` 放在左边时，你在右边得到一个新的表达式。所以你可以说这些是没有顺序的。它们实际上不在顺序上。正确的顺序是这样的：`AND OR`，`OR OR`。但你明白我的意思。

所以其他的术语也不正确。你可以把 `AND` 放在左边，把 `OR` 放在右边。它们不是同一个表达式；它是不同的。

在 `Erlang` 中，你不需要这些术语。`Erlang` 有一个特性叫做部分应用（partial application），它允许你把函数放在函数的一侧，把参数放在另一侧，然后主体将应用到该函数。所以如果你把 `AND` 放在左边，你将得到一个不同的函数。如果你把 `OR` 放在左边，你会得到该函数。它的工作方式简直很神奇。

你在对标准库的每次调用中都能看到这一点。你现在可能在屏幕上看到一些东西，例如标准库会给你一个 `list` 函数。它不在标准库里。但如果你不指定列表参数，它会给你一个所有列表的列表。如果你指定了列表参数，它会给你一个对的列表。所以你可以有一个两个列表的对，也可以有另一个对的对，然后再有另一个对的对对。你可以拥有所有的排列。这只是排列语言中的一种排列。

我目前正在使用的这个 Erlang 版本可能会包含一个支持列表函数和其他形式的偏应用函数的 API。所以你可能能理解为什么在 Erlang 中你应该使用命令式编程而不是函数式编程。函数式编程比命令式编程容易理解得多，但当你处理使用标准库的关键系统时，可能很难考虑到所有可用的选项型，以及如何将它们应用到你的问题中。而且，如果你处理的是关键系统，你可能根本不想去考虑这些。

## 命令式编程与排版（Typesetting）

在我看来，使用命令式编程的另一个好理由是，它允许你进行一种被称为“排版”（typesetting）的操作。你以某种方式编写程序，使其能够被编译，并被转换成一种可读的方式。Erlang 中有不同层级的排版，例如，编译器可以自动将你的程序转换为函数式语言。然后，你程序的不同部分（如方法），你可以用函数式语言来编写。

对于 `Java`、`C++` 或任何其他你可能使用的语言也是如此。编译器会识别出它是一门语言，并且程序的部分部分将在命令式语言中执行，而程序的其余部分将在函数式语言中执行。这就是动态类型编程。

## 动态翻译（Dynamic Translation）

你编写程序的方式使其能够被动态地翻译。也就是说，如果你用函数式语言编写了一个程序，并想在其中放入一些数据（比如一个或两个函数），那么这些数据将被自动转换为命令式语句或命令式数据结构，这样你就可以将它们插入程序的中间，看看会发生什么。然后当你运行程序时，你可以获得你放入的那些数据产生的结果。

所以如果你不怕动态排版，那么你可能应该考虑使用 Erlang，你的编程风格可能会发生一点变化。但你看不出来，因为你只是盯着屏幕看。

## Erlang 中的分布式计算

我要给出的最后一个例子之一是关于分布式计算的，即你有多个节点在相互作用。这与细胞自动机在分布式计算中使用的范式非常相似，因为在 Erlang 中，每个进程都必须与它有访问权限的所有其他进程进行通信。这非常酷。

这是一种全局的、分布式的并行计算模型，进程之间的通信可以在多个不同的层次进行。每个进程都可以访问它有权的所有进程，在每个通信层级上，都有被称为 `message`（消息）的东西，而这个 `message` 就是发送和接收数据的媒介。

例如，你可能在运行 Erlang 的同一台机器上有一个进程，它有两个不同的邮件列表，或者可能有一个邮件列表。它们都可以发送邮件或互相回复。你可以做很多事情。你可以建立分布式处理，这很棒。

你所拥有的、但许多其他语言不具备的功能之一，就是进程之间的通信。要以分布的方式编写程序，你必须学习如何以分布的方式编写程序。因此在上一个例子中，你必须学习如何编写分布式的 Erlang。

## 分布式类型系统（Distributed Type Systems）

你拥有的其他东西之一是分布式类型系统。Erlang 中的类型系统不仅仅是静态类型检查；它不仅仅是对标量进行静态类型检查。它也是动态类型化的。

换句话说，如果我写了一个程序并把它交给编译器，编译器会自动识别出我提供给编译器的代码必须能够处理该程序运行在一个互连的节点集群中的事实，并且节点之间正在相互通信。编译器必须知道如何识别这些节点何时接收到集群一部分节点发送的 `messages`。因此，也存在分布式类型系统。

通过分布式类型系统可以实现的酷点之一是对 Erlang 节点的动态类型检查。所以如果我熟悉我语言中的某种类型系统，并且我想要一个分布式类型系统，酷的地方在于我不需要做任何特殊处理。因为如果我有一个类型系统，并且我可以与分布式类型系统通信，我可以向分布式类型系统发送消息。它会对我给它的代码进行类型检查。所以这非常酷。

拥有分布式类型系统的另一个酷点是，如果存在一种分布式类型系统无法处理或不知道如何处理的类型，它会为你提供一些帮助。所以如果进来一个分布式类型系统尚未处理过的 `message`，那么这个 `message` 将为你提供一个提示，告诉该如何处理该 `message`，而且它会在你不需要阅读该 `message` 代码的情况下完成这一点。

这就是 Erlang 的另一个酷之处。当涉及到这些分布式类型系统时，它不仅仅是分布式类型系统；它还是分布式类型检查。所以如果你写了具有正确类型签名的代码并将并将代码发送到分布式类型系统，那么分布式类型系统提供的类型检查器将验证代码，但它不会自动对代码进行类型检查。它只会告诉你类型是什么以及它们来自何处。当你阅读代码时，你就会知道类型是什么。

很棒的一点是这些分布式类型系统确实存在。当你熟悉它们时，可以去了解。它们正在被构建中。所以我有一个开发这些系统的 IRC 频道，还有一个供开发人员讨论的邮件列表。所以未来充满了与 Erlang 协作的分布式类型系统。

## 通信协议（Communication Protocols）

这些都很有趣。但这里有一个问题。我正在构建一个分布式类型系统，而 Erlang 是一种分布式语言。那么我如何与我的类型系统通信呢？

Erlang 确实拥有一种协议。它被称为 `SIGTERM`。它非常简单。它说：“离开一会儿，因为你将被阻塞一段时间。”但它也有其他复杂的协议。其中之一是 `SIGQUIT`，当你对任何类型调用系统方法时，它会弹出该类型，然后告诉你该类型已经弹出。仅此而已。

这导致了一些严重的问题。第一个问题是，如果你在系统调用中包含过多的参数，当类型检查器处理到消息时，它必须查找参数。它必须检查系统调用中的所有参数，看看是否能找到它们。然后它必须查找消息中的参数并确定是否能找到它们。所以，如果你有一个很长的系统调用，它将会完全卡住。它不知道该去哪里查找，因为它在找到参数之前必须检查整个系统调用。而且它不会在消息中查找参数，因为它们找不到它们，而且在找到它们之前，它无法发出该消息。

第二个问题是，即使你调用了 `SIGQUIT` 并对它使用了 `SIGTERM`，它仍然会发出消息。所以，如果你有一个很长的系统调用，你会收到另一条消息，说：“类型检查器正尝试发送消息。它找不到它，但请让它发送。”这意味着对于非常长的系统调用，你必须重新运行一遍整个系统调用。你会收到两条消息：一条说“不、不、不、不、不、不、不、不、不”，另一说“让它发送”。所以这样做并不是个好主意。

我们发现，这些问题很难解决。我们解决它们是通过更改处理类型检查器的系统调用。处理类型检查器的代码（即块系统调用）被重写为使用不同的系统调用，该调用仅有一组不同的参数。它的参数组要简单得多。它表示：“我不会查找参数，也不会尝试发送消息。”但之所以不允许这样做，是因为这会导致内存泄漏。类型检查器正在使用的存储空间无法放入你进程的内存中。所以，如果你想使用类型检查器，就必须确保你只向它发送能够放入类型检查器使用空间的结构中的数据。这就是为什么你不能那样做。

然后，当你获得一个新类型（且类型非常大）时，你只需要说：“看，我完了。我需要解开结构来查看类型是什么。”然后你就可以发送它。这仍然是一个内存泄漏，但至少不是一个巨大的内存泄漏。

这就是我们为了让那种新类型的系统好很多而所做的另一个主要改进。

## 类型系统的职责

你有很多责任，包括处理类型检查器的一些问题。当然，你拥有所有类型系统开发人员都拥有的常规责任。你必须保持类型系统的安全。你必须使其免受各种攻击，免受任何冒充者或假装者的侵害。为了实现安全，你需要做很多事情。所以你必须做的事情之一就是让人投入一些工作，以便调用你的类型系统。

但你的责任还有另一部分，你还负责保护人们免受他们自己的伤害，尝试帮助他们写出更好的程序。这将比放弃代码的问题要困难得多，因为人们往往试图写出比他们能力范围内更好的程序。所以很多时候，你无法做很多你想做的事情。这是一种权衡。

我已经提到过类型检查器的存在了。如果你不想使用它，那么拥有类型检查器就没有意义。所以我们将类型检查器作为库提供出来，这样人们就可以他们理解的语言编写代码，然后他们只需要从代码外部调用类型检查器，这意味着你不需要运行它。

但即使不使用类型检查器，如果你只是在假设将使用类型检查器的前提下编写代码，你也必须有一种方法来确保你的类型定义都是有效的。类型检查的工作方式很大程度上是试图弄清楚你对类型的含义，然后你必须根据它对你的代码进行检查，这是非常昂贵的。

所以我们做的另一件事是，让类型检查器为你进行检查变得更加经济。如果你写了一个不匹配的检查，你就不需要担心那个检查。类型检查器只会确保它不执行操作。所以如果你得到一个检查且不匹配，你就不需要担心那个检查。类型检查器会直接忘记那个检查。这样你就有了一个程序，不再需要担心去匹配或检查你所有的类型定义。如果类型检查器对你正在编写的类型进行了某种分析，它就会识别出该语言对它没有问题。所以，如果你获得了一种比我们强大得多的类型检查器，那么它们将能够为你解决问题，即使你没有运行它。

因此，解决这个问题有两种方法。你可以写一个检查器。这并不是一个特别好的主意，因为那样你的所有代码都会变得非常脆弱，以至于你的检查器会崩溃，而你的代码仍然会崩溃。所以那不是件好事。但你可以写一些宏（macros），这要好得多。你可以在程序末尾写宏，如果它失败了，你可以确保类型系统捕捉到了它。

好了，现在我要谈谈另一件事，由于所有这些限制，我有时被迫要求重写某些东西，我不认为这一定是一件好事。我上次提到过这个，但我曾被迫重写了库的部分内容来修复一个错误。我确实重写了库来修复这个错误。我选择这样做是因为，我认为“你可以写出一个完全类型安全的程序，并且如果我看到任何类型错误就可以去修复它”这种想法根本不是真的。这不是真的，因为类型检查器仍然在那里，它仍然会检查是否有类型错误。所以当我们从尝试检查的类型中确实发现类型错误时，它会破坏那个检查。所以，你不应该使用类型检查来捕获类型错误。

原因是你实际上一直在试图捕获类型错误，如果存在类型错误，你的程序将始终失败。你可以做的另一件事是尽早失败，向用户打印某些内容，如果是类型错误，那将永远发生。用户将无法看到该消息。但同样，如果你不给用户打印的能力，那么它就不会显示那种类型的错误。所以我认为核心思想是，你应该只将类型检查作为异常检测器。这是因为我认为在各处进行类型检查是不现实的。正如我所说的，如果你想检查一切是否正确，你就无法编写整个程序、整个运行时系统。所以相反，我们需要做的是关注运行时系统所需的内容，以及让 UI 正确运行所需的内容。这样就能达到平衡。

所以你已经了解模式匹配是如何运作的。问题是，有时候你必须进行极其巨大的、极其巨大的类型检查，并且你需要开始对所有内容进行标注，这会让它变得非常脆弱。如果你使用模式匹配，就不需要标注所有内容，只需要标注部分内容。所以当你说对元组进行匹配（matches on tuples）时，我们只需要说这部分匹配元组，而那部分不匹配。现在我们可以有一个类型检查器，它说：“这是一个情况，其中部分是某种情况”。这使得类型检查变得容易得多。

例如，我有时想将对象放入数组中，这些数组将以分布式的方式在内存中保留。我想能够将任何类型放入一个哈希（hash）中，这是我管理它并放入这个数组的方法。这正是我之前尝试解决的问题。现在我可以使用这种模式匹配来实现，通过这种方式，我只需要对这些情况以及相关的案例进行标注。所以你不需要到处都有这个巨大的巨大的类型检查器。你只需要这个小小的模式检查器。但另一点是，在类型检查中，你拥有整个库，然后你有一个用于模式匹配的单一类。在模式匹配中你是无法做到这一点的。你不能说：“噢，好的。我有这个方法来匹配这个模式，它只能匹配系统的这部分。”如果你使用模式匹配，你只能匹配系统的这部分，而这是你唯一需要检查的情况。

所以它也很有用，因为当你有这些大型类型检查时，当你有这些要传输传输的类型检查时，我也发现这种匹配（matching）很有用。这算是一个独立的问题。我甚至不会告诉你们如何进行模式匹配，但这也是另一种方法。我认为它也符合我正在讨论的模型，即我们处理了大量的对象层级结构，而人们很容易忘记某一层或某一层，从而退回到类型检查中。

## 现实世界的工具

这是另一个我考虑很多类型签名的情况。我经常使用某些功能，我使用的签名类型是找到一个数字，然后我知道答案是什么，因为我得到了数字以及我所需的规范，或者我得到了数字并确切知道我该做什么。当你在大型代码库上工作时，那种签名通常运行得很好，人们通常会使用它们。所以你可以为此准备一个特殊类型，那是一个函数的模式。比方你有一个想要打开的文件，你可以放置类似 `file open` 的内容。那个包应该包含该函数的签名，然后当有人要读取那个文件时，他们就知道答案是什么。他们可以针对具有相似签名的文件运行它。你有一个具有不同签名的文件，你可以使用它，你只需要获取那种签名，并在你的代码中使用它。

但现实世界并非如此。在现实世界中，你必须确保人们使用这段代码，然后你还必须确保测试了这段代码，用真实的人测试这段代码，用真实的代码库测试这段代码。所以你必须更加灵活，并且对类型可能要更加小心，因为你不想破坏人们正在使用的类型。因此在现实世界中，拥有一个更灵活的类型系统也是一个好主意。

更灵活的类型系统意味着你可以创建更多使用不同类型函数的情况，这可能让他们更容易知道预期。但同时，你也可以让某人使用的真实函数变得更复杂，这样他们可以更确定他们得到的是他们应该得到的。所以你可以通过类型系统实现这一点，也可以通过其他限制人们访问特定功能的方法来实现这一点。我不会在这次演讲中讨论那个。
