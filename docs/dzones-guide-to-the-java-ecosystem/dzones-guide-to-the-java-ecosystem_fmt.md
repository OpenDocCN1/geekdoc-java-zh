
# DZone Java 生态指南

## 亲爱的读者

20 年——对于一种编程语言来说是一辈子，但对于一个平台来说却不是。今年，我们庆祝 Java 的 20 周岁，没有什么比发布 DZone 第一本《生态生态系统指南》更好的庆祝方式了。

我还记得第 10 届 JavaOne。当时充满了能量，人们相信 Java 能够履行它的使命，为开发者提供真正的“一次编写，随处运行”的机会。尽管在经济变化和互联网飞速发展的背景下，太阳微系统（Sun Microsystems）一直在努力在市场中找到自己的位置。而今天，Java 无处不在，它是企业和独立开发者的共同力量。它不仅仅是一门语言。在多年以后，Java 仍然是开发者最受欢迎的语言（Toodle），也是求职者最活跃的语言之一（Indeed）。

在 DZone 出现很久，我们就看到了 javalobby：这是一个由 Java 开发者组成的独立群体，他们渴望讨论这种需要内存管理并有如此强大组织支持的新语言。多年来，我们观察了自己对 Java 的愿景（在我们 Java 主题板块附近），但它仍然是我们网站最大的板块之一，也是网络上 Java 开发者的主要目的地之一。由于 Java 在世界中所扮演的角色，为本指南选择关注点是我们编辑团队今年做出的最艰难的决定之一。

希望你喜欢今天的指南，它侧重于理解开发者如何使用 Java 平台的趋势。你正在使用哪个版本的平台？你使用的是全 EE 还是只使用 Spring 这样的工具？相比 WebSphere，开发者更倾向于什么？这些统计数据——连同专家分析和行业领导者的文章——在《2015 生态系统指南》中等待着你。

## 核心研究结果

超过 600 名专业人士参与了 DZone 的 2015 年 Java 生态系统调查。以下是该研究的人口统计数据：

- 开发者（42%）和开发负责人（25%）是最常见的角色。
- 63% 的受访者来自大型机构（100 人或更多员工），37% 来自小型机构（100 人以下）。
- 绝大多数受访者的总部位于欧洲（44%）或美国（32%）。
- 超过半数的受访者（61%）拥有超过 10 年的 IT 专业人士经验。
- 我们调查了在组织内部使用 Java 的开发者。其他大型生态系统还包括 C#（31%）、C/C++（29%）、通用脚本（Universal Script，28%）、PHP（26%）、Python（26%）和 Groovy（23%）。

任何新应用程序使用 Java 6 或更低版本的情况极少，1% 的新应用使用了 Java 5 或更低版本。对于现有应用，Java 8 尚未赶上 Java 7；大多数组织（62%）仍在使用构建在 Java 7 上的应用，几乎一半（47%）仍在使用 Java 6 上的应用。受访者表示，许多开发者渴望随着 Java 的演进而跟进，但他们对重构已在旧平台上构建的应用程序感到犹豫（18% 的用户尚未迁移到 Java 8，且在未来 6 个月内没有使用 Java 8 的计划，无论新旧应用）。

## 02. Java EE 和 Spring 几乎平分

企业级 Java 社区中重大的争论之一是使用 Spring 和使用 Java EE。我们的调查显示，平台组件的使用非常接近，Java EE 略占优势。总体而言，58% 的人使用 Spring，67% 的人使用 Java EE 或更低版本，或 Spring 2x 或更低版本。每个版本的划分可以在图表中找到，但有趣的是，几乎三分之一（32%）的受访者使用它们。

## 03. JVM 语言拥有大量 Java 开发者份额

57% 的受访者曾用非 Java、基于 JVM 的语言编写过代码。Groovy（所有受访者中的 60% 是他们最常使用的语言），Scala（39%）紧随其后。接下来大的是 Ruby 和 Cloojure，超过 80% 的人表示他们喜欢使用它们。然而，只有 6% 的小组尝试过某种特定的 JVM 语言。只有 Groovy 和 Scala 有足够的用户来对用户意见进行显著观察。当被问及是否想在工作中使用这些语言时；45% 的 Groovy 用户表示愿意，55% 的 Scala 用户表示愿意。

# STREAMS API

`Streams API`为你提供了一个强大的工具来查询和操作你的数据。查看有关该主题的一些文章或书籍可以获得更全面的视角。为大数据构建流式查询与为普通操作构建同样有用。假设你有一本书列表，并想按字母顺序获取这些书的作者列表：

```java
private final Map<Customer, Customer> customers = new HashMap<>();

public void incrementCustomerOrders(Customer customerID) {

    Customer customer = customers.get(customerID);

    if (customer == null) {

        customer = new Customer(customerID);

        customers.put(customerID, customer);

    }

    customer.incrementOrders();

}

public List<Author> getAllAuthorsAlphabetically(List<Book> books) {

    List<Author> authors = new ArrayList<>();

    for (Book book : books) {

        Author author = book.getAuthor();

        if (!authors.contains(author)) {

            Collections.sort(authors, Comparator<Author>() {

                public int compare(Author o1, Author o2) {

                    return o1.getSurname().compareTo(o2.getSurname());

                }

            });

        }

    }

    return authors;

}
```




这种“检查元素是否在 `map` 中：如果不在，则创建它”的操作非常常见，因此 `Map` 现在支持了它：`computeIfAbsent`。该方法将第二个参数作为 `lambda`，用于说明如何创建缺失的项：

```java
public void incrementCustomerOrders(Customer customerID) {
    Customer customer = customers.computeIfAbsent(customerID, id -> new Customer(id));
    customer.incrementOrders();
}
```

事实上，Java 8 中还有另一个名为方法引用（method references）的特性，可以让代码更短：

```java
public void incrementCustomerOrders(Customer customerID) {
    Customer customer = customers.computeIfAbsent(customerID, Customer::new);
    customer.incrementOrders();
}
```

在下面的代码中，我们首先遍历书籍列表，如果之前没见过该书，则将其添加到作者列表中；然后我们按姓氏对作者进行字母排序。这正是流（streams）设计用于优雅解决的操作：

```java
public List<Author> getAllAuthorsAlphabetically(List<Book> books) {
    return books.stream()
        .map(book -> book.getAuthor())
        .distinct()
        .sorted((o1, o2) -> 
            o1.getSurname().compareTo(o2.getSurname()))
        .collect(Collectors.toList());
}
```

这不仅行数更少，而且更具描述性——开发者看到这段代码可以轻松阅读并理解 (1) 它正在从书中获取作者，(2) 它对唯一作者感兴趣，(3) 返回的列表按作者姓氏排序。将 `Streams API` 与其他特性——方法引用和 `Comparator` 的新方法结合起来，你可以得到更简洁的版本：

```java
public List<Author> getAllAuthorsAlphabetically(List<Book> books) {
    return books.stream()
        .map(Book::getAuthor)
        .distinct()
        .sorted(Comparator.comparing(Author::getSurname))
}
```

这比按作者姓氏排序的方法更加显而易见了。

> 新方法结合 `lambda` 表达式，允许我们极大地简化代码。

## 易于并行化

我们谈论开箱即用的性能，除了之前提到的那些特性外，Java 8 可以通过将方法替换为 `parallelStream` 轻松地使用更多 CPU 核心，JVM 将操作拆分为单独的任务，并使用 `fork/join` 在多个核心上运行它们。然而，并行化并不是解决一切的魔法。并行操作总是需要更多的工作——拆分操作和合并结果——因此不会花费更少的时间。但这个选项对于适合并行化的领域非常有吸引。

## 最小化空指针异常

Java 8 的另一个特性是 `Optional` 类型。这种类型提供了一种显式声明“我可能有一个值，也可能为 `null`”的方法。这意味着 API 现在可以返回可能为空的值，也可以返回始终非空的值，从而最小化了遇到 `NullPointerException` 的代价。

`Optional` 的用处在于你如何使用工具来告诉它。例如，如果你在列表中查找一本书，新的 `findFirst()` 方法返回一个 `Optional`，告诉我们它不保证能找到值。如果你找到了，你就可以决定它是否为 `null`。如果你想抛出异常，可以使用 `orElse`：

```java
public Book findByTitle(List<Book> books, String title) {
    Optional<Book> book = books.stream()
        .filter(book -> book.getTitle())
        .findFirst();
    return book.orElseThrow(() -> new
        BookNotFoundException("ID did not find book with title " + title));
}
```

或者你可以返回另一本书：

```java
return book.orElseGet(() -> 
    getRecommendedAlternativeBook(title));
```

或者我们可以返回一个 `Optional`，以便方法的调用者可以根据未找到书籍时该做什么做出自己的决定。

本文并不讨论微服务是好是坏，也不讨论你应该从一开始就为微服务设计应用，还是让它们从你的单体应用中逐渐产生。

## 无容器化

无容器化方法实现了单 JAR 部署（也称为“胖 JAR 部署”）。这意味着应用程序及其所有依赖项被封装成单个 `java -jar myservice.jar`，作为一个独立的 Java 文件。

在无容器化方法中，开发者将 JVM 上的一切视为应用程序的一部分。

瓶颈需要不同的方法。以 `jstack` 为例：它是一个将它们整合在一起的强大工具。你可能已经以某种方式熟悉它了。基本上，它只需要挂钩到运行中的进程中，并输出其中运行的所有线程。它会打印每个线程的堆栈跟踪（无论是 Java 还是原生的）；它们持有的锁以及各种其他元数据。你还可以分析已经结束的进程的堆转储（heap dumps）或核心转储（core dumps）。这是一个悠久且非常有用的工具。

问题是，`jstack` 主要用于事后分析。你想要调试的条件已经发生了，而你只能在碎片中寻找。服务器没有响应，线程被阻塞，数据库查询花费了无限的时间：典型的输出是某些糟糕的数据转储上的几个堆栈跟踪，完全没有关于我们是如何到达那一步的线索。一个好的工具应该允许你在问题开始崩溃时激活它，获取关键时刻 `jstack` 输出。例如，你可以设置一个阈值，并让 `jstack` 在性能下降时运行。

# 使用 JAVA AGENTS 跳过日志记录 ALTLOGGER

此过程的下一步是获取应用程序运行时的可视性。日志是事后检查的，并且只包含预先决定放在那里的信息。我们很清楚如何用状态数据来丰富它们，但我们需要一种方法来访问每个更改的精确值，以追根溯源。Java agents 赋予了我们在不写入磁盘和使用日志文件的情况下获取所需数据的能力，因此只提取我们真正会使用的数据。

一种有趣的方法是使用 BTrace，这是一种开源的 Java agent，它可以挂钩到 JVM 并打开堆栈跟踪，让你能够查询插桩程序。例如，你可以访问 `ClassLoaders` 及其子类，并在某些出现问题的类实例化时加载它们。它是调查特定问题的有用工具，但它要求你为想要覆盖的每个用例编写脚本。

你也可以编写自己的金丝雀代理（canary agent），就像 `FAINT-TRACE` 那样。我们在 Takip 中也进行过一次测试，由于某种原因，某个类正在初始化许多新对象。我们使用了一个挂钩到该对象构造函数的 agent。我们分配的对象会提取其堆栈跟踪。然后我们分析了结果，并理解了问题源于哪里。在日常工作中，我们使用一个生产级降级代理（production grace agent），它知道提取每个异常或日志记录错误的变量值，所有这些都以堆栈跟踪的形式，并跨越不同的机器。

# 在生产环境中进行测试：针对胆小者

在生产环境中“开玩笑”是一项许多公司正在参与的严肃实践。他们无法完全取消测试阶段，但他们理解预发布环境（staging environments）不足以模拟构建环境，无论你投入了多少时间和精力。唯一真实的地方是在生产环境中进行测试，让真实数据流经系统，并让意外情况冲击它。

根据你正在测试的功能类型，你可以采用的几种方法来进行受控测试。一种选择是将实时流量复制并路由到系统以及你正在测试的组件的新版本。通过这样，你可以看到新组件的行为，并直接与当前版本进行比较，而不会产生向用户交付错误结果的风险（如果是某些数据处理的话）。

另一个选项是划分流量并展示新功能。做到这一点的方法是使用金丝雀服务器（canary server），它是系统中运行你决定发布的新版本的单个节点（就像矿井里的金丝雀）。在金丝雀服务器上添加监控和日志也有帮助。另一个选项是在这个金丝雀设置上添加监控，实施并利用发布开关，或对应用程序的一些更改进行 A/B 测试，以观察它们的影响。

# JVM 响应式趋势

JONAS BONÉ

## 快速览

- 01 响应式系统依赖于异步消息传递的基础来创建具有响应性、韧性和弹性的松散耦合系统。
- 02 分析正在被推入流中（通过 Spark），这正在成为跨越数十亿数据实现秒级查询响应的事实标准。
- 03 快数据（或流数据）使系统更具响应性。响应式流（Reactive Streams）通过智能控制数据消费速率，使数据变得可管理。

两年前，我与几位开发者合作，在企业中定义了一套新的架构原则。很显然，从新兴的部署环境到用户预期，再到数据集的大小，一切都超出了以前构建软件的模式。基本上，典型的“崩溃”问题与大多数软件具有同步调用请求和池隔离，导致了单点故障和过度的竞争。

## 什么是响应式？

《响应式宣言》（Reactive Manifesto）的目标是将设计高扩展和可靠应用程序的知识整合为四种架构特征。

## 响应式（RESPONSIVE）

如果可能，系统会及时做出响应。响应性是可用性和实用性的基石，但不仅如此，响应性意味着可以快速检测到并有效处理问题。响应式系统专注于提供快速且一致的响应时间，以交付一致质量的服务。这种行为反过来减少了错误处理，建立了终端用户的信任，并鼓励了进一步的交互。

## 韧性（RESILIENT）

系统在面对故障时保持响应性。这不仅适用于高可用、任务关键系统——任何不具韧性的系统在故障后都会处于无响应状态。通过复制、隔离和委托来确保韧性。故障被限制在每个组件内部，隔离确保了系统的部分可以失败并恢复而不影响其他部分。组件的恢复被委托给另一个（外部）组件，并在必要时通过复制确保高可用性。组件的客户端无需承担处理故障的负担。

## 弹性（ELASTIC）

系统在不断变化的工作负载下保持弹性。响应式系统可以通过增加或减少分配给服务这些输入的资源来响应输入速率的变化。这意味着设计中没有竞争点或正确的瓶颈，从而能够对组件进行分片或复制并将输入分布在它们之间。响应式系统通过提供实时性能衡量，支持了生产力，以及响应式的扩展的代数。它们在通用硬件和软件平台上以一种成本效益的方式实现了弹性。

在《响应式宣言》中，我们创建了一套新原则，描述了需要闭环反馈来从系统中提取数据。数据的优势是系统更具响应性和适应性，允许你将实时处理数据回响应式系统，使其做出反应。这种能力可以使这些系统更加健壮和可扩展，同时降低复杂度。

## 从原则到实现模式的响应式演进

我们创建了一套新原则，描述了响应性、韧性、弹性消息驱动特性，我们认为这些特性对于现代应用时代是有效的，运行着从移动设备到带有多核处理器的云端集群的一切应用。

在过去的两年里，社区的反应是热烈的支持（《响应式宣言》上有 12,000 多个签名），以重新滚一遍（我在 Slack 的一个承诺中是说的）。“我们想要一台能让事情变得简单的机器。我们不知道如何构建它。我们将此称为：响应式宣言。”一些在内部开发中长期被接受的属性，就像某些敏捷方法在“敏捷”一词出现之前就已经用于软件开发一样。有些响应式是规范性的，而另一些则感觉太泛泛。

## 消息驱动（MESSAGE-DRIVEN）

作为上述三个特征的基础，响应式系统使用异步消息在组件之间建立边界，且不保持松散耦合、隔离、并发；并提供了以消息形式精炼和委托故障的手段。高效的消息传递通过共享和监控系统中的消息队列，并在内存变得瞬态时应用反压，实现了负载管理、弹性流控制。这种通信的透明性使得故障管理能够在跨集群或在单个主机内以相同的契约工作。非阻塞通信允许接收者在活动时消耗资源，从而导致更高效的系统利用。

在数据场景中，流式数据早期的陷阱之一是缺乏反压（back-pressure）。如果一个处理阶段产生数据比下一个阶段消费数据的快，就会导致消费者失败，从而发生级联故障。响应式流允许它们引入反压来控制数据消费速率。通常，构建大数据和物联网的后端系统适用于响应式架构。

## 作为记录服务的事件日志（EVENT LOGGING AS THE SERVICE OF RECORD）

> 典型的“崩溃”问题源于大多数软件具有同步调用请求和糟糕隔离，导致了单点故障和过度的竞争。

我们看到许多响应式创新的另一个领域，特别是在 JVM 上，当事件被记录到“服务记录”时。每个记录的事件都是历史——具体化为日志中的事件。你得到一个具有应用程序完整历史的数据库，一个事实数据库，而不是像 Pat Hall 说的、基于“事实立方体”运行的传统 SQL 数据库。如果你的持久状态缺失，可以很容易通过移动到其他地方或通过系统恢复其位置。这是处理分布式流式处理的一种极佳模式——如果某件事可以恢复速度并继续运行。这样的架构模式包括事件 CQRS。这种关于持久化架构的思考方式与微服务非常契合，每个服务都有其独立的一致性事件、事件加载存储，处理服务之间的一致性和可用性问题。数据是持久化架构的基础。

## 驱动响应式创新的新模式

## 微服务（MICROSERVICES）

在传统的 EE 应用中，服务是以单体方式编写的。这意味着组件和服务之间是紧密耦合的。应用服务器（如 Bean、Tomcat）正在鼓励这种单体模型。我们假设你将服务带入 EAR 文件，就像将服务封装成 JAR 包一样，而不是将你所有的应用程序和服务部署到应用服务器，这使得单实例运行服务的隔离变得困难。容错策略。

我们拥有了更进化的隔离基础——从底层开始，从每个 Docker 容器，一直延伸到硬件和通信协议。我对第一类公民隔离感到兴奋，它是韧性的必要条件。如果没有隔离，你就无法构建响应式系统，因为无法在故障组件之外拥有一个独立的上下文来防止故障扩散。我认为响应式是敏捷方法的一个类似者。许多公司在“敏捷”一词出现几年前，就已经在使用敏捷方法了。但命名为敏捷让讨论这种哲学变得容易，因此《敏捷宣言》诞生了。当这些原则对社区变得熟悉后，你开始看到 Scrum 的采用，然后是支持编程原则和实践的 XP 框架，如团队 Scrum 开发和持续集成。

# 术语表

- JAVA COMPATIBILITY KIT (JCK) 一套用于认证 Java 平台实现的工具、资源和测试套件的组合包。

- JAVA VIRTUAL MACHINE (JVM) Java 平台的运行时引擎，它将用 Java 编写的程序编译为字节码。JVM 为开发者提供了一种编写平台无关代码的方法。

- JAVA DATABASE CONNECTIVITY (JDBC) 一种 Java 标准，提供一种可以访问 SQL 数据库的调用级 API。

- APPLET 一种为 Web 编写的 Java 程序，通常嵌入在 HTML 页面中。

- JAVA DEVELOPMENT KIT (JDK) 一套完整的二进制文件集，包含了用于开发、调试和监控应用程序的 JRE。

- LAMBDA EXPRESSION Lambda 表达式。在 Java 8 中：一种匿名方法，用于用轻量且更具可读性的代码替换类。使得 Java 的函数式编程变得简单得多。

- BEAN 也称为 JavaBeans，这些是符合某些简单操作的对象，具有属性命名和数据封装。

- JAVA ENTERPRISE EDITION (EE) 一种用于开发和运行企业软件的 API 和运行时，包括 Web 服务和大型网络。

- ENTERPRISE JAVABEANS (JB) 一种基于注解的关键 Java API，为 POJOs 提供组件。

- JAVA MESSAGING SERVICE (JMS) 一种 Java API 和消息标准，促进基于 Java EE 的组件之间以中间件为导向的功能。

- MICROSERVICES 微服务是一种由小型、轻量级服务组成的系统或应用程序，这些服务根据您的领域边界上下文执行单一功能。它们是可独立部署且松耦合的。

- GARBAGE COLLECTION 垃圾回收是 JVM 使用的一种自动内存管理系统，用于释放未使用对象占用的空间。

- OBJECT-RELATIONAL MAPPING (ORM) 对象关系映射，一种用于在不兼容类型之间转换数据的面向对象编程技术。ORM 让开发者能够在无需为数据库编写语言代码的情况下操作关系型数据库。

- INTEGRATED ENVIRONMENT (IDE) 集成开发环境是一种提供代码编辑器、调试器、编译器和许多其他功能的应用程序，使开发者效率更高并减少在构建软件时产生错误。

- JAVA EDITION (ME) 一种运行在移动设备和互联网设备上的 Java 应用的解决方案，包括微控制器、传感器、机顶盒和打印机。

- OPENJDK 官方的开源 Java 实现。

- JAVA API FOR RESTFUL SERVICES (JAX-RS) 一种使用注解将帮助资源类（POJOs）映射到基于 SOAP 的 服务的 Java API。

- JAVA NAMING AND INTERFACE (NDI) 一一组 API，用于帮助 Java 软件客户端管理对象和数据的发现与查找。

- PLAIN OBJECT (POJO) 简单 Java 对象，一个术语，用于解释给定的 Java 对象不是特殊对象，只是由 EJB 框架定义的。一种没有实现框架接口或扩展框架类的简单对象。Java beans 是带注解的 POJO。

- JAVA ARCHIVE (JAR) Java 归档，一种格式化多个 Java 类文件并嵌入元数据的包，以便在 Java 平台上分发类和库。

- JAVA PERSISTENCE API (JPA) 一种用于对象关系映射方面管理关系型数据的标准规范。

- JAVA RUNTIME ENVIRONMENT (JRE) Java 环境，一组允许你在机器上执行 Java 程序的二进制文件。

- Servlet 一种运行在 Web 服务器内部并提供服务器能力的 Java 程序。

- JAVA ARCHITECTURE FOR XML BINDING (JAXB) 一种用于对象与 XML 之间进行序列化和反序列化的 Java API。

- JAVA SERVER PAGES (JSP) Java 平台中的工具，允许开发者开发和构建 HTML、XML 和其他文档。JSP 在运行时会被转换为 Servlet。

- STREAM API 流 API 是 Java 8 的新 API，用于对集合进行声明式、并行化的数据处理。强大的类似于 SQL 的数据查询和操作能力。

- JAVA CARD Java 卡为运行在智能卡和其他内存限制设备上的应用程序提供安全环境。

- JAVA REQUEST SERVICE (JSR) Java 请求规范，为 Java 平台功能编写建议规范和最终规范。

- TECHNOLOGY COMPUTATION KIT (TCK) 技术计算套件，一组通过构建并提交以认证 JSR 合规性的套件。

- JAVA COMMUNITY PROCESS (JCP) Java 社区进程，社区成员通过该过程提出、讨论并确定功能，以改进和扩展 Java 平台。

- JAVA STANDARD EDITION (SE) Java 标准版，用于桌面和服务器开发及部署 Java 环境的最常用平台。
