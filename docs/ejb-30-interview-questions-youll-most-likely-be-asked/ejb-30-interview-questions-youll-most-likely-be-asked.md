## EJB 环境

# 1: 什么是 EJB 容器？

答案：

EJB 容器可以定义为运行在应用程序服务器上并实现 EJB 规范的程序。

# 2: 什么是应用程序服务器？

答案：

应用程序服务器可以定义为为运行企业级应用提供环境的应用程序。

# 3: 为什么应用程序服务器在企业级应用开发中很流行？

答案：

应用程序服务器为企业级应用直接提供事务、安全、持久化等所有环境支持。因此，在使用应用程序服务器实现时，企业级应用的开发会变得简单得多。

# 4: 列举两个目前常用的应用程序服务器？

答案：

`Weblogic` 和 `WebSphere` 应用程序服务器。

# 5: 应用程序服务器运行在哪里？

答案：

应用程序服务器既可以远程运行，也可以在客户端机器运行。

# 6: 应用程序服务器和 EJB 服务器有什么区别？

答案：

应用程序服务器为企业级应用提供支持，而 EJB 服务器仅为企业 Bean 提供支持。

## 企业 Bean (Enterprise Beans)

# 7: 什么是企业 Bean？

答案：

企业 Bean 设计用于封装企业级应用的业务逻辑。它是一个 Java EE 服务端组件，运行在 EJB 容器内部。

# 8: 什么时候使用企业 Bean？

答案：

企业 Bean 用于大型企业级应用开发。因此，如果企业级应用需要事务、完整性、可扩展性等，那么企业 Bean 是最佳选择。

# 9: EJB 3.0 中提供了哪些类型的 Bean？

答案：

- 会话 Bean (Session bean)

- 消息驱动 Bean (Message driven bean)

# 10: EJB 3.0 删除了哪些接口？

答案：

Home 接口（home interface）被删除了。

# 11: EJB 3.0 中提供了哪些类型的 Bean？

答案：

Home 接口被删除了。

# 12: 什么是业务逻辑层？

答案：

会话 Bean 和消息驱动 Bean 成了该层。

# 13: 什么是持久化层？

答案：

持久化层用于数据的持久化存储。

# 14: EJB 2.x 有哪些类型？

答案：

- 会话 Bean (Session bean)

- Home Bean

- 实体 Bean (Entity bean)

# 15: EJB 3.0 有哪些特性？

答案：

- 会话 Bean

- 持久化层

- 实体 Bean

# 16: EJB 3.0 中提供了哪些类型的 Bean？

答案：

- 无状态会话 Bean (Stateless session bean)。

# 17: 你如何定义一个 POJO 类？

答案：

通过使用注解（annotations）来定义 EJB。

# EJB 3.0 面试题 你极可能被问到的

# 18: EJB 3.0 中提供了哪些类型的会话 Bean？

答案：

- 有状态会话 Bean (Stateful bean)

- 无状态会话 Bean (Stateless bean)

# 19: 什么时候使用有状态会话 Bean？

答案：

当需要保留业务过程的状态时，使用有状态会话 Bean。

# 20: EJB 2.x 中包含哪些组件？

答案：

- 会话接口 (Session interface)

- Home 接口 (Home interface)

- Bean 类 (Bean class)

# 21: 使用什么注解来表示无状态会话 Bean？

答案：

使用 `@Stateless` 注解来定义无状态会话 Bean。

# 22: 该注解的作用是什么？

答案：

注解告诉容器该 POJO 是会话 Bean 并强制生命周期和语义。

# 23: 使用什么注解来表示远程接口（remote interface）？

答案：

使用 `@Remote` 注解来引用远程接口。

# 24: 什么时候使用有状态会话 Bean？

答案：

当需要状态时，使用有状态会话 Bean。

# 25: 使用什么注解来表示有状态会话 Bean？

答案：

使用 `@Stateful` 注解来表示该会话 Bean。

# 26: 会话可以是抽象的或最后的 POJO 吗？

答案：

会话必须是具体的 POJO。

# 27: 会话 EJB 可以继承另一个会话 Bean 吗？

答案：

不，会话 EJB 不能继承另一个会话 Bean。它可以继承 POJO。

# 28: 为什么要使用消息驱动 Bean？

答案：

消息驱动 Bean 用于处理基于 J2EE 应用中的异步消息。

# 29: 谁负责调用消息驱动 Bean？

答案：

消息驱动 Bean 由容器调用。它们从未被客户端或其他 Bean 调用。

# 30: 消息驱动 Bean 使用什么注解？

答案：

消息驱动 Bean 使用 `@MessageDriven` 注解。

# 31: 消息驱动 Bean 实现的接口是什么？

答案：

消息驱动 Bean 实现 `MessageListener` 接口。其中仅定义了一个方法，被称为 `onMessage`。

# 32: 消息驱动 Bean 中用于配置相关信息的属性名称是什么？

答案：

名称是 `ActivationConfigProperty`。它包含了所有的配置信息。

# 33: 注解对回调方法（call back methods）有什么影响？

答案：

注解用于标记生命周期管理所需的回调方法。

# 34: EJB 3.0 规范中的生命周期方法是强制的吗？

答案：

不，在 EJB 3.0 规范中生命周期方法的实现是可选的。但在 EJB 2.x 中是强制的。

即使你没有使用，规范也是。

## 会话 bean (Session Beans)

# 35: 描述状态会话 bean（stateful session bean）的生命周期。

答案：

以下是状态会话 bean 的生命周期阶段：

- a) 创建 (Create)

- b) 依赖注入 (Dependency injection)

- c) `PostConstruct` 回调 (PostConstruct callback)

- d) 删除 (Remove)

- e) `PreDestruct` 回调 (PreDestruct callback)

# 36: 状态会话 bean 其他两个生命周期阶段是什么？

答案：

另外两个阶段是：

- a) `PrePassivate` 回调 (PrePassivate callback)

- b) `PostActivate` 回调 (PostActivate callback)

# 37: 状态会话 bean 是否有超时值？

答案：

是的，状态会话 bean 有超时值。如果在超时时间内未使用，容器将自动删除它。但通常建议在使用后显式移除该 bean，而不是依赖于超时机制。

# 38: 会话 bean 或 MDB 中拦截器（interceptors）的用途是什么？

答案：

拦截器通常用于在调用业务逻辑方法之前进行验证和安全检查。

# 39: 什么是默认拦截器（default interceptor）？

答案：

默认拦截器是 EJB 3.0 规范提供的一个概念。它不是通过任何注解定义的，而是必须在 EJB 模块的部署描述符中显式编写。

# 40: 不同拦截器的执行顺序是什么？

答案：

它们按照以下顺序被调用：

- a) 默认拦截器 (Default interceptor)

- b) 类拦截器 (Class interceptor)

- c) 方法拦截器 (Method interceptor)

# 41: 是否可以禁用任何拦截器的调用？

答案：

可以，可以使用 `@ExcludeDefaultInterceptors` 和 `@ExcludeClassInterceptors` 等注解来禁用调用。

# 42: EJB 3.0 规范中的依赖注入是什么？

答案：

依赖注入是一种无需任何 JNDI 查找即可获取 Java EE 资源的强大方式。它使应用程序变得松耦合。

# 43: 用于将 EJB 注入到客户端代码中的注解是什么？

答案：

`@EJB` 注解用于将会话 bean 注入到客户端。

# 44: 用于资源注入（resource injection）的注解是什么？

答案：

`@Resource` 注解用于注入资源。

# 45: 为什么要使用 setter 注入（setter injection）？

答案：

不应将资源直接注入到应用程序代码中。资源应该分离在不同的组件，这会让代码更灵活。setter 注入用于实现这一目的。

# 46: 部署描述符（deployment descriptor）的用途是什么？

答案：

EJB 3.0 中的所有任务都可以通过注解完成。但也可以通过部署描述符来实现。

# 47: EJB 3.0 功能包中提供的两个命名空间（name spaces）是什么？

答案：

以下是提供的两个命名空间：

- JVM 作用范围的 `EJBlocal` 命名空间

- 全局 JNDI 命名空间

# 48: 打包 Java 企业应用程序的格式名称是什么？

答案：

该格式名称为企业应用归包（EAR）。它包含了所有其他模块，如 WAR、RAR 等。

# 49: 用于部署 Java 企业应用程序的部署描述符的名称是什么？

答案：

部署描述符的名称是 `EJB-jar.xml`。

# 50: 容器使用的两个默认绑定（bindings）是什么？

答案：

两个默认绑定是：

- a) 短绑定 (Short binding)

- b) 长绑定 (Long binding)

# 51: 什么是短绑定（short binding）？

答案：

在短绑定中，仅使用带包限定的接口 Java 类名。

# 52: 长绑定（long binding）是如何实现的？

答案：

在长绑定中，bean 的组件 ID 作为额外的限定符与带包限定的接口类名一起使用。

# 53: 组件 ID（component ID）的不同部分是什么？

答案：

EJB 的组件 ID 是使用企业 bean 的应用程序名称、模块名称和组件名称形成的。

# 54: 你在哪里绑定本地接口（local interfaces）？

答案：

所有本地接口都绑定到 `EJBLocal` 命名空间，该空间仅在同一个 JVM 内可访问。

# 55: 你在哪里绑定远程接口（remote interfaces），为什么？

答案：

所有远程接口都绑定到全局作用范围（global-scoped）命名空间，以便可以从 WebSphere 产品单元的任何地方访问。

# 56: 所有与 EJB 相关的绑定的最佳实践是什么？

答案：

最佳实践是将所有与 EJB 相关的绑定分组在 EJB 上下文中。

# 57: 你在哪里提供用户定义的绑定信息？

答案：

用户定义的绑定信息提供在一个新创建的文件中，名为 `META-INF/ibm-EJB-jar-bnd.xml`。

# 58: 可用的两种打包选项是什么？

答案：

两个可用选项如下：

- a) 使用 Java 项目或 Java 工具项目

- b) 使用 EJB 项目

# 59: 使用 Java 打包选项时，在部署描述符中需要编辑什么？

答案：

需要在 `application.xml` 文件中添加以下行：

```
<module>
  <EJB>MyEJB3Module.jar</EJB>
</module>
```

# 60: 如果我们使用 EJB，我们需要添加任何内容吗？

答案：

如果我们使用 EJB 项目选项，则不需要在部署描述符中添加任何内容。

# 61: `EJB.xml` 文件的用途是什么？

答案：

根据 EJB 3.0 规范，不需要 `EJB.xml` 文件，因为一切都是通过注解指定的。

# 62: EJB 3.0 使用什么规范？

答案：

Java Persistence API (JPA) 用于持久化。

# 63: JPA 的优势是什么？

答案：

JPA 使用可插的服务模型。因此很容易与不同的供应商配合。

# 64: JPA 的三个主要部分是什么？

答案：

以下是 JPA 的三个部分：

- Java 持久化 API (Java Persistence API)

- 对象关系映射 (Object relational mapping)

- 查询语言 (Query language)

# 65: JPA 中的实体（entity）是什么？

答案：

用于持久化的主要对象称为实体。

# 66: 实体继承任何类吗？

答案：

不，实体是普通的 Java 对象（POJO），它不继承任何类。

# 67: EJB2.x 的什么局限性被实体解决了？

答案：

实体可以通过 RMI-IIOP 进行序列化，但实体 bean（entity beans）不能。

# 68: JPA 描述符文件的名称是什么？

答案：

文件名称是 `orm.xml` JPA 描述符。

# 69: 使用哪个注解来引用主键？

答案：

在实体中使用 `@Id` 注解来引用表中的主键。

# 70: 创建实体遵循什么规范？

答案：

使用 JavaBean 规范来创建实体。

# 71: `@Table` 注解包含什么？

答案：

当实体映射到表时，`@Table` 注解包含模式（schema）和表名。

# 72: 使用哪个注解来映射表列和实体属性？

答案：

`@Column` 注解用于映射表列与实体属性。

# 73: 实体有哪些可用的持久化机制？

答案：

这两种机制是：

- a) 字段持久化 (Field-based persistence)

- b) 属性持久化 (Property-based persistence)

# 74: 你能描述字段持久化吗？

答案：

在字段持久化中，不使用 getter/setter 方法。实体属性被声明为 public 或 protected，并指示 JPA 供应商不要使用 getter/setter。

# 75: 你能描述属性持久化吗？

答案：

在属性持久化中，使用 getter 和 setter 方法来持久化数据。

# 76: 推荐使用哪种持久化机制，为什么？

答案：

始终推荐使用属性持久化机制，因为它符合 Java 编程规范。

# 77: 一个实体可以继承另一个实体吗？

答案：

是的，一个实体可以继承另一个实体。

是的，一个实体可以扩展另一个实体。在这种情况下，属性会自动持久化。

# 80: 实体可以扩展类吗？

答案：

是的，实体也可以扩展类。但那种情况下，该类的属性不会被持久化，因为它没有被声明为实体。

# 81: 什么时候使用 `@Basic` 注解？

答案：

如果你想按原样将任何标准值持久化到数据存储中，则使用 `@Basic` 注解。

# 82: 什么时候使用 `@Transient` 注解？

答案：

如果你不想持久化实体中的某个字段，则使用 `@Transient` 注解。

# 83: 指定实体标识的方法有哪些？

答案：

标识实体标识有三种不同的方法：

- a) `@Id` 注解

- b) `@IdClass` 注解

- c) `@EmbeddedId` 注解

# 84: 什么时候使用 `@Id` 注解？

答案：

在以下情况下适用于 `@Id` 注解：

- a) 可用自然主键

- b) 可用代理键

# 85: 你如何管理复合主键？

答案：

复合主键通过使用 `@IdClass` 或 `@EmbeddedId` 注解来定义。

# 86: 为了创建复合主键需要重写哪些方法？

答案：

在创建复合主键时需要重写 `equals` 和 `hashCode` 方法。

# 87: 为什么在创建复合主键时没有 setter 方法？

答案：

没有 setter 方法是因为在使用主键值构造它之后，它不能再被更改。

# 88: 什么时候使用 `@EmbeddedId` 注解？

答案：

此注解用于建模没有自身标识的持久化对象，因为它们嵌套在另一个实体内部。

# 89: 使用什么注解来生成自动标识？

答案：

`@GeneratedValue` 注解用于自动生成 Id。

# 90: JPA 中可用哪四种自动生成类型？

答案：

这四种类型如下：

- a) `GenerationType.IDENTITY`

- b) `GenerationType.SEQUENCE`

- c) `GenerationType.AUTO`

- d) `GenerationType.TABLE`

# 91: 什么时候使用 identity 和 sequence 作为生成类型？

答案：

当持久化提供程序使用数据库标识列来生成标识时，使用 `IDENTITY` 生成类型；

当持久化提供程序使用数据库序列来生成标识时，使用 `SEQUENCE` 生成类型。

# 92: 什么时候使用 `AUTO` 生成类型？

答案：

当持久化提供程序选择最适合底层数据库的主键生成器时，使用 `AUTO`。

# 93: `TABLE` 生成类型的含义是什么？

答案：

`TABLE` 生成类型用于指定持久化提供程序使用底层数据库表来为实体分配主键。



# 94: 哪种生成器类型是可移植的？

答案：

`TABLE`生成器类型是最可移植的解决方案。

它只使用普通的数据库表，可以使用任何关系型数据库管理系统（RDBMS）。

# 95: 在活动事务期间创建主键时，可用哪些事务机制？

答案：

以下是可用的两种机制：

- a) 挂起当前事务
- b) 使用单独的事务

# 96: JPA 中可用哪些回调方法？

答案：

以下是 JPA 中可用的回调方法：

- a) `@PostLoad`
- b) `@PrePersist`
- c) `@PostPersist`
- d) `@PreUpdate`
- e) `@PostUpdate`
- f) `@PreRemove`
- g) `@PostRemove`

# 97: 什么时候使用 `@PostLoad` 回调方法？

答案：

`@PostLoad`回调方法在实体加载到当前持久化上下文之后，以及当对其应用刷新操作时被调用。

# 98: 什么时候调用 `@PrePersist` 和 `@PreRemove`？

答案：

`@PrePersist`和`@PreRemove`回调方法在对实体执行相应的持久化（persist）和删除（remove）操作之前被调用。

# 99: 什么时候使用 `@PreUpdate` 和 `@PostUpdate` 回调？

答案：

`@PreUpdate`和`@PostUpdate`回调用于数据库更新操作之前和之后。

# 100: 什么时候使用 `@PostPersist` 和 `@PostRemove` 回调方法？

答案：

`@PostPersist`和`@PostRemove`回调方法在实体持久化或删除之后立即被调用。

# 101: 为实体使用回调方法的方法有两种两种？

答案：

回调方法可以直接插入实体类中，也可以保留在单独的类中并引用。

# 102: 当回调保留在单独的类中时，使用什么注解？

答案：

在实体类中使用`@EntityListeners`注解来引用回调。

# 103: 你如何在 JPA 中定义关系？

答案：

在 JPA 中，关系通过从源对象到目标对象的对象引用来定义。

# 104: 对象之间的单向关系是指什么意思？

答案：

单向关系意味着源对象拥有目标对象的引用，但不能保证目标对象拥有源对象的引用。

# 105: JPA 中可用哪些不同类型的关系？

答案：

关系有：

- a) 一对一 (one-to-one)
- b) 多对一 (many-to-one)
- c) 一对多 (one-to-many)
- d) 多对多 (many-to-many)

# 106: 什么时候使用 `@ToOne` 注解？

答案：

`@ToOne`注解用于定义多对一关系。

# 107: 什么是双向关系？

答案：

在双向关系中，源对象拥有目标对象的引用，目标对象也拥有源对象的引用。

# 108: 你如何在 JPA 中定义一对关系？

答案：

一对关系通过`@OneToOne`和`@JoinColumn`注解实现。

# 109: JPA 中的 JoinColumn 是什么？

答案：

`JoinColumn`用于指定数据库中的外键列。

# 110: 有没有创建 JoinColumn 的默认机制？

答案：

如果你不指定`JoinColumn`，将根据字段名假设默认名称。

# 111: 什么是一对多关系？

答案：

一对多关系是指一个实体与多个其他实体相关联。

# 112: 你如何实现多对多关系？

答案：

多对多关系通过`@ManyToMany`和`@JoinTable`注解实现。

# 113: 多对多关系中使用了哪些注解？

答案：

使用`@ManyToMany`和`@JoinTable`注解来实现多对多关系。

## 123: 用于选择加载类型的默认策略是什么？

答案：

默认策略是：

- a) 当上下文为基础或多对一时时，使用快速加载（eager loading）
- b) 当上下文为一对多或多对多时，使用懒性加载（lazy loading）

## 124: 什么是级联类型（cascade type）？

答案：

当实体管理器读取、更新或删除实体时，可以使用`cascade`属性指示它自动将操作级联到持久化字段中持有的实体。

## 125: 有哪些级级联规则？

答案：

以下是不同的级联规则：

- a) `CascadeType.PERSIST`
- b) `CascadeType.REMOVE`
- c) `CascadeType.REFRESH`
- d) `CascadeType.MERGE`
- e) `CascadeType.ALL`

## 126: 请描述你何时使用 ‘PERSIST’ 级联类型？

答案：

当我们需要持久化一个实体的同时也持久化该字段中持有的实体时，使用此类型。

## 127: 你能简要描述其他任何级联类型吗？

答案：

其他类型如`remove`、`refresh`或`merge`，用于与这些字段中持有的值一起删除、刷新或合并实体。

## 128: 你在何时使用级联类型为 ‘ALL’？

答案：

当我们需要实现所有类型的级联操作时，使用 ‘ALL’。

## 129: 什么是阻抗不匹配（Impedance Mismatch）？

答案：

正如我们所知，对象与关系型世界之间总是存在不匹配。我们采取了不同的策略在关系型数据库中持久化对象，但这种不匹配仍然存在。这被称为阻抗不匹配。

## 130: JPA 中支持继承的策略有哪些？

答案：

JPA 支持的三种策略是：

- a) 单表（Single table）
- b) 联表（Joined tables）
- c) 每个类表（Table per class）

## 131: 什么是单表继承？

答案：

在单表继承中，整个类层次结构被映射到单个基表中。

## 132: 你在何时使用 `@Inheritance` 注解？

答案：

根类（super root class）需要标记`@Inheritance`注解。

## 133: `@DiscriminatorColumn` 和 `@DiscriminatorValue` 注解是什么？

答案：

根类使用`@DiscriminatorColumn`注解标明表中哪一列用于存储区分符值。`@DiscriminatorValue`注解用于继承类，标明哪一列映射到哪个实体。

## 134: 单表继承模型的优势是什么？

答案：

在单表继承中，由于所有实体都存储在单个表中，因此检索实体时不需要连接（Join）。插入和更新操作也容易执行。

## 135: 如果层次结构很宽，你会使用单表层次结构吗？

答案：

你始终可以使用单表层次结构模型。但在层次结构很宽的情况下，所有列都需要存储在单个表中，在这种情况下可能会出现许多空值列。

## 136: 描述联表层次结构（joined table hierarchy）中使用的策略？

答案：

在这一策略中，顶层实体映射到一个包含所有实体公共字段的表中，而继承的实体则映射到仅属于该实体的表中。因此，在重组时，需要执行 Join 操作来检索整个层次结构。

## 137: 使用哪个注解来指示主键？

答案：

使用`@PrimaryKeyJoinColumn`注解来指示主键。

## 138: 联表策略的优势是什么？

答案：

这种策略的优势在于我们没有扰动数据库中现有的表。相反，我们为新实体创建表，它们通过主-外键关系与父实体相关联。

## 139: 可以在联表策略中使用归一化吗？

答案：

是的，在使用联表策略时，可以使用归一化模式，而不会产生冗余数据。

## 140: 联表策略对性能有影响吗？

答案：

对于检索实体结构，我们需要连接表，如果层次结构本身很复杂，这可能会花费很长的时间并产生复杂的查询。

## 141: 如果你有一个复杂的数据模型，应该使用哪种策略？

答案：

在具有复杂关系的复杂数据模型中，联表策略是最合适的。

## 142: 什么是每个类继承（table per class inheritance）？

答案：

在这一策略中，父类和子类存储在各自自己的表中，之间没有任何关系。

## 143: 为什么在每个类继承中所有表都运行了 `@Table` 注解？

答案：

所有实体都使用`@Table`注解，因为每个实体都映射到一个单独表中。

## 144: 你在何时使用每个类策略？

答案：

当你对一个已知的类进行操作时，这种策略非常有帮助。

## 145: 每个类策略的缺点是什么？

答案：

如果你不知道子类，那么实施这种策略将很困难，因为表之间没有可用的连接（join）。

## 146: 你如何识别子类？

答案：

在未知的情况下，通过实现每个类的基 SQL 查询来识别。

## 147: 什么是持久化单元（persistence unit）？

答案：

持久化单元可以定义为由持久化管理的实体集。它代表了数据存储。

## 148: 什么 XML 文件用于定义持久化单元？

答案：

使用`persistence.xml`文件来定义持久化单元。

## 149: 持久化单元的根节点是什么？

答案：

`persistence.xml`文件位于 JAR 的`META-INF`目录。

## 150: 持久化单元的范围是什么？

答案：

持久化单元的范围由其唯一名称决定。

## 151: 持久化单元是如何打包的？

答案：

持久化单元作为 WAR 或 EJB 包的一部分。

## 152: `persistence.xml` 中的事务类型是指？

答案：

事务类型指定了持久化单元参与的类型（JTA 或其他）。

## 153: 持久化单元范围内的映射文件是什么？

答案：

映射文件包含包含在持久化单元的信息。

## 154: 你可以用注解替换 `persistence.xml` 吗？

答案：

该文件是强制性的，无法用注解替换。

## 155: 可以使用任何 XML 文件进行 ORM 映射？

答案：

是的，ORM 映射也可以在 XML 文件`orm.xml`中完成而不是使用注解。

## 156: 谁负责持久化实体？

答案：

注解仅用于定义实体及其与数据库的映射。但持久化是由`EntityManager`接口完成的。

## 157: 描述实体管理器执行的任务？

答案：

以下是实体管理器执行的任务：

- 管理实体实例的生命周期
- 管理持久化单元

## 158: 什么是持久化上下文（persistence context）？

答案：

持久化上下文可以定义为创建、持久化或删除实体的范围。

## 159: 持久化上下文关闭会发生什么？

答案：

当持久化上下文关闭时，所有实体和实体管理器都将变为分离状态。因此，在实体上进行的任何更改都不会反映在数据库中。

## 160: 什么是未管理实体？

答案：

当实体从持久化上下离离时，它被称为未管理实体。

## 161: 持久化管理器执行的合并操作是指？

答案：

这意味着将分离实体的状态合并到其托管副本中。

## 162: 持久化管理器执行的刷新（flush）操作的作用是什么？

答案：

刷新操作将实体的状态同步到数据库部分。

## 163: 可用的两种类型实体管理器是？

答案：

两种类型是：

- 容器托管实体管理器（Container managed entity manager）
- 应用程序托管实体管理器（Application managed entity manager）

## 164: 容器管理的实体管理器（entity manager）的主要功能是什么？

答案：

它负责管理持久化上下文（persistence context）的生命周期。

## 165: 如何获取容器管理的实体管理器的引用？

答案：

通过 JNDI 查找或依赖注入获取引用。

## 166: 容器管理的实体管理器使用什么类型的事务？

答案：

容器管理的实体管理器使用 JTA 事务。

## 167: 容器管理的持久化上下文有哪些范围（scopes）？

答案：

这两个范围是：

- a) 事务持久化范围（Transaction persistence scope）
- b) 扩展持久化范围（Extended persistence scope）

## 168: 存在于事务持久化范围内的上下文生命周期有多长？

答案：

上下文的生命与事务同步，并在事务结束时关闭。

## 169: 使用什么注解在 EJB3 session bean 中注入实体管理器？

答案：

使用`@PersistenceContext`注解在 session bean 中注入实体管理器。

## 170: 实体管理器是线程安全的吗？

答案：

实体管理器实例不是线程安全的。因此使用 JNDI 查找来获取结果并将其赋值本地变量。

## 171: 什么是扩展持久化上下文（extended persistence context）？

答案：

持久化上下文可以扩展到事务完成后仍然存在，被称为扩展持久化上下文。

## 172: 容器管理的扩展持久化上下文的局限性是什么？

答案：

局限性在于只有有状态的 session bean 才能可以拥有容器管理的扩展持久化上下文。

## 173: 什么时候使用扩展持久化上下文？

答案：

当工作流跨越多个事务时使用。

## 174: 应用程序管理的实体管理器（application managed entity manager）是指什么？

答案：

在这种类型的实体管理器中，实体管理是通过应用程序代码完成的。

## 175: 应用程序管理的实体管理器的基本方面有哪些？

答案：

基本方面是：

- a) 实体管理器实例的生命周期由应用程序代码管理。
- b) 持久化不支持传播。
- c) 关联的持久化上下文由应用程序代码创建和销毁。

## 176: 在什么情况下使用应用程序管理的实体管理器？

答案：

以下是我们应该使用它的两种场景：

- a) 在 java SE 环境下，持久化上下文是独立的。
- b) 在 java EE 环境下，我们希望对实体管理器的生命周期有更多的控制。

## 177: 使用什么 API 来获取实体管理器？

答案：

使用`EntityManagerFactory` API 来获取实体管理器。

## 178: 在 java SE 环境下，应用程序管理的实体管理器应该用什么来管理事务？

答案：

应该使用`EntityTransaction`接口，因为 JTA 是不可用的。

## 179: 实体实例何时变为未管理状态（unmanaged）？

答案：

当事务范围或扩展持久化上下文结束时，它们变为未管理且离线状态（detached）。

## 180: 我们可以将离线实体（detached entity）发送给远程客户端吗？

## 181: EJB2.x 模型和 EJB3.0 模型中的实体有什么区别？

区别在于，在 EJB2.x 模型中，实体始终由容器管理，而在 EJB3.0 中，它们可以由容器或应用程序管理。

## 182: java EE 的两种基本方法是什么？

## 23：你还在寻找哪些类型的工作？

**回答：**

这个问题的回答可以向面试官展示你正处于人才市场且很受欢迎。提到你申请过或看过的与你领域密切相关、或与你正在面试的职位相似的工作。不要提到那些为了迫于一急而找的、与你领域完全无关的兼职。

## 24：你曾在工作中受过纪律处分吗？

**回答：**

希望答案是否——但如果你确实在工作中因为某些事受过纪律处分，务必确保你能彻底解释清楚。详细说明你从那个情况中学到了什么，并反思在这个过程中你是是如何成长的。

## 25：你的时间安排是怎样的？

**回答：**

你的时间安排显然应该是尽可能开放的，任何时间上的空缺都应该得到解释和说明。避免询问休假或请假（以及其他福利），并向面试官传达你对工作的严肃态度。

## 26：我可以联系你的现任雇主吗？

**回答：**

如果可能，让面试官联系你的现任雇主作为推荐是最好的。然而，如果不联系你的雇主非常重要，请委婉地解释原因，例如你刚开始找工作，还没有机会告知他们你正在寻找其他工作机会。不过，要谨慎使用这个理由，因为雇主可能会怀疑你是否会在为他们工作期间也开始寻找更好的机会。

## 27：你是否有任何可以为我们公司带来价值的优质人脉？

**回答：**

如果你能带来知识、人脉或其他新雇主可以进行社交拓展的联系，那是太棒了。但是，请确保你没有提供任何前任雇主的客户，或以任何方式违反合同协议。

## 28：你多久可以开始工作？

**回答：**

虽然你希望在公司对你有聘用兴趣时确保能尽快开始工作，但如果你还有另一份工作，请确保至少提前两周通知他们。尽管你的新雇主可能急于让你开始，但他们会希望雇佣一个因给予充分通知而受尊重的员工，这样他们就不必担心你最终会把他们抛弃不管。

## 29：你的上任雇主会说你是为什么离开的？

**回答：**

这个问题的关键在于，雇主的回答必须与你对离开原因的回答一致。例如，如果你告诉雇主你离开是为了寻找更多职业晋升的机会，那么你的雇主最好不要说你是因为缺勤太多而被解雇的。诚实是你求职过程中的关键。

## 30：你积极找工作多多久了？

**回答：**

最好你没有积极找工作太久，因为时间太长可能会让面试官疑惑为什么没有其他人雇佣你。如果已经过了一段时间，请务必解释原因，并保持积极。也许你还没有遇到太多能给你提供足够挑战，或与你的教育背景和经验充分匹配的机会。

## 31：你什么时候不来上班？

**回答：**

显然，唯一可以接受缺勤的时间是真正的紧急情况或你真的生病了——所以现在不要开始提到你计划因休假或家庭生日而缺勤的时间。或者，你可以告诉面试官你对工作有多投入，你如何总是努力全情投入，并在每次上班时投入相同的工作，即使在你感到身体微不适时。

## 32：你缺勤最常见的原因是什么？

**回答：**

如果你有一个经常性缺勤的原因，现在是披露它的时候——但在面试期间这样做会对你的形象产生负面影响。理想情况下，你只会在极端疾病或其他紧急情况下缺勤。

## 33：你的出勤率记录如何？

**回答：**

务必诚实地回答这个问题，但理想情况下，你已经付出了努力来证明你很少缺勤或迟到。然而，如果你的考勤记录中有空缺，请用合适的理由简要解释，并确保强调你对工作的投入和可靠性。

## 34：你从哪里听到这个职位的？

**回答：**

这看起来像是一个简单的问题，但答案实际上可以反映你的很多信息。如果你是由朋友或公司的另一名员工推荐的，这是一个提到你人脉关系的好机会（如果那个人表现良好的话！）。然而，如果你是从招聘会或工作安置中介机构听说的，你可能想重点关注这一点。

## 35：还有什么其他你想了解的吗？

**回答：**

这是你对自己进行最后一次推销的绝佳机会——提醒面试官你为什么胜任这个职位，以及你能为公司带来什么其他人都无法提供的价值。表达你对有机会参与这一使命的兴奋之情。

## 36：你从哪里寻找灵感？

**回答：**

灵感可以来自任何地方，面试官想看到你的想法是多样化的。提到你获取灵感的多个来源，并详细说明你如何记录这些想法或在之后对其进行扩展。

## 37：你如何在工作中实现创造力？

**回答：**

向面试官展示你能够在工作中善于利用资源并具有创新精神，同时不触碰公司价值观是非常重要的。解释你的灵感通常源于何（例如可以列清单或思维导图等练习），并将其与工作中某个需要创造力的特定任务联系起来。

## 38：你如何促使他人创造想法？

**回答：**

如果你处于管理职位，这可能要求员工提交特定数量的想法，或完成定期的灵感激发练习，以锻炼他们的创意肌肉。然而，你也可以通过创造更多自己的想法来促使周围的人创造想法。此外，与面试官讨论“质疑他人”的重要性，以此作为激发灵感和改变的方式。

## 39：描述一下你的创造力。

**回答：**

尽量将这个答案控制在专业领域，但如果你在职业经历之外的某些创意领域有令人印象深刻的背景，不要害怕将其包含在回答中。关于创造力的最佳回答将与解决问题的能力、目标设定，以及在工作中寻找创新方法来处理项目或完成销售有关。然而，办公室之外的爱好也很棒（只要它们不会占用你的工作时间或精神空间）。

## 40：你会如何处理负一个负能量的同事？

**回答：**

每个人都必须面对负能量的同事——做到这一点最好的方法是保持积极。你可能会尝试与同事建立关系或在某种程度上与他们产生共鸣，但即使你的努力遭遇了面对冷脸，你必须保持积极的态度。最重要的是，要强调你绝不会让同事的负面情绪影响你自己的工作或效率。

## 41: 如果你目睹同事在浏览网页、看书等浪费公司时间的行为，你会怎么做？

回答：

面试官会希望看到你意识到员工浪费公司时间是多么大的不利，并且你你认为这并不是一件可以轻视的事情。解释你将如何遵守公司政策，无论这包括亲自与该同事交谈、直接向主管汇报该行为，还是与人力资源部门（HR）的人员交谈。

## 42: 你如何处理自己以及与其他员工之间的竞争？

回答：

健康的竞争可能是一件好事，最好的办法是专注于其中的积极方面。不要提到你与其它同事之间的冲突，而要关注保持以跟上他人优秀表现的动力，以及同事如何成为一个极好的支持网络，帮助推动你迈向新的成功。

## 43: 什么时候与同事社交是合适的？

这个问题有两个极端的答案（一直社交，或者从不社交），在大多数情况下，你的面试官会希望看到你处于两者之间。与同事建立稳固的关系非常重要，但绝不能以牺牲工作为代价。理想情况下，关系的建立可以在团队协作练习和特殊项目中进行，也可以在休息室进行。

## 44: 告诉我说你上一份工作中发生重大变更的经历，以及你是如何处理的。

提供该情况的背景介绍，包括旧系统、变更是什么、如何实施的以及变更的结果，并包括你对每一步的感受。请确保你对旧系统的最初想法是中性的，并且你的兴奋程度随着新变更的每一步而增加，因为面试官会看到你的适应能力并感到很高兴。

## 45: 在委派任务时，你如何选择哪些任务分配给哪些团队成员？

回答：

面试官希望通过这个问题深入了解你的思维过程，因此请务必为你的选择提供详尽的理由。解释你根据每个人的个人专长来分配任务，或者你考虑每个人目前正在参与多少其他项目，以实现尽可能的匹配。

## 46: 告诉我说你曾向同事或主管维护过你坚定信认为的事物的经历。

回答：

虽然向面试官解释冲突的情况可能很困难，但这是展示你的激情、信念以及对信仰投入的绝佳机会。不仅向面试官解释情况，还要详细阐述为什么维护这个问题是如此重要，以及你的同事或主管之后是如何回应你的——他们是变得更有尊重了吗？还是不予采纳？开放心态？还是表达了歉意？

## 47: 告诉我说你曾帮助别人完成工作的经历，即使那不是“你的工作”。

回答：

虽然被要求为别人的工作收场时可能会感到沮丧，但对提供帮助保持积极态度是重要的。面试官将寻找你是否是一个具有团队合作精神的人，通过帮助他人完成他们独立无法处理的任务，你既展示了帮助团队成功的意愿，也展示了自己的胜任能力。

## 48: 团队工作的挑战是什么？你是如何处理的？

回答：

团队工作有很多显而易见的挑战，例如处理不同的观点、协调个人日程或适应难以合作的员工。最好专注于某一个挑战，例如个人团队成员错过截止日期或未能履行承诺，然后提供一个明确解决该问题的解决方案。例如，你可以为团队组织每周状态会议来讨论进度，或者分配更短的截止日期以确保长期截止日期按计划进行。

## 49: 你看重职场中的多样性吗？

回答：

多样性在职场中很重要，因为它能营造一个包容、平等且充满不同观点和背景的环境。务必表现出对这些问题的意识，并强调从他人经验中学习的重要性。

## 50: 如果一个同事不接受他人的多样性，你会如何处理？

回答：

解释遵守有关多样性的公司政策是重要的，并且你会与相关的主管或管理团队交谈。在适当的情况下，与相关同事谈论不同视角的益处可能是最好的——如果你可以自己处理这种情况，最好不要将可以解决的问题提交给管理层。

## 51: 团队工作和独立完成任务，哪种能让你获得更多回报？

回答：

最好的办法是在这两个方面之间表现平衡——你的雇主希望看到你对独立工作感到自在，并且可以在没有帮助高效、高质量地完成任务。然而，让雇主看到你是一个具有团队精神的人，并且你理解多个视角和努力能为项目带来的价值，也是同样重要的。

最后，祝你好好运！
