
## 23.9 Lock 和 Condition 接口

### 提示 23.5

在大多数情况下，非公平锁是优的，因为使用公平锁会降低等待性能。

### Condition 对象和接口 Condition

如果拥有 `Lock` 的线程确定在满足某些条件之前无法继续执行其任务，则该线程可以在 `condition` 上等待。使用 `Lock` 对象允许你显式地声明线程可能需要等待的 `condition` 对象。例如，在生产者/消费者关系中，生产者在一个对象上等待，而消费者可以在另一个对象上等待。在使用 `synchronized` 关键字时这是不可能的。

### Lock 和 Condition 与 synchronized

在应用程序中，使用 `Lock` 和 `Condition` 可能比使用 `synchronized` 好。`Condition` 对象允许你显式地声明线程可能需要等待的条件。

### 软件工程观察 23.7

将 `Lock` 和 `Condition` 视为 `synchronized` 的高级版本。

### 错误预防提示 23.6

使用 `Lock` 和 `Condition` 容易出错——不保证一定会被调用 `unlock()`，而 `synchronized` 语句中的监视器会被自动释放。

### 代码示例：SynchronizedBuffer.java

```java
// Fig. 23.20: SynchronizedBuffer.java
// 使用 Lock 和 Condition 接口对共享整数的访问进行同步处理
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;
import java.util.concurrent.locks.Condition;

public class SynchronizedBuffer implements Buffer {
    // 用于控制与此缓冲区同步的 Lock
    private final Lock accessLock = new ReentrantLock();

    // 控制读写的条件
    private final Condition canWrite = accessLock.newCondition();
    private final Condition canRead = accessLock.newCondition();

    private int buffer = -1; // 生产者和消费者共享
    private boolean occupied = false; // 缓冲区是否被占用

    // 将值放入缓冲区
    public void blockingPut(int value) throws InterruptedException {
        accessLock.lock();
        try {
            // 如果缓冲区不为空，将线程置于等待状态
            while (occupied) {
                System.out.println("Producer tries to write.");
                displayState("Buffer full. Producer waits.");
                canWrite.await(); // 等待缓冲区为空
            }

            buffer = value; // 设置新的缓冲区值
            // 表明生产者无法存储另一个值，直到消费者提取了当前缓冲区值
            occupied = true;

            displayState("Producer writes " + buffer);

            // 通知任何等待从缓冲区读取的线程
            canRead.signalAll();
        } finally {
            accessLock.unlock(); // 解锁此对象
        }
    }

    // 从缓冲区获取值
    public int blockingGet() throws InterruptedException {
        int readValue = 0; // 初始化从缓冲区读取的值
        accessLock.lock(); // 锁此对象

        try {
            // 如果没有数据可读，将线程置于等待状态
            while (!occupied) { // 修正逻辑：原代码此处 while(occupied) 与语义不符，应为 !occupied
                System.out.println("Consumer tries to read.");
                displayState("Buffer empty. Consumer waits.");
                canRead.await(); // 等待缓冲区填满
            }

            // 表明生产者可以存储另一个值，因为消费者刚刚提取了缓冲区值
            occupied = false;

            readValue = buffer; // 从缓冲区获取值
            displayState("Consumer reads " + readValue);

            // 通知任何等待缓冲区为空的线程
            canWrite.signalAll();
        } finally {
            accessLock.unlock(); // 解锁此对象
        }

        return readValue;
    }

    // 显示当前操作和缓冲区状态
    private void displayState(String operation) {
        try {
            accessLock.lock(); // 锁此对象
            System.out.printf("%-40s%d\t%b%n%n", operation, buffer, occupied);
        } finally {
            accessLock.unlock(); // 解锁此对象
        }
    }
} // 类 SynchronizedBuffer 结束
```

### 代码解析

`blockingPut` 方法中的第 23 行调用了 `accessLock` 的 `lock()` 方法。如果锁可用（即没有其他线程获取它），该线程将拥有该锁并继续执行。如果锁不可用（即它被另一个线程持有），该方法将等待直到锁被释放。获取锁后，执行后续逻辑。代码测试 `occupied` 以确定缓冲区是否满。如果是，将显示一条消息，指示线程将等待。调用 `canWrite` 对象上的 `await()` 方法，这会临时释放 `SynchronizedBuffer` 的锁，并等待来自消费者的可写信号。当缓冲区可用时，方法继续执行，写入缓冲区，将 `occupied` 设置为 `true`，并显示指示生产者已写入值的消息。调用条件对象 `canRead` 上的 `signalAll()` 方法，通知等待的消费者（如果有的话）缓冲区有新数据可读。最后在 `finally` 块中调用 `unlock()` 方法以释放锁并允许消费者继续。

`blockingGet` 方法调用 `lock()` 方法来获取 `Lock`。该方法等待直到 `Lock` 可用。一旦获取锁，测试 `occupied` 是否为 `false`，这表示缓冲区为空。如果是，调用条件对象 `canRead` 上的 `await()` 方法。回想 `blockingPut` 方法中在 `canRead` 上调用 `signalAll()` 方法（第 45 行）会唤醒等待线程。当 `Condition` 对象被通知时，`blockingGet` 方法继续执行。将 `occupied` 设置为 `false`，并将 `buffer` 的值存储在 `readValue` 中。最后在 `finally` 块中调用 `unlock()` 方法释放锁并将值返回给调用者。

### 常见编程错误

忘记调用 `signal()` 或 `signalAll()` 唤醒等待线程是一个逻辑错误。这种疏忽会导致无限期延迟。`Lock` 和 `Condition` 对象确保线程不会在违背顺序的情况下执行任务。如果生产者没有生产，消费者必须等待；如果消费者没有消费，生产者必须等待。运行此程序多次以观察并发行为。
