您的测试用例可以成功运行，并且一次执行一行时可以按预期工作，但是作为套件或批处理运行时，它可能会失败。挠头以了解其背后的原因？让我们深入了解！

当我们使用`driver.get("url_we_wish_to_access")`、`driver.navigate().to("url")`或单击超链接等时，这些调用将在加载活动完成之前启动页面加载并返回。因此，如果页面的加载线程尚未填充`WebElement`，而您尝试使用`driver.findElement("locating_strategy")`找到它，则得到的只是异常，即`NoSuchElementException`、`ElementNotVisibleException`等。

所有这些意味着我们必须找到一种告诉`Selenium`的方法：我们希望它等待一定的时间，或者直到`WebElement`变得可访问、可单击或显示，然后再引发可怕的异常。不要惊慌。我看到一些汗珠滴到你的额头上！那么，如何使这种压力成为我们自己的大力水手菠菜的版本？感谢**隐式等待、显式等待和流畅等待**。

## 隐式等待

了解我们使用`findElement`或`findElements`命令在`WebDriver`中定位`WebElement`非常重要（后面的文章将详细介绍该主题以及各种定位策略）。因此，当尝试在页面上查找特定的`WebElement`时，如果该元素不是立即可用的，则隐式等待会告诉`WebDriver`在指定的时间内轮询`DOM`。如果在指定的等待时间内找到该元素，测试将继续执行；如果没有找到，则抛出`NoSuchElementException`。

下面是带有隐式等待命令的代码片段，以便更好地理解：

```java
@Before
public void setUp() throws Exception {
    // Selenium version 3 beta releases require system property set up
    System.setProperty("webdriver.gecko.driver", "E:\\Selenium\\geckodriver-v0.10.0-win64\\geckodriver.exe");

    // Create a new instance for the class FirefoxDriver
    // that implements WebDriver interface
    driver = new FirefoxDriver();

    // Implicit wait for 3 seconds
    driver.manage().timeouts().implicitlyWait(3, TimeUnit.SECONDS);

    // Assign the URL to be invoked to a String variable
    baseUrl = "https://www.google.com";
    pageTitle = "";
    expectedTitle = "Google";
}
```

如突出显示的那样，使用隐式等待的语法是：

```java
driver.manage().timeouts().implicitlyWait(3, TimeUnit.SECONDS);
```

隐式等待有两个参数。在此示例中，第一个参数为`3`，这是它必须等待的时间；第二个参数为`TimeUnit.SECONDS`，表示时间单位。可以指定为`DAYS`、`HOURS`、`MINUTES`、`SECONDS`、`MILLISECONDS`、`MICROSECONDS`、`NANOSECONDS`等。

此外，在键入此语句时，`TimeUnit`下方会出现一条弯曲的线。悬停时，Eclipse会建议所有可能的快速修复。单击建议导入`java.util.concurrent.TimeUnit`包的第一个修复程序。

1. 隐式等待只需要初始化一次。设置后，它将适用于`WebDriver`对象实例的整个生命周期。换句话说，它将在浏览器打开的整个过程中就位。因此，`WebDriver`将在额外等待指定时间后，再对所有[`findElement`](https://selenium.googlecode.com/svn/trunk/docs/api/java/org/openqa/selenium/WebDriver.html#findElement(org.openqa.selenium.By))和[`findElements`](https://selenium.googlecode.com/svn/trunk/docs/api/java/org/openqa/selenium/WebDriver.html#findElements(org.openqa.selenium.By))调用抛出异常。

2. 默认时间设置为`0`。

3. 隐式等待仅影响`findElement(s)`，不会影响其他`WebDriver`方法，例如`driver.getCurrentUrl()`等。

4. 在大多数情况下，尤其是在调试时，仅有`NoSuchElementException`并不是很有用。我们可能希望使用更多信息来自定义此错误消息，例如捕获屏幕快照或添加更多详细信息等。可以通过在每次`findElement(s)`调用周围使用`try-catch`块来实现此目的，但这不是我们使用隐式等待的目标，因为隐式等待是一个全局性的时间设置。

5. 由于有大量的`JavaScript`，可能会出现一些奇怪的情况。即使元素位于`DOM`中，也可能无法立即单击、显示或启用它。结果，我们可能会看到[`ElementNotVisibleException`](https://selenium.googlecode.com/svn/trunk/docs/api/java/org/openqa/selenium/ElementNotVisibleException.html)、[`WebDriverException`](https://selenium.googlecode.com/svn/trunk/docs/api/java/org/openqa/selenium/WebDriverException.html)、[`StaleElementReferenceException`](https://selenium.googlecode.com/svn/trunk/docs/api/java/org/openqa/selenium/StaleElementReferenceException.html)。

6. 由于不同的元素可能在不同的时间加载，因此我们可能会说服自己将等待时间设置为较高的值，或设置为最慢`WebElement`的加载时间，例如`20`秒左右。我们的理由是：“无论如何，所有元素的加载速度都将比此时快，测试将按预期进行。”但是您甚至猜不到**性能**：这种方法不是一个好主意。我在这里给您举几个示例，以便更好地了解。

   **情况 1**：如果希望找到一个元素，但无论结果如何，都可以继续进行测试。

   **情况 2**：如果仅需要验证是否缺少某个元素，例如等待警报框出现并关闭它。即使这样，`WebDriver`也将不得不等到超时，即在这种情况下为`20`秒。在庞大的测试套件中运行时，这将产生巨大的影响。
