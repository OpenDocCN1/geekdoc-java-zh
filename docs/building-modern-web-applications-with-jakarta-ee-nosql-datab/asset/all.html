Jakarta EE platform

Jakarta EE is a platform that offers a set of components and APIs for the development of Java business applications. It orients towards the support of HTML5, Enterprise Java Beans, Web Services, JSON, Databases, Microservices, WebSocket among others.

These components are based on the combination of specifications (JSR) coming from the ecosystem of JavaEE platform led by Java Community Process (http://jcp.org) but rebranded under Eclipse Jakarta EE and Eclipse Microprofile standards (https://microprofile.io/); formed by companies, user groups, communities, which establish consensus on them, to be adaptable to the new requirements of the industry.

The APIs that are part of the specifications are known as Java Specification Request (JSR).

History

The Java EE platform has incorporated major changes in recent years, allowing a simpler development, performance improvements through reusable components resulting in lighter and scalable applications adapting to environments such as cloud, and Microservices.

Context and Dependency Injection CDI 2.0 (JSR 365)

Context and Dependency Injection (CDI) was introduced from Java EE 6, and the specification defines it as a set of services that allow objects to be linked to the context life cycle, injected, and associated with Interceptor and Decorator.

It allows interacting with events. Offers integration with Enterprise Java Beans components, Java Server Faces Managed Beans, Bean Validation. It supports asynchronous events.

Injection of dependencies can be performed at the level of:

  • Attributes
  • Constructor
  • Method

The permitted scoped are:

  • RequestScoped
  • SessionScoped
  • ApplicationScoped
  • ConversationScoped
  • DependentScoped

The specification defines some annotations that we will show in the following table:

@Named

It is the standard qualifier that allows us to define beans to be used by injecting dependencies with other beans and with expression language.

@Model

It helps to define a stereotype that identifies a particular bean that usually defines the layer of the MVC model.

@Inject

Allows declaring fields, methods, and constructors of a bean. To be injected.

@Producer

A production method acts as a source of objects to be injected. These objects do not need to be instantiated, may vary in run time, and cannot be initialized in the bean constructor.

@Qualifier

Through the annotation @Qualifier, we create qualifiers that help us identify one or a group of classes of other classes, among the advantages it provides is that we have more readable code.

@Intercepetor

Allows cross-cutting transversals to be applied, these can be enabled or disabled at runtime. They intercept calls to methods, and we can specify calls to other methods before or after invoking a method.

@Decorator

They apply only to beans in a particular Java interface, and they are very similar to Interceptors.

@Delegate

Identifies the delegate which uses the Decorator to delegate method calls to the container.

BASE verses ACID

While in the relational persistence technology, they use the ACID, which is an acronym for Atomicity, Consistency, Isolation, and Durability.

  • Atomicity: All of the operations in the transaction will complete, or none will.
  • Consistency: The database will be in a consistent state when the transaction begins and ends.
  • Isolation: The transaction will behave as if it is the only operation being performed upon the database.
  • Durability: Upon completion of the transaction, the operation will not be reversed.

In the NoSQL world, they usually focus on the BASE. As ACID the BASE is an acronym.

  • Basic availability: The database appears to work most of the time.
  • Soft-state: Stores don't have to be write-consistent, nor do different replicas have to be mutually consistent all the time.
  • Eventual consistency: Stores exhibit consistency at some later point (e.g., lazily at the reading time).

CAP theorem

There is no silver bullet; the CAP can explain it, based on three behavior. The following figure illustrates the same:

Figure 2.5

The CAP theorem applies to distributed systems that store state. Eric Brewer, at the 2000 Symposium on Principles of Distributed Computing (PODC), conjectured that in any networked shared-data system, there is a fundamental trade-off between consistency, availability, and partition.

Tolerance: In 2002, Seth Gilbert and Nancy Lynch of MIT published a formal proof of Brewer's conjecture. The theorem states that networked shared-data systems can only guarantee/strongly support two of the following three properties:

  • Consistency: A guarantee that every node in a distributed cluster returns the same, most recent, successful write. Consistency refers to every client having the same view of the data. There are various types of consistency models. Consistency in CAP (used to prove the theorem) refers to linearizability or sequential consistency - a very strong form of consistency.
  • Availability: Every non-failing node returns a response for all read and writes requests in a reasonable amount of time. The keyword here is every. To be available, every node (on either side of a network partition) must be able to respond in a reasonable amount of time.
  • Partition tolerance: The system continues to function and uphold its consistency guarantees in spite of network partitions. Network partitions are a fact of life. Distributed systems guaranteeing partition tolerance can gracefully recover from partitions once the partition heals.

  • There isn't any impact in change from one vendor to another; in some moments, it's necessary to use a specific database resource, but in this case, not everything in the DAO layer is lost.

Currently, in NoSQL, the database has no standard, so a Java developer has some issues:

  • Lock-in vendor
  • To each new database, it's necessary to learn a new API. Any change to another database has a high impact, and once all the communication layers will be lost, there isn't a standard API. This happens even with the same kind of NoSQL database; for example, a change in a column to another column.

There is a massive effort to create a common API to make the Java developer's life easier, such as Spring Data, Hibernate ORM, and TopLink. Introduction a JMoordb

It is a Java API for working with NoSQL databases. It supports methods to perform the most common operations on databases, collections, and documents. It is built to integrate with Java EE/Eclipse Jakarta. Benefiting from the APIs offered by the platform. Its syntax is very similar to the JPA specification, currently working to support Jakarta NoSQL.

This API is not a replacement for Jakarta NoSQL, it is an API focused mainly on MongoDB and document-oriented databases.

Before starting the development of applications that use jmoordb it is important to understand some basic concepts that will help in the development of the applications.

Entity

An entity is a Java class that represents the attributes of a document. They are defined by the standard Java data types by adding a set of annotations provided by Jmoordb. These Java classes are serialized and deserialized to be stored and retrieved from the NoSQL database.

Annotation

Annotations allow us to decorate the attributes with types and aspects that are used by the API to interact with databases and perform operations on them. The following are the list of annotations we have the following:

  • @Id: Defines the key field of the document.
  • @Ignore: The attribute will be ignored in the document.
  • @Embedded: Defines an embedded document, the entire content will be stored in the document.
  • @Referenced: Defines a document that is referenced, only the value of the key field of the referenced document is stored.
  • @Secondary: Indicates that the attribute is a secondary key.

An example of a simple entity that represents a Person class:

public class Person {

@Id

private String id;

private String name;

}

@Id

The @Id annotation identifies the attribute used as the primary key, remember that NoSQL databases such as MongoDB use an internal field that identifies one document from another. Each entity must have a @Id attribute.

The primary keys are used to identify a unique document within the collection and avoid duplication of data. When key fields are autoincrementable type they do not have a direct representation in databases such as MongoDB we must establish their control by programming.

When you want to work with autoincrementable as primary keys, we have to keep in mind that some databases like MongoDB internally generate a field that is unique for each document but does not offer a mechanism to establish another field as a primary key that is autoincrementable. In jmoordb, we offer a simple way to implement it by means of autoincrementableServices that offers a getContador("") method that allows to take a counter of documents of the collections that are specified as parameters.

Integer idperson = autoincrementableServices.getContador("person");

@Ignore

In some situations, you define some attributes in the entity, but you do not want them to be stored in the database documents. That is, they are ignored by the API. For these types of fields we use the @Ignore annotation:

public class Person {

@Id

private String id;

private String name;

@Ignore

private String comment;

}

@Embedded

An embedded document is a document that is inserted into another document. It is one of the characteristics of NoSQL databases that makes it very useful and allows us to improve data models that are not possible to do in relational databases. The API allows us to define an embedded document or a list of embedded documents. This document is defined by another entity defined using the respective annotations.

The use of embedded documents depends on the particular situation in which you want to use them. For example, if you have documents embedded in others, and these need to be updated, you would have to review all the documents to update the embedded documents. This can be a limitation if the database is not well designed.

The following is an example of how to define embedded documents:

public class Country {

@Id

private String id;

private String country;

}

public class Person {

@Id

private String id;

private String name;

@Embedded

private Country country;

}

To define a list of embedded documents, use a syntax similar to this List<T>:

public class Person {

@Id

private String idperson;

private String name;

@Embedded

List<Country> country;

}

@Referenced

A document referenced is a document that stores the reference to the key field of the other document. Jmoordb offers a simple mechanism to manage references between documents. Using references avoids duplication of documents that can occur when using embedded documents. Their use is associated with the design of the database and is adapted to particular needs, simulating the relationships between documents.

For example, a document embedded with the information of a country is stored within 100000 documents of a collection called Person. You can see that the same information from the country Panama is found in all the documents of people living in Panama.

With that design the information is duplicated, consuming more storage space, and to make any change in the country's information, one would have to review all the documents of the people where they are and edit them, which would directly impact the performance of the application.

Layers, layers, and more layers

The number of layers in an application is always a colossal discussion when we talk about microservices. Layers are essential to split responsibility and write clean code, while maintaining the several patterns built following this approach, like the MVC.

However, a vast number of layers are also hard to keep, and to maintain; we need to pay attention to the delay layers. Otherwise, instead of an MVC, we're creating the onion pattern, where you cry each time you go through a layer. There is no magic formula to determine the number of layers you'll need. Rather, it will be based on the complexity of the business rules, and how the infrastructure code can give us the cleanest architecture.

In our sample, we have three layers:

  • The entity: The first instance of the business and where the domain lives. These entities, for best practice, should follow a rich model. We can make these entities agnostic to a database, but this time, let's keep it simple and use the entity highly coupled with the database.
  • The data transfer object (DTO): Just a dump class to allow transfer values between the controller and the entity. It's most prominent goal is to prevent that entity from becoming an anemic model, because some frameworks might require getter and setter methods to serialization, which usually means weak encapsulation.

  • The controller: The bridge between the view and the model. It only manipulates the flow among them. With small exceptions, it must keep clean as possible–you remember the high cohesion rule, right?

Jakarta EE

The security of applications and microservices is a crucial issue to ensure the integrity of the operations performed.

The Jakarta Security specification is the equivalent of the specification defined by the JSR-375 Java EE Security API. The base document for the specification can be found at https://projects.eclipse.org/projects/ee4j.es/governance. Some concepts that define the specification:

  • Authentication Mechanism: This is the mechanism by which the server interacts with the caller to obtain the credentials and invoke the identity store to verify the identity.
  • Caller, Caller Principal: It is the user who requests the application. The MainCaller is the object that represents the user.
  • Identity Store: It is a component that can access the specified security of the application such as users, groups, roles, and permissions. An identity store can be through Data Access Object, LDAP directory, file system, etc.

IdentityStore is defined by the specification as an abstraction of an identity store which is a database or directory with the information of the identities of the users who are application callers. It can be used for implementations with HttpAuthenticationMechanism and other types of authentication mechanisms

The IdentityStoreHandler interface allows you to invoke an Identity Store and validate a user's credentials.

It has two methods:

  • validate(Credential): Validates the credential and returns information about the user.
  • getCallerGroups(CredentialValidationResult): It returns all the groups associated with the caller.

Eclipse MicroProfile Interoperable JWT RBAC

It is a Microprofile specification that establishes how to implement JSON Web Token (JWT) with microservices. It uses OpenID Connect (OIDC) and JWT (JSON Web Tokens) for role-based access control (RBAC). The specification can be consulted at the following link:

https://github.com/eclipse/microprofile-jwt-auth/releases/download/1.1/microprofile-jwt-auth-spec-1.1.pdf

The specification defines some characteristics such as:

  • RESTFUL Security is the architecture to guarantee the security of microservices.
  • Microprofile Microprofile is built on standard APIs such as JAX-RS, CDI, and JSON-P.
  • One of the ways to spread security from customers to services and from services to services is through the use of tokens.
  • The services do not store the status of the client.
  • Services can identify the caller by introspection on the token.

The specification also defines Token-Based Authentication as a mechanism to enable systems to authenticate, authorize, and verify token-based identities. It also defines the entities involved:

  • Issuer: Responsible for issuing the token.
  • Client: This is the application for which the token was issued. It also acts as an intermediary between a subject and the target service.
  • Subject: Entity to which the token information refers.
  • Resources Server: Application that consumes the token.

@javax.enterprise.context.ApplicationScoped

public class CypherService {

private static final Logger LOG = Logger.getLogger(CypherService.class.getName());

private String issuer;

private int tokenValid;

private String audience;

private String headerKey;

private final Collection<String> roles = new LinkedHashSet<>();

@javax.annotation.PostConstruct

public void init() {

Security.addProvider(new BouncyCastleProvider());

LOG.info("Credentials loaded");

}

public String createToken(PrivateKey key, String username, Collection<String> groups) {

LocalDateTime now = LocalDateTime.now();

LocalDateTime expiration = now.plus(tokenValid, ChronoUnit.SECONDS);

return Jwts.builder()

.setHeaderParam("typ", "JWT")

.setIssuedAt(Date.from(now.atZone(ZoneId.systemDefault())

.toInstant()))

.setExpiration(Date.from(expiration.atZone(ZoneId.systemDefault())

.toInstant()))

.signWith(SignatureAlgorithm.RS256, key)

.setSubject(username)

.setAudience(audience)

.setHeaderParam("kid", headerKey)

.claim("groups", groups)

.setId(UUID.randomUUID().toString())

.setIssuer(issuer).compact();

}

public PrivateKey readPrivateKey() throws IOException, NoSuchAlgorithmException, InvalidKeySpecException {

try (InputStream is = CypherService.class.getResourceAsStream("/jwt-config.json")) {

JsonObject json = Json.createReader(is).readObject();

String keyString = json.getString("private-key");

this.issuer = json.getString("issuer");

this.audience = json.getString("audience", "audience");

json.getJsonArray("roles").stream()

.map((v) -> (JsonString) v).forEachOrdered((s)

-> roles.add(s.getString()));

this.tokenValid = json.getInt("token-valid");

this.headerKey = json.getString("header-key");

byte[] encoded = Base64.getDecoder().decode(keyString);

return KeyFactory.getInstance("RSA").generatePrivate(new PKCS8EncodedKeySpec(encoded));

}

}

public Collection<String> getRoles() {

return roles;

}

}

@Consumes(MediaType.APPLICATION_FORM_URLENCODED)

public Response login(

@FormParam("password") String password,

@Context HttpServletRequest request) {

if (key == null) {

}

try {

cypherService.getRoles()

.stream()

.filter((role) -> (request.isUserInRole(role)))

.forEachOrdered((role)

-> target.add(role)

);

}

Tekton Framework

Tekton is a framework based on Kubernetes that makes the creation of CI/CD systems more flexible. With it, it is possible to test various cloud providers by abstracting the details of the implementation. (https://cloud.google.com/tekton/).

The components are:

  • Task: These are the jobs that must be executed. They are like the Pod of a Kubernetes cluster.
  • TaskRunner: Executes the defined tasks.
  • PipelineResources: It defines the artifices that are used by a task.
  • PipelineRun: Defines the list of tasks to be executed.

The requirements are very basic:

  • Install Kubernetes:

    snap install kubectl --classic

    kubectl version

    To install it we follow the following steps:

    kubectl apply --filename https://storage.googleapis.com/tekton-releases/pipeline/latest/release.yaml

    The execution is done by:

    kubectl get pods --namespace tekton-pipelines

    The following examples are part of the official documentation that you can find at https://github.com/tektoncd/pipeline/blob/master/docs/tutorial.md

  • Create a task:

    apiVersion: tekton.dev/v1alpha1

    kind: Task

    metadata:

    name: echo-hello-world

    spec:

    steps:

    - name: echo

    image: ubuntu

    command:

    - echo

    args:

    - "hello world"

  • Create a TaskRunner:

    apiVersion: tekton.dev/v1alpha1

    kind: TaskRun

    metadata:

    name: echo-hello-world-task-run

    spec:

    taskRef:

    name: echo-hello-world

  • Now create a PipelineResources:

    apiVersion: tekton.dev/v1alpha1

    kind: PipelineResource

    metadata:

    name: skaffold-git

    spec:

    type: git

    params:

    - name: revision

    value: master

    - name: url

    value: https://github.com/GoogleContainerTools/skaffold

  • Creating the Pipeline:

    apiVersion: tekton.dev/v1alpha1

    kind: Pipeline

    metadata:

    name: tutorial-pipeline

    spec:

    resources:

    - name: source-repo

    type: git

    - name: web-image

    type: image

    tasks:

    - name: build-skaffold-web

    taskRef:

    name: build-docker-image-from-git-source

    params:

    - name: pathToDockerFile

    value: Dockerfile

    - name: pathToContext

    value: /workspace/docker-source/examples/microservices/leeroy-web #configure: may change according to your source

    resources:

    inputs:

    - name: docker-source

    resource: source-repo

    outputs:

    - name: builtImage

    resource: web-image

    - name: deploy-web

    taskRef:

    name: deploy-using-kubectl

    resources:

    inputs:

    - name: source

    resource: source-repo

    - name: image

    resource: web-image

    from:

    - build-skaffold-web

    params:

    - name: path

    value: /workspace/source/examples/microservices/leeroy-web/kubernetes/deployment.yaml #configure: may change according to your source

    - name: yamlPathToImage

    value: "spec.template.spec.containers[0].image"
